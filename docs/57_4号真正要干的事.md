## 一、P95 显示 0ms：看着最好，其实是没样本（最该先修）

**线上现在就是这样**：

```
headline.first_audio_p50_ms = 2358.0
headline.first_audio_p95_ms = 0        ← 19 个样本
headline.first_audio_samples = 19
```

样本不足 20 时 `p95()` 返回 `None`（`events.py:481-483`，注释写得很好："样本太少时
P95 等于最大值，容易造成误判，干脆不出"），但 `events.py:494-497` 用 `or 0` 兜底：

```python
"processing_p95_ms": round(p95(processing) or 0, 1),
"first_audio_p95_ms": round(p95(voice_vals) or 0, 1),
```

结果前端看到的是 `0ms`。**0ms 是"最快"的意思**，不是"没有数据"。任何人扫一眼看板
都会读成"P95 为 0，性能极好"，而 P50 是 2358（已经超了 2000ms 的闸门）。

- 修法：`None` 就传 `null`，前端显示"样本不足（19/20）"，别塞 0。
- 注意：`processing_p95_ms` 与 `first_audio_p95_ms` 两处都要改，只改一处等于留一半。
- 验收：临时库跑 19 轮语音 → 看板 p95 显示"样本不足"；跑到 20 轮 → 出真数；
  `verify.py` 里加一条断言"样本不足时 p95 必须是 None 而不是 0"。
- 归属：4 号自己。`dashboard.py` 的字段名不改，只改值。

## 二、事件库活不过一次部署（答辩当天数据是空的）

`prep_deploy.py` 每次都把 `data/events.db` 移进 `data/archive/`——这是对的，
11-12 那次 `socket hang up` 事故就是坏库被带进部署包。但代价是：

- 容器换一次 → 看板归零，`/api/dashboard/summary` 里只有本次容器内的事件；
- 现在线上看到的 31 通 / 594 事件，是这个 sandbox **复用**留下来的，不是真的持久化；
- 答辩习惯是"先跑几通给人看，再看板讲数据"——如果中间重启/重发，看板就空了。

两条路，选一条，别两条都做：

1. **演示用种子库**（省事）：跑一段脚本生成一批标了 `source=demo` 的事件，随包带一个
   只读 `data/demo_events.db`，看板支持 `?db=demo` 只读打开。答辩前不用现跑。
2. **真正的持久化**（工程上对）：事件落外部存储（对象存储/远端库），容器只做写入端。
   这个在赛题周期内大概做不完，且会引入网络依赖——**不建议现在动**。

- 验收：删掉容器内 `data/events.db` 重启 → 看板仍有种子数据，且明确标了是演示数据。
- 归属：4 号自己。**关键是不能让看板把演示数据当成真实通话统计汇报**，
  这和第一条是同一类问题：数字好看但含义不对。

## 三、幂等库 `tickets.db` 不在部署清理清单里

`modules/adapters/store.py` 默认落 `data/tickets.db`（`_DEFAULT_PATH`），
`prep_deploy.py` **只处理 `events.db`**（`DB = os.path.join(DATA, "events.db")`）。

现在 `tools.idempotency_store` 没配，走的是内存，所以还没炸。一旦按建议配上 sqlite：

- 每次部署把**上一轮的工单**带上去；
- 演示"同一通电话重复建单只建一张（`created=False`）"时，可能读到上一轮的旧单，
  看起来"幂等生效了"，其实是读到了别的通话——**假绿**；
- 真要开，`prep_deploy.py` 必须一起清 `tickets.db`（或同样归档），并加一条断言：
  新容器里 `ticket_for_session` 对全新 session 必须返回 `None`。

- 归属：4 号（`prep_deploy.py` + 配置）。开不开 sqlite 需要和 1 号一起定，
  因为"演示幂等"这件事到底要不要做，取决于答辩怎么讲。
