# 任务 1 实现方案：实时语音与终端

> 负责人：张博涵（1 号·队长）
> 对应模块：M1 浏览器终端、M2 实时语音网关；对应代码：`modules/voice.py`、`web/index.html`、`app.py` 的传输层
> 版本：v1 草案（2026-11-03）。本文只讲怎么做，不含代码。契约依据：`docs/03_事件契约.md`、`docs/04_时延打点规范.md`、`contracts.py`（v1）

## 0. 一句话定位

**任务 1 不做任何语义判断，只负责"把声音又快又准地搬过去、再把声音搬回来，并且随时能被用户打断"。**

判断"这句话什么意思""下一句该说什么"是 2A 佟欣的事；判断"该查哪个订单"是 2B 潘柏亦的事。任务 1 的边界就三件事：

| 做什么 | 不做什么 |
|---|---|
| 采集音频、判端点、把音频变成文字 | 不判断这句话的业务含义 |
| 把文字变成声音、按时播出来 | 不决定说什么内容 |
| 播报期间监听用户、命中就停 | 不改状态机、不写话术 |

**这个边界必须守住。** 一旦任务 1 开始"顺便做点意图判断"，就会和 2A 的代码打架，而且两个人都会以为对方在做。

## 1. 现状：骨架里已经有什么，假在哪

先把话说清，避免照着文档以为已经实现了。

| 现在有的 | 位置 | 真实程度 |
|---|---|---|
| 半双工录音（点一次录、再点一次发） | `web/index.html` 的 `toggleRec` | 真的能录音，但整段上传，不是流式 |
| 音频上传接口 | `POST /api/turn`，字段 `audio_b64` | 真的，但服务端不解码 |
| VAD 占位 | `voice.vad_detect()` | **假的**：只要有字节就判"有人说了话" |
| ASR 占位 | `voice.asr()` | **假的**：不看音频，返回固定句 |
| TTS 占位 | `voice.tts()` | **假的**：服务端不合成，前端用浏览器 `speechSynthesis` 念 |
| 打断占位 | `voice.detect_barge_in()` | **假的**：恒为 `False` |
| 时延打点 | `app.py` 的 `latency` | **口径不对**：是"服务端处理一轮"的耗时，不含用户说完之前、也不含声音播出来之后 |

结论：**声音这条链路上真正跑通的只有"声音能传上来、能播出去"，其余四段全是占位。** 任务 1 的活就是把这四段换成真的，并把打点口径改对。

## 2. 主要思路：一条双向管道 + 一条横切的打断线

### 2.1 为什么不能继续用"整段上传"

现在的做法是：录完整句 → base64 → 一次 HTTP 请求。它有三个绕不过去的缺陷：

1. **必须等用户说完才能开始识别**，首字时延天然多出整段录音时长；
2. **传不了中间结果**，2A 无法在用户还没说完时预判意图；
3. **做不了打断**：请求-响应模型里，服务端在等回复，没有"下行音频"这个概念，也就没有"中途掐掉"的对象。

所以任务 1 的第一个结构性改动是：**把一次性的 HTTP 请求，换成一条双向长连接（WebSocket）**，上行音频帧、下行音频帧、控制指令（cancel / barge_in）全部走这一条连接。

### 2.2 三段解耦

管道拆成三段，每段可独立替换、独立测：

```
上行：麦克风 → 采集分帧 → VAD → 流式 ASR → 文本
下行：文本 → 流式 TTS → 音频帧 → 播放队列
横切：打断（播报期间并行 VAD，命中即三层取消）
```

**为什么要解耦成三段**：如果一开始就把它们焊在一起，接云 ASR 时改不动、换 TTS 时又要重写，最后只能整段重来。拆开之后，每段都能先用假实现占位，逐个替换——这也是骨架现在采用的策略，只是要从"整段"升级成"流式"。

### 2.3 为什么先 WebSocket、后 WebRTC

赛题原文要求"在 WebRTC 网页端跑通"，这一点不能忽略。但第一周就上 WebRTC 的代价是：

- 需要信令服务器（另一个人力）、ICE/STUN、SDP 协商；
- 音频编码要换成 Opus，服务端还要解码；
- 一旦不通，排障面非常大（是信令、NAT、还是编码？）。

**我的建议是分两步**：先 WebSocket + PCM 把"流式 + 打断"跑通（已经有分、能拿维度 1 的分），再在 K3 之后把传输层换成 WebRTC——**接口不变，只换运输方式**。这是一次有意的取舍，答辩时要主动说明，不要假装已经是 WebRTC。

## 3. 关键步骤（按依赖顺序，每步都有验收标准）

### S1 采集改造：从 MediaRecorder 换成 AudioWorklet

**做什么**：把"录一段 webm"改成"按 20ms 切 PCM 帧，边采边发"。

- 用 `getUserMedia` 拿麦克风，带约束：`echoCancellation: true`、`noiseSuppression: true`、`autoGainControl: true`（**回声消除必须开**，否则播报声会被自己的麦克风收进去，VAD 会以为用户在说话）；
- 用 `AudioContext` + `AudioWorkletNode` 拿原始 PCM，**不要用 `MediaRecorder`**——它给你的是压缩后的 webm，无法切帧、无法算能量；
- 浏览器一般是 48kHz，要重采样到 **16kHz / 16bit / 单声道**（ASR 通用输入格式），在 worklet 里做或单独一个重采样节点；
- 每 20ms 一帧（320 采样点）通过 WS 二进制帧发出去。

**验收**：后端能连续收到帧、帧号不跳、10 秒录音后台端收到的样本数 ≈ 160000；页面 F12 里没有丢帧警告。

### S2 传输层：加一条 WebSocket 通道

**做什么**：在 `app.py` 加 `/ws/call`，与现有 HTTP 接口并存（不改动、不删除任何现有接口）。

- 用 `websockets` 或 `aiohttp`，或直接用标准库手写（标准库没有内置 WS 服务端，需要引入依赖——这是**全项目第一次引入第三方包**，必须写进 README 并告知全员）；
- 消息分两类：**二进制帧**（音频）和 **JSON 文本帧**（控制指令：`start`、`stop`、`cancel`、`barge_in`）；
- 服务端每条 WS 连接对应一个 `session_id`，与 HTTP 侧的会话表复用同一份状态。

**验收**：浏览器连上后能持续推帧 30 秒不断线；服务端能主动下发一条 `cancel` 并被前端收到；部署到线上沙箱后同一个链接也能建立 WS（**这一步要单独验，反向代理可能不支持 upgrade**）。

**这一步要 4 号黄睿哲配合**：`app.py` 是他的区域，按 README 的约定"传输层由 4 号改，1 号只提供 `voice.py` 的接口"。

### S3 VAD：从"有字节就算说话"换成真判定

**做什么**：在浏览器端做端点检测，判"用户开始说"和"用户说完"。

两种做法，**建议直接用第二种**（2026-11 复核后修正：原来写的"先手写门限"是错的，见下）：

| 做法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 能量 + 过零率双门限 | 分帧算 RMS 能量，超过自适应噪声底一定倍数算语音 | 零依赖、可解释 | **换个房间就要重调**，空调声、键盘声都能骗过它 |
| **Silero VAD**（首选） | 小型 ONNX 模型逐帧判语音概率，约 2MB | 抗噪好、跨环境稳定、CPU 实时 | 多一个模型文件 + onnxruntime 依赖 |

**为什么改口**：手写能量门限不是写不出来，而是"自适应噪声底"在真实房间里调不稳——安静房间调好的系数，到有空调的教室就完全失效。你可能要花两三天调参，而 Silero 装上就跑。

另外还有一层**必须单独解决**的问题：VAD 只能判"有没有声音"，判不了"这句话说完了没有"。用户思考时停顿 500ms，纯 VAD 就会误判成说完，客服抢话。这一步叫**轮次判定（turn detection）**，有两个现成件：

- **Pipecat Smart Turn v3.2**：BSD 许可，8MB 量化 ONNX，CPU 上部分场景约 10ms，支持 23 种语言，输入是"音频 + 部分转写文本"，输出"这一轮是否结束"；
- 或用"VAD + ASR 端点信号"两层简单相关（LiveKit 的思路，零额外推理，但停顿多的人会被抢话）。

**建议**：先用 VAD + 200ms 静音判结束跑通，把 Smart Turn 作为"停顿被误判"出现后的第一个补丁。它解决的是真实痛点，不是锦上添花。

关键细节，三条都必须做：

1. **噪声门限交给 Silero，不要手调**。只保留一个"最短语音时长"过滤（≥200ms），否则咳嗽、键盘声都会触发一轮；
2. **播报期间提高判定阈值**：Silero 的概率阈值从 0.5 抬到 0.7–0.8，配合 `echoCancellation`，避免自激；
3. **判定延迟可调**：结束判定等 200–300ms 静音再下结论，这段直接进 T0 之前，不要设成 800ms。

**验收**：安静房间连说 10 句、漏检 ≤1；播报期间不触发误打断；说完到判定结束 ≤ 250ms。

### S4 流式 ASR：把音频帧变成文字

**做什么**：把 WS 上行的音频帧喂给流式识别，拿回 `partial`（中间结果）和 `final`（最终结果）。

选型建议（详见 `docs/05_技术选型对比.md` 第 9 节）：两条都做，先做有账号的那条。

| 路线 | 首字延迟 | 上手成本 | 适合情况 |
|---|---|---|---|
| **云流式 ASR**（讯飞/阿里/腾讯） | 200–400ms | 当天能通，要实名账号、按量计费 | 已经有账号、想尽快拿到基线 |
| **FunASR 本地流式** `paraformer-zh-streaming` | 约 600ms 一档增量 | 半天到一天，要装 torch、下模型 | 不想花钱、想讲"数据不出机器" |

本地这条路的关键参数（官方文档口径）：`chunk_size=[0,10,5]`（左/中/右，单位 60ms，中间 10 即 600ms 一档）、`encoder_chunk_look_back=4`、`decoder_chunk_look_back=1`，`cache` 字典跨 chunk 复用，最后一块传 `is_final=True` 收尾。

**务必用它的两遍方案**：流式结果只用于即时反馈，一句话结束（VAD 判端点）后**用离线模型重解码整句替换**。流式的准确率天生低于离线，不做这步，字准率很难过 90%。

不要自己训模型。赛题允许用现成的，训模型是纯负收益。

关键设计：

- `partial` 只用于**提前判断意图**（给 2A 用，属于增强，不是必须），不写进事件库，否则事件量爆炸；
- `final` 才写 `asr_result` 事件，并带 `confidence` 和 `latency_ms`；
- 必须带 `hints`（热词），否则"张伟""订单号 2026…"这类专有词错得离谱。

**验收**：说 20 句常用业务话术，字准率 ≥90%（人工数）；首字延迟实测记录；`asr_result` 事件的 `fake` 字段改为 `false`。

### S5 流式 TTS：把文字变成声音，首包就播

**做什么**：替换浏览器的 `speechSynthesis`，改服务端流式合成，音频帧下推前端。

- 必须用**流式合成**接口，不能等整句合成完——这一段的 150–300ms 是首字时延里最不该浪费的；
- 前端拿到音频帧后**不要一句一个 `new Audio()`**（会有缝、有咔哒声），要用 `AudioContext` 排程：维护一个播放时间游标，每帧按 `start(at)` 精确排到下一位；
- 音色、语速从 `config/scene.json` 读，方便换场景。

**验收**：同一句话，服务端首包 ≤300ms；连续播 5 句无断裂、无重叠；浏览器 `speechSynthesis` 完全停用。

### S6 打断：三层取消，缺一层就不算做到

**做什么**：用户一开口，立刻停。

这是任务 1 最难的一段，因为"停"不是一个动作，是**三个层面同时停**：

| 层 | 要停什么 | 不停会怎样 |
|---|---|---|
| 播放层 | 清空播放队列、`stop()` 当前音频源 | 声音还在响，用户以为没听见他 |
| 合成层 | 取消未完成的 TTS 请求 | 后续音频继续下推，边播边响 |
| 生成层 | 通知 2A 中断本轮生成 | 模型还在生成，回来把已废的文本播出去 |

流程：`播报中 → 麦克风持续 VAD → 命中语音 → 立即①停播 + ②发 cancel 给后端 + ③记 barge_in 事件 → 回到聆听`。

**验收**：播报第 2 秒时插话，声音在 300ms 内停止，状态机回到聆听且不重复播报上一句；`barge_in` 事件带 `latency_ms`（从开口到停播）。

### S7 打点：把 T0–T4 落进事件

按 `docs/04` 的规范，需要给事件 payload 补四个字段（都是选填，**不需要升版本号**，但要同步更新 `docs/03`）：

| 点位 | 落在哪 | 谁写 |
|---|---|---|
| T0 用户说完 | `vad_result.payload.speech_end_ts` | 任务 1（浏览器给 `performance.now()`，服务端换算） |
| T1 识别完成 | `asr_result.payload.latency_ms` + 事件 `ts` | 任务 1 |
| T2 首 token | `agent_reply.payload.first_token_ms` | 2A 佟欣 |
| T3 TTS 首包 | `tts_start.payload.latency_ms` | 任务 1 |
| T4 用户听到 | `turn_end.payload.first_audio_ts` | 任务 1（浏览器回传） |

**验收**：页面能显示 `T4 − T0` 的真实值（不是现在的 `total_ms`），并且这个值在 1.4s 左右。

## 4. 技术点清单

| 层 | 必须掌握的点 | 容易踩的坑 |
|---|---|---|
| 浏览器采集 | `getUserMedia` 约束、`AudioContext`、`AudioWorklet`、重采样 | 用 `MediaRecorder` 拿不到 PCM；不重采样则 ASR 报格式错 |
| 浏览器播放 | `AudioBufferSourceNode` 排程、播放游标 | 一个句子一个 `Audio` 会有缝；`currentTime` 用错会重叠 |
| 传输 | WebSocket 二进制帧、心跳、重连、背压 | 反向代理不支持 upgrade；帧积压导致延迟越拖越大 |
| 端点检测 | Silero VAD（ONNX，CPU）、最短语音时长、播报期阈值抬高 | 手调能量门限，换个房间就废 |
| 轮次判定 | 静音阈值 vs Smart Turn（模型判"说完没"） | 停顿 500ms 就抢话，用户以为被插嘴 |
| 语音识别 | 流式接口、partial/final、热词、置信度 | 把 partial 当 final 用，导致重复回复 |
| 语音合成 | 流式首包、音频格式（pcm/mp3/opus）、按句切分 | 等整句合成，白白多 500ms |
| 打断 | 三层取消、AEC、播报期门限 | 只停播放，后端还在推流 |
| 工程 | 并发连接管理、异常兜底、成本限流 | 无兜底：云服务一挂整通电话哑掉 |

## 5. 难点与风险（按危险程度排序）

### 难点 1：回声自激——打断功能的生死线

**为什么难**：麦克风会收到扬声器的声音。播报不停，VAD 就一直"听到有人在说话"，于是刚播一句就自我打断，陷入死循环。

**怎么解**（三条一起上，缺一条都可能失效）：

1. `getUserMedia` 开 `echoCancellation: true`（浏览器自带 AEC，效果对"自己播的声音"还不错）；
2. 播报期间 VAD 门限抬高 1.5–2 倍；
3. 演示时**戴耳机**——这是最可靠的一条，但要写进答辩说明，别装作是算法解决的。

### 难点 2：首字 ≤2s 是硬门槛，而时间分布在三个人手里

**为什么难**：`T0→T1`（端点+识别，任务 1）、`T1→T2`（模型首 token，2A）、`T2→T3→T4`（合成+起播，任务 1）。**任何一段超预算，整条就废。**

**怎么解**：先用假 ASR/假 TTS 把 `T0→T1` 和 `T3→T4` 压到预算内（这两段完全由你控制），再去催 2A 的 400ms。**先把自己那段做到位，谈判才有底气**。

### 难点 3：WebSocket 在线上沙箱能不能通

**为什么难**：现在线上是单端口反向代理，HTTP 通了不代表 WS 能 upgrade。如果上线才发现不通，会打乱演示计划。

**怎么解**：S2 一做完就**同时在本机和线上各验一次**，不要等最后。万一线上不支持，退路是 HTTP 长轮询（能做，但延迟更差），或者演示只用本地环境。

### 难点 4：外呼通道这件事赛题没定义

**为什么难**：赛题只给了 Mock 业务系统接口（名单/订单/工单），**没说"拨号"这个动作走什么通道、被叫方是谁**。如果官方要求接 SIP/PSTN（真打电话），任务 1 的边界会扩大到需要媒体网关（FreeSWITCH/Asterisk），那是完全另一个量级的工程。

**怎么解**：这条已经列进答疑必问清单。**在答案回来之前，按"网页端就是终端"来做**——这也是赛题原文"WebRTC 网页端"的字面理解。但心里要留一手：如果要求接 PSTN，这块要提前两周启动。

### 难点 5：噪声与双讲

**为什么难**：现场演示环境不可控（教室回声、走廊人声），双讲（用户和客服同时说）在真实电话里很常见。

**怎么解**：第一版不做真双讲（那是全双工，复杂度翻倍），做**半双工 + 可打断**：播报时也能听、命中即停，但不会"边播边说"。这已经能满足赛题的打断要求，且稳定得多。

### 难点 6：并发与成本

**为什么难**：ASR/TTS 按并发或时长计费，压测时很容易超。云服务一挂，整通电话哑掉。

**怎么解**：`config/` 里配并发上限与单通时长上限；ASR/TTS 调用加超时 + 降级（超时就先用静态话术 + 浏览器 TTS 顶一下，至少不断线）。

## 6. 输入输出

### 6.1 对外接口（与 2A / 2B / 前端之间）

| 方向 | 内容 | 形态 |
|---|---|---|
| 上行输入 | 用户语音 | 16kHz/16bit/单声道 PCM，20ms 一帧，WS 二进制 |
| 上行输出 | 识别文本 `final` | `{text, confidence, latency_ms, fake:false}` |
| 上行输出（增强） | 识别文本 `partial` | `{text, stable:bool}`，只推给 2A，不入库 |
| 下行输入 | 待播文本 | `{text, voice, speed}`，来自 2A |
| 下行输出 | 合成音频 | 流式音频帧，WS 二进制 |
| 控制 | 取消 | `{type:"cancel", reason:"barge_in"}` |
| 控制 | 打断上报 | 事件 `barge_in`，带 `latency_ms` |

### 6.2 事件输出（写给 3 号刘源消费）

| 事件 | 关键字段 | 用途 |
|---|---|---|
| `vad_result` | `started`、`ended`、`speech_ms`、`speech_end_ts` | VAD 准确度、T0 |
| `asr_result` | `text`、`confidence`、`latency_ms`、`fake` | 识别质量、T1 |
| `tts_start` | `text`、`latency_ms` | T3、合成耗时 |

## 10. 三个判断，说在前面

**① 这块确实最难，但难在工程细节，不难在算法。**
难点不是"写出一个 VAD"，而是"让五段各 200ms 的东西加起来不超过 1.4 秒，并且在被打断的瞬间三层同时停住"。这些靠调试和取舍，不靠模型能力。所以由一个人从头盯到尾是对的——**它最怕换人**。

**② 一个人扛得住，前提是砍掉两件事**：不自研 ASR/TTS（用云 API），不在第一周上 WebRTC。砍掉这两件，工作量大约是"两周满负荷"；不砍，会拖住全队。

**③ 这块是唯一"数据必须实时"的模块，也是全队唯一的阻塞点。**
其他四个人的工作都能用假数据先跑，只有你这里，声音不通他们就只能看代码。所以**第 1 周前半的 S1+S2 必须硬保**，哪怕 VAD 先粗糙、ASR 先假着。

## 11. 待决问题（需要你或答疑群确认）

1. **外呼通道**：官方要网页端，还是要接 PSTN/SIP？——决定要不要引入媒体网关，量级差 3 倍。
2. **首字口径**：T0 是从"用户说完"算，还是从"用户开口"算？含不含网络 RTT？——`docs/04` 已按"说完"定义，拿到官方口径后只改计算层。
3. **云 API 费用谁出**：ASR/TTS 按并发计费，压测会烧钱。是否补贴、有无额度。
4. **现场网络**：答辩现场是否允许自带热点？带宽和并发限制是多少。
5. **浏览器要求**：必须 Chrome/Edge 吗？Safari 的音频自动播放策略会多一道用户手势限制。
