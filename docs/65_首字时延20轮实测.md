# 首字时延 20 轮实测（2026-11-20）
## 结论
- 复现命令：`python scripts/e2e_first_audio.py --rounds 20`
- 口径 B（对齐赛题 T4−T0 的可自动化下界）= 请求到达 → 首个 TTS 音频就绪，**P50 = 1469ms，P95 = 2794ms**（门槛 2000ms）
- 口径 A（物理：推完最后一帧 → 首段就绪，含 VAD 端点等待）= P50 2987ms / P95 4311ms
- 两个口径都**不含**浏览器下载音频 + 起播（真实 T4 还要再加约 100–300ms）
- 判定：P50 达标（留 ~500ms 余量给下载+起播）；但 P95 超标——那轮 2794ms 是云端 TTS 长尾，不是画像导致。

## 口径为什么有两个
赛题 T0 = 客户说完那一刻（前端在 VAD 静音端点检测后取），T4 = 浏览器真的开始播声音。无头环境抓不到 onplaying，所以本脚本只能测"服务端首段就绪"这个下界。口径 A 从推完音频帧算起，多含约 1.5s 的 VAD 端点等待；口径 B 从请求到达算起，与答辩 `server_first_audio_ms` 一致，才是可比的。

## 诚实的限制
1. 20 轮标注了 20 种客户画像 label，但音频统一是 s07.wav（"你好，我是张伟"）——语料库里只有这一句是真人客户话，其余多为客服话术；且本机无 MP3 解码/浏览器自动化，无法按客户卡合成不同客户语音。所以画像**没有真正改变对话分支**，20 轮回复都是同一句。画像标签仅作可追溯标记，不可当因果。
2. latency_report（浏览器真实 T4−T0）至今 0 条样本——1.1–1.4s 是文档预算估算 + 服务端 P50 推导，不是用户感知实测。本数据把"服务端下界"变成实测，但真实 T4 仍需带音频播发的浏览器补测。
