# 团队使用规范（两条硬规矩）

> 这两条不是建议，是每次开工都要走的流程。
> 团队协作的提交/PR 细则在 `CONTRIBUTING.md`；本文只管"开写之前"和"收工之前"。

---

## 规矩一：写代码前，先确认"提示内容"有没有更新

这里的"提示内容"指**契约与约定**，不是聊天记录：
`docs/02_状态机定义.md`、`docs/03_事件契约.md`、`docs/04_时延打点规范.md`、
`contracts.py`、`config/scene.json`。

每次让 AI 开始写之前，先花 30 秒确认三件事：

```bash
git pull origin main                                        # ① 有没有人推了新东西
git log --oneline -5 -- docs/ contracts.py app.py            # ② 契约和骨架最近改过没有
```

③ 打开上面三份文档，看开头那行"状态：v1 草案 / 已冻结"，确认它还是你以为的那一版。

**为什么必须有这一条**：契约一改，照着旧版写出来的代码就是白写，而且往往到合并时才发现，
返工成本最高。所以"确认没变化"也是一项工作——叫确认基线一致，不能说"我觉得应该没变"。

**开工前要先报三句话**，确认无误再动手：

1. 这次要改哪些文件；
2. 依据哪几份契约、哪一版；
3. 会不会碰禁改区（`contracts.py`、别人的文件）。

---

## 规矩二：写完就清理，不留"以防万一"的代码

判据只有一句：**"绝对不再需要" = 没人会再读它，也没人会再跑它。**

**必须删**：

- 一次性验证脚本与临时文件（`_t.bat`、`_t.log`、`probe_*.py`、`tmp_*.py`）
- `data/`、`__pycache__/`、`*.pyc`（`.gitignore` 已挡，但确认没被提交）
- 注释掉的大段旧代码，包括写着"先留着"的那些
- 调试用的 `print`、`TODO 临时`、被注释掉的入口
- 已经被替换掉的旧实现（旧函数、旧配置分支）——旧版本在 git 历史里永远找得到，
  仓库里留一份只会让人分不清哪个是现行代码
- 0 字节占位文件、空目录

**不要删**：

- `docs/` 下的设计文档——那是资产，不是垃圾
- 明确还会用到的东西（如 `eval/seed_cases.json`）——没用上 ≠ 不再需要

**清理不是删完就完了，删完必须跑一遍**：

```bash
python app.py                    # 能起来
python scripts/verify.py         # 行为断言全过
python scripts/run_eval.py       # 评测能跑完、分数没掉
```

跑不过说明删错了，`git checkout -- <文件>` 能找回来，不用怕。

**提交前 6 项清理自检**：

- [ ] 临时脚本、日志、探针已删
- [ ] `git status` 里没有 `data/`、`__pycache__`、`*.pyc`、音频、`.env`
- [ ] 没有注释掉的死代码
- [ ] 没有遗留调试 `print`
- [ ] 被替换的旧实现已删干净，不留"旧版备用"
- [ ] 删完之后服务能起来、自检与评测都没掉

## 附：一句话记住这两条

**开工前对齐基线，收工后清干净。** 其余都可以商量，这两条不行——它们分别对应
"白写两周"和"没人敢改"这两种最贵的后果。

## 规矩三：main 分支不许直接推，改动一律走 PR

前两条管的是"代码写成什么样"，这条管的是"代码怎么进仓库"。
`main` 是**随时可以拿去演示**的分支，直推的后果是：
队友的工作区突然变样、没人审过、出问题不知道是谁哪一次提交引入的。

保护分两层，**两层都要有**，因为各自防的不是同一件事：

| 层 | 防什么 | 在哪配 | 能不能绕过 |
|---|---|---|---|
| 本地钩子 | 手滑、图省事 | 仓库里的 `.githooks/pre-push` | 能（`--no-verify`） |
| GitHub 分支保护 | 所有人，包括管理员 | GitHub 网页设置 | **不能**（服务端强制） |

### 3.1 本地钩子（每个 clone 做一次）

```bash
git config core.hooksPath .githooks
```

只做一次，之后一直有效。判断是否装好：

```bash
git config core.hooksPath      # 应该输出 .githooks
```

装好之后直接 `git push origin main` 会被拒绝，并提示正确的做法。
应急放行（仅管理员、用完在群里说一声）：

```bash
ALLOW_MAIN_PUSH=1 git push origin main
```

**为什么要放进仓库里**：`.git/hooks/` 不进版本库，队友 clone 下来没有这份规则。
放 `.githooks/` + `core.hooksPath` 才能让五个人用同一套。

### 3.2 GitHub 分支保护（管理员做一次）

路径：仓库 → **Settings → Branches → Add branch protection rule**

**Branch name pattern** 填 `main`（只填这一个，不要用通配符，避免误保护到 `main-dev` 之类）。

逐项该勾什么、为什么：

| 配置项 | 勾选 | 为什么 |
|---|---|---|
| **Require a pull request before merging** | ✅ | 这是"禁止直推"的核心开关，不勾等于没保护 |
| ↳ Required approvals | **1** | 五个人里找一个看过就行；填 2 会卡住"只有一个人在线"的情况 |
| ↳ Dismiss stale approvals when new commits are pushed | ✅ | 否则审过之后偷偷加一行代码再合并，审核形同虚设 |
| ↳ Require review from Code Owners | 暂不勾 | 需要先有 `CODEOWNERS` 文件并填对 GitHub 用户名，见 3.3 |
| **Require conversation resolution before merging** | ✅ | 审核提的问题必须被回复或解决，不能"看着不顺眼但懒得说"就合了 |
| **Require status checks to pass** | 暂不勾 | 需要先有 CI。现在自检是本地跑 `验证.bat`，等接了 GitHub Actions 再开，否则会因为"找不到检查项"永远合不了 |
| **Do not allow bypassing the above settings** | ✅ | 关键：不勾的话管理员（也就是队长自己）可以绕过全部规则 |
| **Allow force pushes** | ❌ 不勾 | 强推会覆盖别人的提交，历史上直接丢东西 |
| **Allow deletions** | ❌ 不勾 | 防止 main 被误删 |
| **Require linear history** | 可选 ✅ | 禁止 merge commit，历史更清楚；但会强制 rebase，队友不熟 Git 时容易卡住 |

**"Do not allow bypassing" 这一项最容易被忽略，但它是全套规则的地基。**
不勾的话，前面所有勾选对管理员都不生效——包括你自己。

### 3.4 PR 怎么算能合

审核的人只看四件事，别的要求都是次要的：

1. **改动范围说清了吗**：改了哪些文件、影响谁。说不清就别合——不是形式主义，
   是"影响范围"这一栏往往能暴露出作者自己都没意识到的副作用。
2. **原有测试还过不过**：`验证.bat` 必须全绿。**新功能加断言不是必须，但不许让旧断言变红。**
3. **有没有碰禁改区**：`contracts.py`、状态机阶段推进、合规护栏。碰了要单独说明理由。
4. **有没有引入"演示时会炸"的东西**：新增外部依赖、新增必填配置、
   启动顺序依赖、需要联网才能跑。演示现场断网、队友机器没装，都是真实会发生的。

**审核意见只有三种结论，说清楚是哪种**：
- **通过**：可以直接合
- **修改后合并**：列出必须改的项，改完不需要再审一轮（除非改动很大）
- **需要讨论**：设计方向有分歧，先别改代码，先说清方案

不要用"看着还行"这种话合并——出问题时谁都说不清当时审了什么。
