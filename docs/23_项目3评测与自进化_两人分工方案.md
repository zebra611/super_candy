## 一、项目解构

### 1.1 项目 3 是什么

赛题原文（第 3 页）："鼓励探索 RSI 自进化能力，将实时语音交互与持续优化闭环贯通：
系统可自动生成测试用例和包含对抗性场景的模拟用户，结合规则评分与 LLM-as-Judge
构建可复现的评测基线，通过失败聚类与归因，自动优化提示词、业务话术、检索知识和
工具调用策略，并借助版本管理、回归验证和安全回滚机制，确保进化后的整体指标优于
原有基线。同时……避免对已知测试集过拟合。"

**权重的分量**（容易低估）：
- 同分裁决第①顺位就是"RSI 进化有效性得分"（第 6 页五（四））——与其他队同分时先比这个；
- 提交材料第 4 项"自测报告"明确要求"RSI 迭代前后的对比数据"（第 4 页）——没有对比数据 = 该项交白卷；
- 评分维度 6 里"评测方法"是现场答辩四问之一。

### 1.2 现状盘点（开工前必须知道的）

| 组件 | 现状 | 位置 |
|---|---|---|
| 种子评测集 | 30 条 7 类（v1），schema 已定 | `eval/seed_cases.json` |
| 跑批脚本 | 进程内直调 `handle_turn`，事件判定，离线隔离（临时库 + atexit 清理） | `scripts/run_eval.py` |
| 质检 | 五项：闭环/辱骂/虚假承诺/诱导/隐私/必说话术，判不了标 `skipped` | `modules/eval.py` |
| 当前基线 | 通过 30/30；闭环按新口径 **应闭环 11/11、误闭环 0**（旧口径"11/30"分母含本就不该闭环的用例，已废弃）——**自出题自考试，不可对外汇报** | docs/06 第 7 节 |
| 模拟用户 | 无（turns 是写死的剧本） | — |
| LLM-as-Judge | 无（judge() 纯规则） | — |
| 失败聚类归因 | 无 | — |
| RSI 优化回路 | 完全没做 | — |
| 版本管理 | `prompt_version`/`agent_version` 字段已预留 | 事件流 |

### 1.3 要建的六个模块（按依赖排序）

```
M1 评测集工厂 ──▶ M2 模拟用户 ──▶ M3 双轨评分 ──▶ M4 失败聚类 ──▶ M5 RSI 优化器 ──▶ M6 版本与回滚
                     │                │
                     └─── 共同基座：run_eval.py（冻结接口）+ 事件流判定原则
```

- **M1 评测集工厂**：30 → 80–120 条，按 docs/06 第 5 节六个方向扩；抽 20% 标
  `holdout:true` 只做终验。对抗性用例单列一类（`adversarial`），赛题点名的
  "对抗性场景"必须有实体承载。
- **M2 模拟用户**：把写死的 `turns` 升级为 LLM 驱动的角色扮演——给目标、人设、
  底线（同意/拒绝/含糊条件），逐轮生成回复；temperature 固定保证可复现；产出
  仍是 `seed_cases.json` 兼容的 turns 序列（可落盘重放）。
- **M3 双轨评分**：规则轨（现有 judge()，判事件不判文本）保留为快基线；LLM 轨
  （Judge）判语义项：意图识别对不对、安抚是否有效、幻觉、诱导是否成立。
  两轨结论不一致的用例进人工复核清单——这本身就是质检报告素材。
- **M4 失败聚类归因**：失败样本按"环节 × 错误类型"二维聚类（识别错/理解错/
  话术错/工具错/合规险），每簇给出可执行归因（例：NEED 环节对"再说吧"类含糊
  语误判为拒绝）。产出结构化 JSON，是 M5 的输入。
- **M5 RSI 优化器**：读聚类报告 → 生成候选优化（提示词 diff / 话术改写 /
  追问策略参数）→ 跑回归（train 集 + holdout）→ 指标不降且合规 1.0 才允许合入。
- **M6 版本与回滚**：每次进化打 `agent_version`，事件流全程带版本号；回滚 =
  git revert 配置版本指针，不删历史。优化器永不直接改 `contracts.py`（禁改区）。

### 1.4 验收信号（对齐赛题措辞）

1. 自测报告里有"迭代前后对比表"：至少 3 个版本，每版给出 train/holdout 双分数；
2. holdout 分数不因调优上涨过快（抗过拟合证据，赛题原文要求）；
3. 全程可复现：固定种子、temperature=0（Judge 除外，需记录）、版本号入库；
4. 演示可讲：答辩能拿出"哪次失败聚类 → 改了什么 → 哪个指标涨了"的完整链路。

## 二、两人分工方案

**原则：两人互不阻塞。共享的只有三样——JSON schema、run_eval.py 接口、git 约定。**

### 2.1 分工总表

| 模块 | 负责人 | 为什么这样分 |
|---|---|---|
| M1 评测集工厂 | **刘源** | 他已是 seed_cases.json 的 owner（docs/14），类目直觉最重要 |
| M2 模拟用户 | **班长** | 纯新建 LLM 应用，不碰旧代码，独立度最高 |
| M3 双轨评分：规则轨维护 | **刘源** | eval.py 本来就是他的 |
| M3 双轨评分：LLM-Judge | **班长** | 与 M2 同为新建 LLM 应用，技术栈相同 |
| M4 失败聚类 | **刘源** | 消费自己扩的评测集结果，上下文最全 |
| M5 RSI 优化器 | **班长** | 消费 M2 的模拟能力做批量回归，与 Judge 共用 prompt 管理 |
| M6 版本与回滚 | **共同**（班长定机制，刘源定指标门槛） | 回归闸门的标准必须两人共识 |

### 2.2 模块边界与接口约定（冻结后走 PR 才能改）

**接口 1：用例 schema（冻结）** —— `eval/seed_cases.json` 现有字段一个不改；
只允许追加可选字段：`"holdout": true`、`"adversarial": "..."`、`"persona": "..."`。
刘源扩集、班长模拟用户落盘，都写这个格式。

**接口 2：模拟用户输出（班长 → 刘源）**
```json
{"case_id": "A001", "turns": ["..."], "meta": {"model": "...", "seed": 42,
 "persona": "疑虑型中年客户", "exit_condition": "同意/拒绝/超8轮"}}
```
落盘到 `eval/generated/`，格式与种子集完全兼容 → run_eval.py 无需感知来源。

**接口 3：Judge 输出（班长 → 刘源）**
```json
{"case_id": "I02", "rule_verdict": "pass", "judge_verdict": "fail",
 "reason": "第3轮把'考虑一下'判为同意", "disagree": true}
```
逐用例一行 JSONL，`disagree=true` 的进人工复核清单（质检报告直接引用）。

**接口 4：聚类报告（刘源 → 班长）**
```json
{"cluster_id": "K03", "stage": "NEED", "error_type": "含糊语误判为拒绝",
 "cases": ["E02","E05"], "count": 7, "suggested_action": "ambiguous三分法阈值"}
```

**接口 5：优化候选（班长 → 全员/回归闸门）**
```json
{"candidate_id": "P012", "target": "dialogue_prompt", "diff": "...",
 "base_version": "agent_v3", "train_delta": {"closed": "+2/30"},
 "holdout_delta": {"closed": "0"}, "compliant": true}
```

**接口 6：共享基座 run_eval.py** —— 只许加命令行参数（`--judge`、`--holdout`、
`--report`），`judge()` 判定语义谁都不动；要动走 PR 全员同步。

### 2.3 依赖关系的处理

1. **开工顺序**：第 1 周两人一起把接口 1–5 的 JSON schema 定稿（半天会 + 本文档 PR），
   然后 刘源 动 M1（不依赖别人），班长 动 M2（只依赖 schema）。
2. **互不等的技巧**：M5 依赖 M4 的报告，但班长先用**手工写的假聚类报告**开发
   优化器骨架（schema 一致即可），刘源的 M4 就位后无缝切换真数据。反之刘源的
   M4 也先用 30 条种子的现有失败样本开发，不等 M2。
3. **git 约定**：`feat/eval-*`（刘源）/ `feat/rsi-*`（班长）分支，改动过 CODEOWNERS
   审；`contracts.py`、`eval/seed_cases.json` 已有字段为禁改区。
4. **每周对齐一次**：只对三件事——schema 有没有要改、双方接口的样例文件互验、
   当前基线分数刷新。

## 三、自进化模型技术选型

| 方案 | 思路 | 优点 | 缺点 | 判断 |
|---|---|---|---|---|
| A. 纯规则统计优化 | 失败计数超阈值就人工换模板 | 零成本、可控 | "自动"成分约等于零，答辩讲不出创新 | 淘汰（但保留为兜底） |
| B. DSPy（MIPROv2/Bootstrap） | 框架化 prompt 程序优化，以指标驱动自动搜 prompt | 学术背书强、有版本产物、答辩好听 | 学习成本高；要求把 pipeline 改写成 DSPy Module，与我们事件流判定架构冲突；优化过程黑盒、复现性一般 | 作对照实验，不做主线 |
| C. 失败归因驱动的 LLM 优化器（Reflexion 式反思循环） | M4 聚类 → LLM 读失败样本+现 prompt → 产出修改建议 → 自动回归 → 达标合入 | 与现有架构零冲突（读 JSON 出 JSON）；每一步可解释可审计；天然产出"前后对比数据"；成本≈几百次 LLM 调用；正是赛题原文描述的形态 | 容易过拟合 train 集（靠 holdout 纪律约束）；优化质量上限取决于 Judge 质量 | **推荐主线** |
| D. SFT/LoRA 微调 | 拿成功对话微调开源模型 | "真"进化 | 数百通电话的数据量远不够；需 GPU；不可复现风险高；违反"费用自理"的预算现实 | 淘汰 |
| E. 进化搜索（EvoPrompt 类遗传算法） | prompt 变体种群锦标赛 | 新颖 | API 费用爆炸（每代×每体全量评测）；收敛慢 | 只在富余时做演示性小实验 |

**推荐：C 为主线，B 为对照实验（可选加分项）。**

理由：
1. **贴合赛题原文**：赛题要的是"自动优化提示词、业务话术……借助版本管理、回归
   验证和安全回滚"——方案 C 的每一步都能映射到这句话，答辩可以逐词对上；
2. **证据链最好写**：每次优化自动留下 `聚类报告 → diff → 前后分数` 三件套，
   自测报告第 4 项直接生成；
3. **工程量可控**：M4 报告（刘源）+ 一个 meta-prompt（班长）+ 回归闸门（共同），
   两周内可出第一版；DSPy 主线化则要重写 pipeline，风险买不起；
4. **防过拟合是硬约束**：赛题点名"未公开测试集仍稳定"——方案 C 天然要求
   train/holdout 双报告，纪律与得分点一致。

**安全回滚的具体做法**：优化候选永不直接覆盖生产 prompt——合入 = 把
`config/` 里 prompt 版本指针指向新文件，旧文件保留；holdout 分数回退或合规率
< 1.0 时指针指回，一条 git revert 的事。

## 五、零语料冷启动（先搭框架，语料是框架的产物）

**先纠正一个概念**：方案 C（失败归因驱动的 LLM 优化器）**不训练模型**，优化对象是
提示词和话术——所以不存在"先攒训练语料再开工"这个前提。"语料"在框架里的角色是：

```
跑批产生对话 → 事件流留痕 → 失败样本自动沉淀 → 聚类/优化消费
```

语料不是输入，是**中间产物**。框架搭好一轮，语料就自动长一轮。

### 现在手里就有的冷启动材料（不用等任何人）

| 材料 | 数量 | 能干什么 |
|---|---|---|
| 种子用例跑批产物 | 30 条 × 全量事件流 | 聚类器第一版的真实输入（11 个非闭环 = 现成失败样本） |
| 真人通话记录 | 事件库里 5 通（305 清理后） | Judge 开发用的真实对话语气参照 |
| docs/06 第 7 节探针记录 | 6 个探针抓出 4 个 bug | **手工聚类报告的黄金标注**——每条都是"现象→根因→修复"三元组，M4 的输出格式照着它设计 |
| 种子集 expect 字段 | 30 条判定标准 | Judge few-shot 示例现成 |

### 三步开工顺序（零语料依赖，本周就能动）

1. **先让跑批日夜产数据**：run_eval.py 已能离线跑，加一个"每日全量跑批 + 事件流
   落盘"的定时任务——框架还没好，语料先在积累。模拟用户（M2）上线后产量放大。
2. **M2 是语料生产机，优先级因此最高**：给 persona + 底线条件，LLM 逐轮生成对话，
   落盘成 turns 可重放——一条 persona 一晚上能产几百通"合成语料"，且天然带
   标注（persona 即预期行为）。
3. **M4/M5 用手工标注开发**：拿探针记录的 4 个 bug + 种子集 11 个非闭环手写
   10–20 条聚类报告（照接口 4 格式），优化器骨架对着它开发——schema 一致即可，
   真数据后来自动替换。

**避免的坑**：不要为了"攒语料"去爬真实客服录音——赛题红线（P6：不得爬数据）；
也不要等官方资料包——脱敏资料包发了也只是换话术，框架与语料无关。
