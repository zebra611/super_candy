## 一、先定三条全局设计原则

这三条决定了后面所有模块的边界，改起来代价最大，所以先说。

### 1. 双环路架构：在线环路求"快"，离线环路求"变强"

- **在线环路**（一次通话内）：麦克风 → 语音识别 → 对话决策 → 合成播报 → 业务回写。唯一目标是**低延迟、不卡、不崩**，任何重活都不许进这条路。
- **离线环路**（通话之后）：事件日志 → 质检 → 评测 → 归因 → 优化 → 回归 → 上线。这条环路慢一点没关系，但它是赛题里"RSI 自进化"的唯一落点，也是同分裁决的第一顺位。

两条环路之间**只通过数据交换**，不互相直接调用——这样在线环路不会因为评测跑批而卡住。

### 2. 事件溯源：所有会话落成结构化事件流，而不是纯文本日志

每一次"用户开口""识别出结果""决定调用工具""播报开始""第 3 秒被打断"都是一个带时间戳的结构化事件。

**为什么这一条最重要**：全量转写、合规质检、时延统计、失败归因、评测复现、进化对比——七件事全都从同一份事件流派生。如果一开始只写 `print` 日志，后面每一项都要重做一遍。

### 3. 场景配置化：业务规则全部外置，代码里不写死任何一句业务话术

赛题明确"报名完成后公布详细背景资料及业务场景细节"。场景是未知变量，所以话术、槽位、工具清单、合规规则**全部放在配置文件里**，换场景 = 换配置，不改代码。

## 二、角色分工清单

模块编号见第三节，一人负责两个模块，互不交叉。

---

### 角色 1：实时语音与终端（Voice & Realtime）

**一句话**：负责"声音进得来、出得去、能被随时打断"。

**负责模块**：M1 浏览器终端、M2 实时语音网关

**职责范围**

1. 浏览器端音频采集（16kHz 单声道）、帧化上传、下行音频播放队列与抖动缓冲；
2. 通话界面：通话状态、实时字幕、静音/挂断、演示用的"模拟被叫"页面；
3. 语音活动检测（VAD）与端点判定：什么时候算"说完了"、什么时候算"抢话"；
4. 流式语音识别接入与领域词表（人名、产品名、工单号等热词）；
5. 流式语音合成接入：首包延迟、音色、语速；
6. **打断（barge-in）链路**：检测到用户开口 → 立即停播 + 取消当前生成 → 切回聆听态；
7. 回声消除、降噪、双讲场景下的处理策略；
8. 时延埋点：在每个环节打时间戳，产出端到端时延报表。

**交付物**

- 可用的浏览器通话页面（能被评委现场打断且不出错）
- VAD/ASR/TTS 的适配层（换供应商只改适配层）
- 端到端时延报表（P50/P95，分段拆解）
- 抗噪与双讲自测记录（用三类标准噪声源：街道、车载、多人背景）

**对外接口（别人依赖你的东西）**

- 向上游只暴露两类事件：`user_speech_started` / `user_utterance_final`（含文本、置信度、时间戳）
- 接收下游一条指令：`speak(text_stream)`，支持随时 `cancel()`

**不管什么**：不判断"这句话什么意思"，不决定"下一句说什么"——那是角色 2。

**吃的分**：评分维度 1（实时语音交互质量）的主要部分 + 硬门槛 P50≤2s。

---

### 角色 2：对话大脑与工具调用（Agent Core）

**一句话**：负责"听懂了要干什么，并且真的把它办成"。

**负责模块**：M3 对话编排引擎、M4 工具与业务适配（接口契约由其定义，适配层实现与角色 4 共担）

> **本次 5 人安排下的拆分**：2A 负责 M3（`modules/dialogue.py`），2B 负责 M4 的适配层实现（`modules/tools.py`）；角色 4 只提供配置项与部署环境，不写工具逻辑。

**职责范围**

1. 外呼任务的状态机：开场自报身份 → 身份确认 → 需求确认 → 方案/权益沟通 → 结果确认 → 结构化回写，**六个环节一个都不能漏，且要可审计**；
2. 意图识别与槽位填充（槽位定义来自配置），槽位缺失时主动追问；
3. 多轮纠错：用户改口、否认、反问时的状态回退与重问；
4. 长会话记忆：跨轮次记住已确认的信息，不重复问；
5. 话术生成：在状态机约束下生成自然口语（不是念模板），并按合规规则约束措辞；
6. 幻觉抑制：业务事实必须来自资料包/知识检索，答不出来就说不知道并转下一步；
7. 工具调用：以 Function Calling / MCP 形式调用名单查询、订单查询、工单登记；
8. **结构化回写**：字段完整、格式合规，且**幂等**（同一会话重复提交不产生重复工单）；
9. 异常兜底：情绪激动时安抚、连续两轮没听懂时转人工、违规请求时拒答。

**交付物**

- 状态机定义文档（状态、迁移条件、每状态的必说话术与禁止话术）
- 槽位表与工具清单（含参数 schema、返回结构、幂等键设计）
- 提示词与话术库（版本化）
- 端到端闭环演示：一次电话从开场走到回写成功

**对外接口**

- 接收：`user_utterance_final`（来自角色 1）、工具返回结果（来自 M4）
- 输出：`speak(text_stream)`（给角色 1）、`tool_call(name, args)`（给 M4）、`turn_record`（给事件流）

**不管什么**：不碰音频，不写质检报告，不跑评测。

**吃的分**：评分维度 2（任务完成能力）+ 维度 3（业务知识与工具调用）。

### 角色 3：质检、评测与自进化（Eval & RSI）

**一句话**：负责"证明它确实在变好"，这是本赛题最值钱的一块。

**负责模块**：M6 质检与合规、M7 评测与自进化

**职责范围**

1. **全量质检**（不是抽样）：每次通话自动转写 + 合规检测，产出质检报告；
2. 合规规则引擎：必说话术命中率、禁语拦截率（辱骂歧视、虚假承诺、诱导、泄露隐私）；
3. 自建评测集：正常、缺槽、拒接、情绪激动、诱导违规、多轮改口等场景，覆盖 6 个环节；
4. 模拟用户：能自动扮演"不耐烦的客户""答非所问的客户"，且带对抗性；
5. 评分基线：规则评分 + LLM-as-Judge，两者都要能复现（同一输入同一分数）；
6. **失败聚类与归因**：把失败样本归到"没听清 / 没听懂 / 没查对 / 说错了 / 漏环节"；
7. **进化闭环**：根据归因自动产出优化项（改提示词 / 改话术 / 补检索知识 / 调工具调用策略）；
8. 版本管理与回归：每个优化项必须有"优化前 vs 优化后"的跑分对比，不达标就回滚；
9. 防过拟合：留一部分用例不进优化迭代，只用于验收。

**交付物**

- 质检报告生成器 + 一份真实报告样例
- 自建评测集（含说明：怎么构造、覆盖什么、多少条）
- 评测运行器（一条命令跑完，输出分数表）
- **迭代前后对比数据表**（这是提交材料第 4 项，也是同分裁决第一顺位）
- 版本记录与回滚脚本

**对外接口**

- 只读消费事件流（M5），**不阻塞在线链路**
- 产出：`optimization_proposal`（给角色 2 的提示词/话术/知识变更）、`score_report`

**不管什么**：不改在线代码逻辑，只在配置与提示词层面提改动，由角色 2 落地并回归验证。

**吃的分**：评分维度 4（合规与全量质检）+ 同分裁决第①顺位（RSI 进化有效性）+ 维度 5 的创新性。

## 三、总体实现框架

### 3.1 分层视图

```
┌──────────────────────────────────────────────────────────────┐
│  M1 浏览器终端（WebRTC）                                       │
│  采集 · 播放队列 · 字幕 · 通话控制 · 模拟被叫页                  │
└───────────────────────────┬──────────────────────────────────┘
                            │ 音频帧 / 事件（WebSocket 或 DataChannel）
┌───────────────────────────▼──────────────────────────────────┐
│  M2 实时语音网关                                               │
│  VAD 端点 · 流式 ASR · 流式 TTS · 打断控制 · 时延埋点            │
└───────────────────────────┬──────────────────────────────────┘
                            │ user_utterance_final / speak() / cancel()
┌───────────────────────────▼──────────────────────────────────┐
│  M3 对话编排引擎                                                │
│  任务状态机 · 意图槽位 · 话术生成 · 合规约束 · 兜底转人工         │
└───────────────────────────┬──────────────────────────────────┘
                            │ tool_call / tool_result
┌───────────────────────────▼──────────────────────────────────┐
│  M4 工具与业务适配                                              │
│  Function Calling / MCP · Mock 名单·订单·工单 · 幂等回写        │
└──────────────────────────────────────────────────────────────┘
                            │ 全链路事件
┌──────────────────────────────────────────────────────────────┐
│  M5 事件与观测      转写日志 → 合规质检(M6) → 评测归因(M7) → 进化 │
│  M8 场景配置与部署    config/ 话术槽位工具规则 · Docker 一键启动   │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 八个模块的输入输出

| 模块 | 输入 | 输出 | 归属 |
|---|---|---|---|
| M1 浏览器终端 | 麦克风音频、下行音频 | 上行音频帧、播放状态、打断信号 | 角色 1 |
| M2 实时语音网关 | 音频帧、控制指令 | 转写事件、合成音频流、时延埋点 | 角色 1 |
| M3 对话编排引擎 | 转写事件、工具结果、场景配置 | 播报文本流、工具调用请求、轮次记录 | 角色 2A |
| M4 工具与业务适配 | 工具调用请求 | 业务数据、回写结果（含幂等键） | 角色 2B |
| M5 事件与观测 | 全链路事件 | 事件库、指标看板、查询接口 | 角色 4 |
| M6 质检与合规 | 事件库 | 质检报告、合规告警 | 角色 3 |
| M7 评测与自进化 | 事件库、评测集 | 分数报告、优化建议、版本记录 | 角色 3 |
| M8 场景配置与部署 | 配置文件、镜像 | 运行环境、一键启动 | 角色 4 |

### 3.3 在线数据流（一次通话，附时延预算）

```
用户说话
  → M2 VAD 判定"开始/结束"          ← 预算 150ms
  → M2 流式 ASR 出 final 文本        ← 预算 250ms
  → M3 状态机判断当前环节 + 更新槽位
  → （需要业务数据时）M4 调 Mock 接口  ← 预算 200ms，可异步预热
  → M3 生成回复文本（受合规规则约束）
  → M2 流式 TTS 首包                 ← 预算 250ms
  → M1 播放                          ← 预算 100ms
  → 网络与抖动余量                    ← 预留 250ms
                                    合计 ≈ 1.2–1.4s（门槛 2s，留 600ms 余量）
```

每一步同时写一条事件进 M5。

**打断分支**：M2 检测到用户开口 → 立刻 `cancel()` 停播 → M3 回退到当前状态的"重新聆听" → 记一条 `barge_in` 事件（用于打断响应指标）。

### 3.4 离线数据流（一次进化，赛题的核心加分环）

```
M5 事件库
  → M6 全量转写 + 合规检测 → 质检报告
  → M7 用评测集跑分，得基线分
  → M7 失败聚类：没听清 / 没听懂 / 没查对 / 说错了 / 漏环节
  → M7 产出优化项：改提示词 / 改话术 / 补知识 / 调工具策略
  → 版本化（v1 → v2），回归重跑
  → 分数不低于基线且未公开用例稳定 → 上线；否则回滚到 v1
  → 新版本产生新数据 → 回到 M5
```

这条环路每转一圈，必须留下"前后对比"的硬证据——这是提交材料里唯一不能事后编的东西。

### 3.5 三条必须提前冻结的契约

四个人并行开发，最容易死在"接口对不上"。这三件事必须在写代码前定死：

1. **事件 schema**：`session_id / turn_id / ts / type / payload / latency_ms / version`。谁写事件都要符合它，字段只增不改语义。
2. **工具契约**：每个工具的入参 schema、返回结构、错误码、**幂等键**（建议 `session_id + 环节 + 业务主键`）。
3. **状态机定义**：六个环节的状态名、迁移条件、每状态必说话术与禁止话术。角色 2 出，角色 3 据此写合规校验，两人必须用同一份定义。

### 3.6 目录结构建议

### 3.7 技术选型建议（可替换，但四人要统一）

## 六、这份设计最容易被推翻的地方

诚实标注三个弱点，方便后面调整：

1. **M2 与 M3 的边界可能被时延压垮**。如果端到端压不进 2s，最可能的妥协点是把"意图识别"下沉到 ASR 之后立刻做（学 ASR 的中间结果），这会让角色 1 和角色 2 的接口变复杂——届时需要提前约定"中间结果事件"。
2. **M7 的"自动优化"可能是伪自动**。真正全自动改提示词风险很高（改坏了没人发现），建议做成"自动提议 + 人工确认上线"，这在答辩时反而更可信。
3. **角色分工的负载不均**。角色 3 的任务量在后半程陡增（K4–K5 集中爆发），角色 1 在前半程最重。需要允许中期换防：角色 1 在 K2 之后转去支援角色 3 做评测集与归因。
