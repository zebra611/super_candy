# 状态机定义（K0 契约之一）

> 适用范围：`modules/dialogue.py`（角色 2 实现）、`modules/eval.py`（角色 3 据此写合规与评分）、`config/scene.json`（角色 4 填话术）
> 状态名的唯一来源是 `contracts.STAGES`，本文档只解释语义，不新增状态。
> 状态：v1 草案，**待四人评审后冻结**。冻结后只许追加，不许改名。

---

## 1. 为什么要状态机，而不是让大模型自由发挥

外呼任务是有"必须走完的流程"的：没确认身份就给权益、没确认结果就挂机，都是直接扣分的硬伤。让模型自己决定下一步，迟早会漏环节，而且漏了无法审计。

所以分工是：

- **状态机管流程**——现在该问什么、问完去哪、什么情况必须转人工，由它决定，可审计、可测试；
- **大模型管说话**——同一个状态怎么说得自然、怎么应对跑题，交给模型。

**判断标准**：如果一段逻辑错了会导致"漏环节"，它属于状态机；如果只是"话说得不好听"，属于话术层。

## 2. 状态总览

```
GREETING → IDENTITY → NEED → OFFER → CONFIRM → WRITEBACK → DONE
   │          │         │       │        │          │
   └──────────┴─────────┴───────┴────────┴──────────┴──→ HANDOFF（转人工，未实现）
                                              │
                                              └──→ ABORT（用户明确拒绝/要求挂断，未实现）
```

| 状态 | 一句话目标 | 走到这里说明什么 |
|---|---|---|
| `GREETING` | 自报身份，确认对方是不是本人 | 刚接通 |
| `IDENTITY` | 核对身份，拿到确认 | 对方应答了 |
| `NEED` | 问清对方的诉求或情况 | 身份已确认 |
| `OFFER` | 给出方案或权益，讲清是什么 | 知道对方要什么 |
| `CONFIRM` | 拿到明确的同意或拒绝 | 方案已讲完 |
| `WRITEBACK` | 把结果结构化写回业务系统 | 对方给了明确答复 |
| `DONE` | 礼貌收尾并结束 | 回写完成 |

> `HANDOFF`（转人工）和 `ABORT`（中止）**当前不在 `contracts.STAGES` 里**，是 v2 待补的两个终止态。角色 2 开工时要先把它们加进契约并同步全员。

---

## 3. 每个状态的完整定义

每个状态必须定义四样东西：**进入条件、必说话术、槽位要求、退出条件**。缺任何一样，实现时就会靠猜。

### 3.1 GREETING（开场自报身份）

| 项 | 内容 |
|---|---|
| **进入条件** | 通话建立 |
| **必说话术** | 必须包含：① 公司/机构名 ② 自己的身份（数字员工/客服）③ "是否本人"的问句 |
| **禁止** | 一上来就推销、一上来就要订单号、语速过快（>200 字/分钟） |
| **槽位要求** | 无（不读任何槽位） |
| **退出条件** | 用户有任何正面应答（"是""对""你说"）→ `IDENTITY`；用户明确否认本人 → `HANDOFF`（v2）；连续 2 次无有效语音 → `HANDOFF`（v2） |
| **超时** | 15 秒无语音 → 重播一次开场；再 15 秒无语音 → 挂断并记 `no_answer` |

### 3.2 IDENTITY（身份确认）

| 项 | 内容 |
|---|---|
| **进入条件** | 用户对开场有应答 |
| **必说话术** | 必须说明"为了核对身份"并给出核对方式（手机尾号 / 姓名 / 订单号任选其一） |
| **禁止** | 索要完整身份证号、银行卡号、短信验证码（合规红线） |
| **槽位要求** | 需要 `identity_confirmed: bool` |
| **退出条件** | 核对成功 → `NEED`；核对失败 → 允许重试 1 次，仍失败 → `HANDOFF`（v2）；用户拒绝核验 → `HANDOFF`（v2） |
| **注意** | **不得在身份未确认时说出任何订单、金额、地址等个人信息**，这是质检的硬性检查项 |

### 3.3 NEED（需求确认）

| 项 | 内容 |
|---|---|
| **进入条件** | `identity_confirmed = true` |
| **必说话术** | 必须说明本次来电目的（回访 / 通知 / 权益告知），并给出发问句 |
| **禁止** | 在没查业务数据的情况下编造订单信息（这是最容易出现的幻觉） |
| **槽位要求** | 需要 `need: str`（用户诉求，允许是"无诉求/就是确认一下"） |
| **前置动作** | **进入本状态前应先调 `query_order` 或 `query_customer` 拿到真实数据**，再发问。当前骨架代码没有做这一步，属于已知缺陷 |
| **退出条件** | 拿到 `need` → `OFFER`；用户表示"没兴趣/不需要" → `CONFIRM`（直接确认结束）；用户跑题但可拉回 → 停留本状态一次追问 |

### 3.4 OFFER（方案或权益沟通）

| 项 | 内容 |
|---|---|
| **进入条件** | `need` 已填 |
| **必说话术** | 必须说明：① 提供什么 ② 是否需要付费 ③ 有效期或限制条件 |
| **禁止** | "保证""百分百""稳赚""一定会"等承诺性表述；不得给出资料包之外自创的权益 |
| **槽位要求** | 无新增 |
| **退出条件** | 说完方案 → `CONFIRM`；用户提问（"这个要钱吗"）→ 停留本状态作答 |
| **注意** | 权益内容必须来自企业资料包，**不允许模型自由生成**，否则算"虚假承诺" |

### 3.5 CONFIRM（结果确认）

| 项 | 内容 |
|---|---|
| **进入条件** | 方案已讲完 |
| **必说话术** | 必须复述关键结论并问一个**封闭式问题**（"您同意……对吗？"），不能问"您看怎么样"这种开放式问题 |
| **禁止** | 把含糊回答当成同意（"嗯""再说吧""看看吧"都不算） |
| **槽位要求** | 需要 `consent: bool` |
| **退出条件** | 明确肯定 → `WRITEBACK`；明确否定 → `WRITEBACK`（同样要回写"拒绝"结果，不能直接挂断）；含糊 → 停留本状态追问一次，仍含糊 → `WRITEBACK` 记 `consent=unknown` |
| **注意** | **"用户拒绝"也必须走完回写**，否则业务侧不知道这通电话的结果 |

### 3.6 WRITEBACK（结构化结果回写）

| 项 | 内容 |
|---|---|
| **进入条件** | `consent` 有值（true / false / unknown） |
| **必说话术** | 回写**成功之后**才能说"已为您登记"；失败时必须说兜底话术（"稍后会有专员联系您"） |
| **禁止** | 回写还没确认就宣称"已经登记好了"（这是虚假承诺） |
| **动作** | 调 `create_ticket`，幂等键固定为 `<session_id>:WRITEBACK`，同一通电话重复提交只产生一条工单 |
| **槽位要求** | 回写字段必须完整，形状见 `config/scene.json` 的 `writeback_template` |
| **退出条件** | 回写成功 → `DONE`；回写失败重试 1 次仍失败 → `DONE` 但记 `writeback_failed=true`，并触发兜底话术 |

### 3.7 DONE（收尾）

| 项 | 内容 |
|---|---|
| **进入条件** | 回写完成（成功或已兜底） |
| **必说话术** | 感谢接听 + 结束语，不再发起新话题 |
| **禁止** | 在 DONE 之后继续推销（会显著拉低交互质量评分） |
| **退出条件** | 用户挂断，或播报结束后主动挂断 |

## 4. 迁移表（实现时的唯一依据）

| 当前状态 | 触发条件 | 下一状态 | 备注 |
|---|---|---|---|
| `GREETING` | 用户应答 | `IDENTITY` | 默认路径 |
| `GREETING` | 15 秒无语音 | `GREETING` | 重播一次 |
| `GREETING` | 连续 2 次无语音 | 挂断 | 记 `no_answer` |
| `IDENTITY` | 核对成功 | `NEED` | 必须置 `identity_confirmed=true` |
| `IDENTITY` | 核对失败 | `IDENTITY` | 允许重试 1 次 |
| `IDENTITY` | 重试仍失败 | `HANDOFF`（v2） | 当前骨架先落 `DONE` |
| `NEED` | 拿到诉求 | `OFFER` | |
| `NEED` | 明确表示不需要 | `CONFIRM` | 跳过方案讲解 |
| `OFFER` | 讲完方案 | `CONFIRM` | |
| `OFFER` | 用户追问 | `OFFER` | 停留一次 |
| `CONFIRM` | 明确同意 / 拒绝 / 仍含糊 | `WRITEBACK` | 三种都进，`consent` 分别记 true/false/unknown |
| `WRITEBACK` | 回写完成 | `DONE` | |
| `DONE` | 播报结束 | 结束 | 不再迁移 |

**通用跳转**（任意状态可触发，v2 实现）：

| 条件 | 动作 |
|---|---|
| 用户明确要求人工 | → `HANDOFF` |
| 用户辱骂或强烈抗拒 | → `HANDOFF`，且不得回骂 |
| 连续 2 轮听不懂 | → `HANDOFF` |
| 用户要求挂断 | → 记 `aborted` 后结束，**不回写** |

## 5. 当前代码与本文档的差距

诚实列出来，避免有人照着文档误以为已经实现了：

| 文档要求 | 骨架现状 | 谁补 |
|---|---|---|
| 按意图决定迁移 | 每轮无条件推进一格，**完全不看用户说了什么** | 角色 2 |
| 槽位驱动追问 | 话术写死，缺什么不问什么 | 角色 2 |
| `NEED` 前先查业务数据 | 没查就问 | 角色 2 + 4 |
| 身份未确认不得透露信息 | 没有拦截 | 角色 2 |
| `HANDOFF` / `ABORT` 终止态 | 不存在 | 角色 2（需先改契约） |
| 必说话术命中检测 | 只做了禁语字面匹配 | 角色 3 |
| 回写失败走兜底话术 | 没有失败分支 | 角色 2 |

## 6. 冻结前需要四个人确认的三件事

1. **`HANDOFF` / `ABORT` 要不要现在就加进 `contracts.STAGES`？**（加了要同步改对话、质检、配置三处）
2. **"用户拒绝"是否也必须回写？**（本文档的立场：必须。否则业务侧不知道结果）
3. **必说话术由谁定义？**（本文档的立场：角色 2 写、角色 3 校验、角色 4 落配置，三人用同一份 `config/scene.json`）

这三条定了，状态机就可以冻结，角色 2 和角色 3 能同时开工。
