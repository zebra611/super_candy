# 从"轮次式问答"到"电话式通话"：差距、能力范围与实现方案

> 目标：让评委拿起话筒就能像打电话一样用——不用点按钮、说话可以随时插嘴、客服被打断会立刻闭嘴。
> 现状：一问一答。点「按下说话」→ 松手 → 等 → 听 → 再点。

---

## 1. 真实电话交互长什么样

拆开看是六件事，缺一件就不像打电话：

| # | 特征 | 人话解释 |
|---|---|---|
| 1 | **免按键** | 拿起话筒就能说，不需要"按住说话" |
| 2 | **自动断句** | 系统自己判断你说完了，而不是你按按钮告诉它 |
| 3 | **可打断** | 客服还在说，你插一句"等一下"，它必须立刻停 |
| 4 | **连续进行** | 一轮接一轮自动流转，中间没有操作间隙 |
| 5 | **首字够快** | 你说完到听见回应 ≤ 1 秒，超过 1.5 秒就像机器 |
| 6 | **不抢话** | 你说话时它不吭声；它说话时你不被强制静音 |

第 6 条容易被忽略：现在的实现里，播报时麦克风是关的——**用户在物理上没法插话**，
所以"不支持打断"不是没做检测，是根本没有通道。

---

## 2. 当前实现对照

| 特征 | 现状 | 差距 |
|---|---|---|
| 免按键 | 点「按下说话」才开始采集，再点结束 | 每次说话两次点击 |
| 自动断句 | 无。用户点"停止"就是断句 | 没有端点检测 |
| 可打断 | 无。播报期间采集已停，麦克风也关了 | **物理上做不到** |
| 连续进行 | 每轮都要重新点按钮 | 有操作间隙 |
| 首字够快 | 语音轮约 1.0–1.2 秒（ASR 0.4–0.6 + 首段合成 0.4） | 达标，但没余量 |
| 不抢话 | 半双工，天然不抢话——但代价是用户也不能插话 | 靠"关麦克风"实现，不是靠状态管理 |

**一句话**：现在不是"做得不够好"，而是**通道模型不同**——
一轮一次 HTTP 请求，音频整段上传，播报期间链路是单向的。

---

## 3. 能力范围：三块，别混在一起做

很多人把这三件事当一件，结果一起做、一起卡。它们难度差一个量级：

### 3.1 打断（barge-in）——不需要换通道，前端就能做

打断的本质是"**播放时继续听，听到人声就停播**"。麦克风本来就能一直开着，
只是现在被按钮关掉了。所以这一块**不必等 WebSocket**。

要做的是三件事：

1. **采集常开**：通话期间不复用"录一轮就关"的逻辑；
2. **播放时也判定**：播报期间持续算能量，越过阈值就 `pause()`;
3. **打断后收拾干净**：停当前音频、清空待播队列、通知服务端记一条 `barge_in`。

### 3.2 连续双向——需要状态机，不需要换通道

"连续"= 端点检测 + 自动提交 + 状态互斥。仍然是 HTTP 轮次，
只是把"用户点按钮"换成"VAD 判定"，把"点发送"换成"自动提交"。

这一块的关键不是技术，是**状态别打架**：用户说完 → 提交 → 等响应 → 播报 → 再听。
每一步都得有明确状态，否则会出现"客服还在说话，用户又提交了一轮"。

### 3.3 真流式——必须换通道

边说边识别、边合成边播、服务端主动下发，都需要 **WebSocket 双向通道**。
这一块才是"要动架构"的部分，收益是首字从 1.0 秒压到 0.5 秒以内、
以及真正的实时字幕。**优先级最低**，因为 3.1 和 3.2 已经把体验差拉到"能用"了。

## 4. 阶段 1：前端 VAD + 打断 + 自动轮次（不动通道）

### 4.1 状态机

```
        ┌──────────────────────────── 打断 ────────────────────────────┐
        ↓                                                              │
   LISTENING ──(能量超阈值)──> USER_SPEAKING ──(静音 700ms)──> THINKING │
        ↑                                                          │    │
        │                                                    (响应到达)  │
        └────────────(播完)────────── AGENT_SPEAKING <─────────────┘    │
                                          │                             │
                                          └─────(检测到人声)─────────────┘
```

五个状态，前端持有：

| 状态 | 采集 | 播报 | 允许提交 |
|---|---|---|---|
| `LISTENING` | 开 | 静音 | 否（还没检测到说话） |
| `USER_SPEAKING` | 开 | 静音 | 否（等端点） |
| `THINKING` | 开（丢弃） | 静音 | 否（等响应，避免并发 409） |
| `AGENT_SPEAKING` | 开（**用于打断**） | 播放中 | 否 |
| `INTERRUPTED` | 开 | 停止 | 否（回到 LISTENING 的过渡） |

### 4.2 VAD 判定参数（前端，逐帧 20ms）

| 判定 | 条件 | 为什么是这个值 |
|---|---|---|
| 有人说话 | 一帧 RMS ≥ `0.020` | 约 -34dBFS，正常说话在 -30~-20dBFS，留足余量 |
| 说完 | 连续 35 帧（700ms）RMS < `0.010` | 短于 500ms 会把句中停顿当说完；长于 1 秒用户会觉得迟钝 |
| **疑似插话** | 连续 3 帧（60ms）RMS ≥ `0.035` | **故意高于说话阈值**：外放时麦克风会收到自己播的声音，阈值太低会自己打断自己 |
| **确认插话** | 疑似之后持续说话，静音 18 帧（360ms）→ 送去识别 | 光有能量不算数，要等这句说完、认出字来才停播 |
| 疑似最长 | 160 帧（3.2 秒） | 用户一直说不停的话，到点也要判，不能永远等不到端点 |

`getUserMedia` 已经开了 `echoCancellation: true`，但仍要留这道余量——
AEC 对外放的回声只能压 20–30dB，不保证干净。

### 4.3 打断的三段式：疑似 → 识别 → 确认/否决

**为什么不能一有能量就停**（第一版就是这么写的，被指出来才改）：
60ms 的咳嗽、碰麦、椅子响、隔壁说话都能把客服打断，而打断是**不可逆**的——
那半句话用户再也听不到，得从头重听。宁可偶尔"客服多说了半句"，
也不能让清嗓子把客服打断。

```
播报中，检测到 60ms 超阈值能量
  ↓
【疑似】suspected
  · 立刻把播报音量压到 12%（约 -18dB），**不暂停**
  · 开始把这一小段音频攒进 bargeBuf（不进主缓冲，避免混进客服自己的声音）
  ↓ 这段说完（静音 360ms）或攒满 3.2 秒
【识别】probing
  · POST /api/asr/probe → 只识别，不建轮次、不推进状态机、不写业务事件
  ↓
  ├─ has_content = false → 【否决】抬回音量继续播，日志记"疑似插话已忽略"
  └─ has_content = true  → 【确认】真的停播（见 4.4）
```

**为什么用"压低音量"而不是"直接暂停"**：如果一上来就暂停，误判时
"暂停再恢复"会有一个明显的断音；而音量压下去再抬回来，用户几乎察觉不到。
误判率越高，这个选择的收益越大。

**什么算"有内容"**（`app.py` 的 `_has_interrupt_content`）：

| 识别结果 | 判定 | 理由 |
|---|---|---|
| `""` / `"。"` | 不打 | 纯噪声 |
| `"嗯。"` / `"啊"` / `"嗯嗯啊"` | 不打 | 随口应一声 |
| `"我"` | 不打 | 单字，但不像要抢话 |
| `"停"` / `"别"` / `"不"` | 打 | 单字但意图明确 |
| `"等一下"` / `"不是"` | 打 | 典型插话 |
| **`"Thank you."`** | 不打 | **白噪声实测被识别成这句**，纯英文一律当幻觉 |

最后一行是实测挖出来的：ASR 遇到噪声会吐训练集里的高频短语。
所以规则补了一条——**一个汉字都没有就直接判幻觉**。中文外呼场景里
用户插话必是中文，宁可漏掉一次 "OK"，也不能让噪声把客服打断。

### 4.4 确认之后：停播的顺序

```
1. 立刻 audio.pause()          ← 先停声音，用户最在意的是"它闭嘴了"
2. 清空待播队列（playToken +1，让所有段失效）
3. 把 bargeBuf 接到本轮缓冲最前面 —— 用户是连着往下说的，"等一下"不能丢
4. 通知服务端：POST /api/call/barge_in（带上识别出的文字，记进 heard）
5. 状态切 LISTENING，用户继续说完 → 正常走端点 → 提交新一轮
```

第 4 步放在第 1 步之后：网络请求可以慢，但"闭嘴"不能慢。

第 3 步容易被漏掉：确认打断用的那段音频，正是用户说的头几个字。
扔了的话，用户"等一下，我想问…"里的"等一下"就消失了。代价是这段混着
压到 12% 的客服声音，识别时略有干扰——但比丢掉半句话可接受得多。

### 4.5 服务端要补的

两个接口，其余逻辑沿用：

- `POST /api/asr/probe`（新）：体是原始 PCM（`application/octet-stream`），
  query 带 `session_id` / `token`。只识别，返回 `{text, has_content, asr_ms}`。
  **刻意不写任何事件、不推进状态机**——用户清个嗓子不该在事件链上留痕。
- `POST /api/call/barge_in`：体 `{session_id, token, turn_id, text}`，
  写 `barge_in` 事件（`contracts.EVENT_TYPES` 里早就预留了），
  payload 里带上 `heard`（用户到底说了什么，用于复盘误判率），
  并丢弃该轮未取的 `tts_rest`（避免用户回来后听到上一轮的残句）。

`handle_turn` 的并发保护（`SESSION_BUSY 409`）继续生效——它就是"状态互斥"的服务端兜底。

**实测代价**：probe 一次真实识别 283–420ms。也就是说从"用户说完"到
"客服真的闭嘴"有约 0.4 秒延迟。这段时间客服还在说话（音量已压低）。
在半双工电话里，这听起来像正常的反应延迟，不像 bug。

### 4.6 不改什么

- 不改 `contracts.py`（`barge_in` 事件位已经在）
- 不改 ASR/TTS 调用方式
- 不改 `/api/turn` 的请求/响应形状

## 5. 阶段 2：WebSocket 流式（要动通道，另开一轮）

### 5.1 为什么必须换

HTTP 是"请求-响应"：服务端没办法在用户说话说到一半时主动告诉前端"我听到前半句了"。
要做到边说边识别、边合成边播，通信模型必须从"问答"变成"双向流"。

### 5.2 目标形态

```
浏览器 ──[WS]──> 服务端 ──[WS]──> qwen3-asr-flash(realtime) / paraformer-realtime-v2
   │                                    │
   ├─ 二进制帧：PCM 20ms                 ├─ partial 文本（不回给用户，只做前端字幕）
   └─ JSON：控制指令（start/stop/barge）  └─ final 文本（触发编排）
```

关键变化：

1. **音频不再缓存整段**：采集到的帧直接推给识别，说完即出 final；
2. **服务端主动下发**：TTS 首包一到就推给前端播，不再等整句；
3. **打断变成协议事件**：`{type:"barge_in"}` 同时通知服务端停合成、通知前端停播。

### 5.3 代价

- 服务端要维护长连接与会话映射（现在每个请求无状态）；
- 前端要处理重连、半开连接、断线重放；
- 云端识别换实时接口，单价与调用方式都变（`docs/05` 有价格）。

**建议：阶段 1 上线跑通、评委试用过之后，再决定要不要投入阶段 2。**

## 6. 接入步骤

### 阶段 1（当前这一步）

1. `web/index.html`：采集从"按需开关"改成"通话期间常开"，加帧级 VAD 与五态状态机；
2. `web/index.html`：播放逻辑增加打断判定；打断时按 4.3 的顺序收拾；
3. `app.py`：新增 `POST /api/call/barge_in`，写 `barge_in` 事件、清掉该轮 `tts_rest`；
4. `scripts/verify.py`：补断言——打断后事件链里有 `barge_in`、该轮剩余音频被丢弃、
   打断后仍能正常提交下一轮；
5. 人工验证：外放播报时说一句"等一下"，确认 0.3 秒内停播，且随后能正常对话。

### 阶段 2（另开一轮，不在本次范围）

1. `app.py` 加 `/ws/call`，处理二进制帧与 JSON 控制；
2. `modules/voice.py` 加 `asr_stream()`，接实时识别；
3. `contracts.py` 追加流式相关事件（`asr_partial` 等）；
4. 前端换 `WebSocket`，采集管线不变（帧已经切好了）。

## 7. 怎么验证"真的像打电话"

别只看代码，按下面四条实测，每条都要能过：

| # | 动作 | 期望 |
|---|---|---|
| 1 | 拿起就说，不点任何按钮 | 说完约 0.7 秒后客服开始回应 |
| 2 | 客服说到一半，插一句"等一下" | 0.3 秒内停播，日志出现 `barge_in` |
| 3 | 连续说三四轮，中间不操作 | 每轮都自动接上，不出现 409 或串轮 |
| 4 | 外放音量开大，客服自己说话 | **不能自己打断自己**（这是最容易翻车的一条） |

第 4 条如果过不了，说明打断阈值太低或 AEC 没生效，宁可把阈值调高——
"偶尔打断不了"比"自己跟自己抢话"体面得多。
