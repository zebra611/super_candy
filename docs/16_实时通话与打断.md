# 从"轮次式问答"到"电话式通话"：差距、能力范围与实现方案

> 目标：让评委拿起话筒就能像打电话一样用——不用点按钮、说话可以随时插嘴、客服被打断会立刻闭嘴。
> 现状：一问一答。点「按下说话」→ 松手 → 等 → 听 → 再点。

---

## 1. 真实电话交互长什么样

拆开看是六件事，缺一件就不像打电话：

| # | 特征 | 人话解释 |
|---|---|---|
| 1 | **免按键** | 拿起话筒就能说，不需要"按住说话" |
| 2 | **自动断句** | 系统自己判断你说完了，而不是你按按钮告诉它 |
| 3 | **可打断** | 客服还在说，你插一句"等一下"，它必须立刻停 |
| 4 | **连续进行** | 一轮接一轮自动流转，中间没有操作间隙 |
| 5 | **首字够快** | 你说完到听见回应 ≤ 1 秒，超过 1.5 秒就像机器 |
| 6 | **不抢话** | 你说话时它不吭声；它说话时你不被强制静音 |

第 6 条容易被忽略：现在的实现里，播报时麦克风是关的——**用户在物理上没法插话**，
所以"不支持打断"不是没做检测，是根本没有通道。

---

## 2. 当前实现对照

| 特征 | 现状 | 差距 |
|---|---|---|
| 免按键 | 点「按下说话」才开始采集，再点结束 | 每次说话两次点击 |
| 自动断句 | 无。用户点"停止"就是断句 | 没有端点检测 |
| 可打断 | 无。播报期间采集已停，麦克风也关了 | **物理上做不到** |
| 连续进行 | 每轮都要重新点按钮 | 有操作间隙 |
| 首字够快 | 语音轮约 1.0–1.2 秒（ASR 0.4–0.6 + 首段合成 0.4） | 达标，但没余量 |
| 不抢话 | 半双工，天然不抢话——但代价是用户也不能插话 | 靠"关麦克风"实现，不是靠状态管理 |

**一句话**：现在不是"做得不够好"，而是**通道模型不同**——
一轮一次 HTTP 请求，音频整段上传，播报期间链路是单向的。

---

## 3. 能力范围：三块，别混在一起做

很多人把这三件事当一件，结果一起做、一起卡。它们难度差一个量级：

### 3.1 打断（barge-in）——不需要换通道，前端就能做

打断的本质是"**播放时继续听，听到人声就停播**"。麦克风本来就能一直开着，
只是现在被按钮关掉了。所以这一块**不必等 WebSocket**。

要做的是三件事：

1. **采集常开**：通话期间不复用"录一轮就关"的逻辑；
2. **播放时也判定**：播报期间持续算能量，越过阈值就 `pause()`;
3. **打断后收拾干净**：停当前音频、清空待播队列、通知服务端记一条 `barge_in`。

### 3.2 连续双向——需要状态机，不需要换通道

"连续"= 端点检测 + 自动提交 + 状态互斥。仍然是 HTTP 轮次，
只是把"用户点按钮"换成"VAD 判定"，把"点发送"换成"自动提交"。

这一块的关键不是技术，是**状态别打架**：用户说完 → 提交 → 等响应 → 播报 → 再听。
每一步都得有明确状态，否则会出现"客服还在说话，用户又提交了一轮"。

### 3.3 真流式——必须换通道

边说边识别、边合成边播、服务端主动下发，都需要 **WebSocket 双向通道**。
这一块才是"要动架构"的部分，收益是首字从 1.0 秒压到 0.5 秒以内、
以及真正的实时字幕。**优先级最低**，因为 3.1 和 3.2 已经把体验差拉到"能用"了。

## 4. 阶段 1：前端 VAD + 打断 + 自动轮次（不动通道）

### 4.1 状态机

```
        ┌──────────────────────────── 打断 ────────────────────────────┐
        ↓                                                              │
   LISTENING ──(能量超阈值)──> USER_SPEAKING ──(静音 700ms)──> THINKING │
        ↑                                                          │    │
        │                                                    (响应到达)  │
        └────────────(播完)────────── AGENT_SPEAKING <─────────────┘    │
                                          │                             │
                                          └─────(检测到人声)─────────────┘
```

五个状态，前端持有：

| 状态 | 采集 | 播报 | 允许提交 |
|---|---|---|---|
| `LISTENING` | 开 | 静音 | 否（还没检测到说话） |
| `USER_SPEAKING` | 开 | 静音 | 否（等端点） |
| `THINKING` | 开（丢弃） | 静音 | 否（等响应，避免并发 409） |
| `AGENT_SPEAKING` | 开（**用于打断**） | 播放中 | 否 |
| `INTERRUPTED` | 开 | 停止 | 否（回到 LISTENING 的过渡） |

### 4.2 VAD 判定参数（前端，逐帧 20ms）

| 判定 | 条件 | 为什么是这个值 |
|---|---|---|
| **像人声**（Z6 新增） | RMS ≥ `0.020` **且** 过零率 ≤ `0.45` **且** 400Hz/2000Hz 能量比 ≥ `0.35` | 三条一起判"是不是人在说"，不只是"有多响"。键盘频谱偏高频（实测 tilt≈0.1），白噪/摩擦过零率 >0.4 |
| 开口 | 连续 2 帧（40ms）像人声 | 键盘单次瞬态 5~12ms，一帧就过去的响声不再触发一轮 |
| 说完 | 连续 35 帧（700ms）不像人声 | 短于 500ms 会把句中停顿当说完；长于 1 秒用户会觉得迟钝 |
| **疑似插话** | 连续 3 帧（60ms）RMS ≥ `0.035` | **故意高于说话阈值**：外放时麦克风会收到自己播的声音，阈值太低会自己打断自己 |
| **确认插话** | 疑似之后持续说话，静音 18 帧（360ms）→ 送去识别 | 光有能量不算数，要等这句说完、认出字来才停播 |
| 疑似最长 | 160 帧（3.2 秒） | 用户一直说不停的话，到点也要判，不能永远等不到端点 |

> **打断判定坚持只看能量**（不套谱特征门）：打断要的是快，宁可多探一次再否决；
> 而端点判定套了谱特征门，因为它决定"这一轮提交什么"。两者的取舍方向相反。

**现场标定**：地址栏加 `?vaddebug=1`，麦克风状态行会实时显示 `rms/zcr/tilt`
与当帧判定。演示机是内置麦 + 外放，浏览器还开着噪声抑制与 AGC，
电平分布与离线语料不同——先看一眼再决定要不要调。

参数的可测部分是 `scripts/tune_barge_vad.py`：它**从本文件对应的
`web/index.html` 里解析 `const VAD`**（不另存一份），在同一套 12 个场景上跑
状态机仿真：正常插话、外放回声、弱 AEC、键盘、清嗓、小声说话、句中停顿、
连续长说、纯静音、说话含敲击。改了前端参数没跑这个脚本，等于没标定。

`getUserMedia` 已经开了 `echoCancellation: true`，但仍要留这道余量——
AEC 对外放的回声只能压 20–30dB，不保证干净。

### 4.2b 服务端 VAD（Z6，2026-11-07）

前端那套管"什么时候提交"，服务端这套管"这段到底有没有人说话"。两件事别混：
前端要零延迟，只能用轻量判据；服务端不参与节奏，可以跑模型。

**改造前后**

| | 改造前 | 改造后 |
|---|---|---|
| 判定 | `started = bool(audio_bytes)`——有字节就算说了话 | 逐帧判定 + 起止聚合 |
| 噪声片段 | **9/9 全部触发**（白噪、键盘、椅子都会被当成用户开口） | **0/9 触发** |
| `speech_ms` | 恒等于整段时长（含静音） | 真正是人声的累计时长 |
| 事件字段 | 4 个 | 增加 `engine` / `engine_note` / `speech_ratio` / `frames` |

**两层引擎，一套聚合**

| 引擎 | 何时用 | 逐帧依据 | 实测（12 人声 / 9 噪声 / 3 混合） |
|---|---|---|---|
| `silero` | 装了 onnxruntime + `data/models/silero_vad.onnx` | ONNX 模型概率 ≥0.5（32ms 窗） | 12/12 · 0/9 · 3/3，4~7 秒音频约 60ms |
| `spectral` | 否则（干净机器、CI） | 多频点 + 自相关周期 + 过零率 + 谱倾斜 | 12/12 · 0/9 · 3/3，同一批约 120ms |

留出集（另 6 条台词、噪声幅度 ×1.35、不同随机种子）上两个引擎同样全对；
数字由 `scripts/bench_vad.py` 出，语料由 `scripts/gen_vad_corpus.py` 生成。

**聚合参数（两引擎共用，改了要同步这张表）**

| 判定 | 值 | 为什么 |
|---|---|---|
| 开口 | 连续 **96ms** 语音帧 | 键盘单次瞬态只有 5~12ms，关门/椅子冲击 <120ms；真人元音段 ≥150ms |
| 段内合并 | 间隔 <180ms 不切断 | 「京东」两个音节之间的闭塞本来就有 80~150ms |
| 说完 | 最后一段人声后静音 ≥**300ms** | 这一段音频已被前端切好，服务端只填 `ended`，不参与节奏 |

**为什么不是"能量阈值换皮"**：能量门挡不住风扇（稳态）也挡不住键盘（瞬态够响），
改造前的 `bool(bytes)` 更是连判都没判。谱特征判的是"像不像人说话"：
语音在 300~3000Hz 有 5 个以上明显频点、低频占比高、浊音段自相关 >0.4；
键盘能量集中在高频、摩擦声过零率高、关门是"一上来最响然后一路衰减"。

**已知挡不住的**（不夸大）：远处人声、真人咳嗽——它们与语音同分布，
谱特征层做不到，只能靠 ASR 语义层兜（C6 已做：噪声不烧核身次数、不挂断）。
**说话人分离也没有**：VAD 只回答"有没有人声"，不回答"是不是本人"。

### 4.3 打断的三段式：疑似 → 识别 → 确认/否决

**为什么不能一有能量就停**（第一版就是这么写的，被指出来才改）：
60ms 的咳嗽、碰麦、椅子响、隔壁说话都能把客服打断，而打断是**不可逆**的——
那半句话用户再也听不到，得从头重听。宁可偶尔"客服多说了半句"，
也不能让清嗓子把客服打断。

```
播报中，检测到 60ms 超阈值能量
  ↓
【疑似】suspected
  · 立刻把播报音量压到 12%（约 -18dB），**不暂停**
  · 开始把这一小段音频攒进 bargeBuf（不进主缓冲，避免混进客服自己的声音）
  ↓ 这段说完（静音 360ms）或攒满 3.2 秒
【识别】probing
  · POST /api/asr/probe → 只识别，不建轮次、不推进状态机、不写业务事件
  ↓
  ├─ has_content = false → 【否决】抬回音量继续播，日志记"疑似插话已忽略"
  └─ has_content = true  → 【确认】真的停播（见 4.4）
```

**为什么用"压低音量"而不是"直接暂停"**：如果一上来就暂停，误判时
"暂停再恢复"会有一个明显的断音；而音量压下去再抬回来，用户几乎察觉不到。
误判率越高，这个选择的收益越大。

**什么算"有内容"**（`app.py` 的 `_has_interrupt_content`）：

| 识别结果 | 判定 | 理由 |
|---|---|---|
| `""` / `"。"` | 不打 | 纯噪声 |
| `"嗯。"` / `"啊"` / `"嗯嗯啊"` | 不打 | 随口应一声 |
| `"我"` | 不打 | 单字，但不像要抢话 |
| `"停"` / `"别"` / `"不"` | 打 | 单字但意图明确 |
| `"等一下"` / `"不是"` | 打 | 典型插话 |
| **`"Thank you."`** | 不打 | **白噪声实测被识别成这句**，纯英文一律当幻觉 |

最后一行是实测挖出来的：ASR 遇到噪声会吐训练集里的高频短语。
所以规则补了一条——**一个汉字都没有就直接判幻觉**。中文外呼场景里
用户插话必是中文，宁可漏掉一次 "OK"，也不能让噪声把客服打断。

### 4.4 确认之后：停播的顺序

```
1. 立刻 audio.pause()          ← 先停声音，用户最在意的是"它闭嘴了"
2. 清空待播队列（playToken +1，让所有段失效）
3. 把 bargeBuf 接到本轮缓冲最前面 —— 用户是连着往下说的，"等一下"不能丢
4. 通知服务端：POST /api/call/barge_in（带上识别出的文字，记进 heard）
5. 状态切 LISTENING，用户继续说完 → 正常走端点 → 提交新一轮
```

第 4 步放在第 1 步之后：网络请求可以慢，但"闭嘴"不能慢。

第 3 步容易被漏掉：确认打断用的那段音频，正是用户说的头几个字。
扔了的话，用户"等一下，我想问…"里的"等一下"就消失了。代价是这段混着
压到 12% 的客服声音，识别时略有干扰——但比丢掉半句话可接受得多。

### 4.5 服务端要补的

两个接口，其余逻辑沿用：

- `POST /api/asr/probe`（新）：体是原始 PCM（`application/octet-stream`），
  query 带 `session_id` / `token`。只识别，返回 `{text, has_content, asr_ms}`。
  **刻意不写任何事件、不推进状态机**——用户清个嗓子不该在事件链上留痕。
- `POST /api/call/barge_in`：体 `{session_id, token, turn_id, text}`，
  写 `barge_in` 事件（`contracts.EVENT_TYPES` 里早就预留了），
  payload 里带上 `heard`（用户到底说了什么，用于复盘误判率），
  并丢弃该轮未取的 `tts_rest`（避免用户回来后听到上一轮的残句）。

`handle_turn` 的并发保护（`SESSION_BUSY 409`）继续生效——它就是"状态互斥"的服务端兜底。

**实测代价**：probe 一次真实识别 283–420ms。也就是说从"用户说完"到
"客服真的闭嘴"有约 0.4 秒延迟。这段时间客服还在说话（音量已压低）。
在半双工电话里，这听起来像正常的反应延迟，不像 bug。

### 4.6 不改什么

- 不改 `contracts.py`（`barge_in` 事件位已经在）
- 不改 ASR/TTS 调用方式
- 不改 `/api/turn` 的请求/响应形状

### 4.7 V1 参数标定：扫描结果与安全区间（2026-11-07）

**怎么测的**：`scripts/tune_barge_vad.py` 从 `web/index.html` 解析 `const VAD`
（不另存参数副本），用同一套判据在 15 个仿真场景上跑前端状态机。
场景音频取自 `data/vad_corpus`（12 条 TTS 人声 + 九类**合成**噪声），外放按 AEC 残压合成。

> ⚠️ 本节结论建立在**自造数据**上，先看 §4.8 的真机直录结果再决定要不要信：
> 真机上底噪 rms 峰值到 0.035，本节的"静音不开口"在真机上是不成立的。

| 场景 | 构造 | 期望 |
|---|---|---|
| A 正常插话 | -26dB 回声 + 1.5s 后用户说话 | 打断 |
| B 外放回声 | 只有 -26dB 回声 | **不打断** |
| C 键盘 / D 清嗓 | 回声 + 键盘（清嗓） | **不打断** |
| E 句中停顿 | 两句之间停 400ms | 只切 1 轮 |
| F 连续长说 | 6 秒不停 | 只切 1 轮，端点不无限拖 |
| G 纯静音 | 3 秒无声 | 不提交 |
| H 说话含敲击 | 人声 + 键盘 | 正常切 1 轮 |
| I 弱 AEC 回声 | -18dB 回声 | **不打断** |
| J 小声说话 | 正常音量 35% | 能切 1 轮 |
| K 回声 + 爆响键盘 | -18dB 回声 + 键盘 ×2 | **不打断** |
| L 弱 AEC 插话 | -18dB 回声 + 60% 音量用户 | 打断 |
| M 极小声 | 15% 音量（rms≈0.02） | 能切 1 轮 |
| N 强回声 | -12dB（AEC 几乎失效） | **不打断** |
| O 爆响键盘 | -12dB 回声 + 键盘 ×4 | **不打断** |

当前参数：**15/15**。两类延迟分开看（口径不同，不能混着报）：
- **端点延迟**（用户说完 → 判"可以提交"）：E 句中停顿 4180ms、F 连续长说 7740ms
  —— 这两个数含语音本身的时长，真正属于判定的只有末尾的 700ms 静音；
- **插话确认**（用户开口 → 客服真停播）：A 1820ms、L 1800ms
  —— 含"等这句说完（360ms）+ 识别这段"的两段式代价，设计上就该这么慢（见 §4.3）。

**栅格扫描 384 组**（speechRms × bargeRms × endpointFrames × zcrMax × tiltMin ×
onsetFrames）→ **352 组全过**。各维度的通过率说明只有两个维度真正敏感：

| 维度 | 取值 → 通过率 | 结论 |
|---|---|---|
| `speechRms` | 0.012→96/96 · 0.016→96/96 · **0.020→96/96** · 0.024→64/96 | 调到 0.024 会把小声用户整段漏掉（M 场景失败） |
| `bargeRms` | 0.025→96/128 · **0.035→128/128** · 0.045→128/128 | 调到 0.025 会在强回声下自己打断自己（N 场景失败） |
| `endpointFrames` | 25/30/35/40 均 88/96 | 700ms 附近不敏感，25 帧（500ms）更快但更易被句中停顿切开 |
| `zcrMax`/`tiltMin`/`onsetFrames` | 0/1 两档完全同分 | **合成场景测不出这三条的收益**——键盘已经被"等 60ms + 等这句说完再识别"挡住，轮不到谱特征出手 |

**结论（合成场景内不改参数，但这个结论不能推广到现场）**：

- 现状 `speechRms=0.020` 是安全区的**上边界**，`bargeRms=0.035` 是**下边界**。
  两个都贴着边，但都在里面，没有理由乱动。
- 现场若"用户很小声、经常切不出来"→ 把 `speechRms` 降到 0.016（仍有 96/96）。
- 现场若"外放回声大、客服老是自己停"→ 把 `bargeRms` 抬到 0.045（仍有 128/128），
  代价是用户要说得响一点才打断得了。
- 谱特征三条（zcr/tilt/onset）保留但保持宽松：它们在合成场景里没有区分度，
  真实的收益要等现场 `?vaddebug=1` 看一眼再判断。**不假装它们已经被证明有效。**

**为什么不全信这张表**：所有音频都是合成或 TTS，外放回声按固定衰减模拟。
真实现场还有麦克风频响、房间混响、系统级 AGC——这些变量合成不出来。
所以 V1 的交付不是"一组魔法数字"，而是**可观测（`?vaddebug=1`）+ 可复算（本脚本）
+ 有安全区间（上表）**，现场照着调三分钟就能定下来。

### 4.8 真机直录推翻了 4.7 的一部分结论（2026-11-07 补）

4.7 那张表是在**我自己造的数据**上跑出来的：静音是数字 0，回声是把播报乘 0.05。
在这上面怎么调都全过。所以补了一轮真机直录（`scripts/record_real_vad.py`，
waveIn 直连麦克风阵列、**不经浏览器 AEC**），结果直接打脸：

| 实测项 | 结果 | 意味着什么 |
|---|---|---|
| 静音 6 秒的 rms | p50 `0.0001` · **p99 `0.0294`** · max `0.0352` | 底噪峰值已经高过 `speechRms=0.020` |
| 静音里 ≥0.020 的最长连续帧 | **4 帧**（开口只要 2 帧） | **没人说话也会自己开口** |
| 外放播报 12 秒的 rms | p90 `0.1200` · **max `0.2119`** | 回声比人声 p50（0.039）响 5 倍 |
| 播报里 ≥0.035 的最长连续帧 | **9 帧**（疑似打断只要 3 帧） | **客服会把自己打断**（音量被反复压低） |
| 底噪 tilt（低频/高频） | p50 `36` · p90 `540` | 底噪是低频隆隆，tilt 比部分人声帧还高 |
| 人声 tilt | p50 `160` | **tilt 分不开底噪** —— 这条判据在真实底噪面前方向是错的 |

两条硬结论：

1. **合成语料上的 15/15 不能当现场证据。** 底噪是 0 的语料永远测不出"静音误开口"。
2. **纯能量 + tilt 在真实底噪下不成立**，所以真实链路必须靠浏览器那三道
   （`echoCancellation` / `noiseSuppression` / `autoGainControl`）先把底噪压下去。
   上面这些数是**没有 AEC 的最坏情况上限**，不能直接拿去当前端阈值用——
   在错的链路上调参，正是这一轮踩的坑。

> 也因此不能反过来"按真机数据把 speechRms 调到 0.035"：那是拿无 AEC 的噪声底
> 去要求有 AEC 的链路，调完真人小声就切不出来。**结论只能是：去浏览器链路里采。**

**同时修掉的三个真缺陷**（都与 4.7 无关，是代码本身的问题）：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| 端点用 `voiced` 数静音帧 | 用户说到一半侧头/换字音，zcr 或 tilt 一不达标就算静音，700ms 把一句话切成两半 | 端点只看能量（`rms ≥ silenceRms`），`voiced` 只用于**开口确认** |
| `bandEnergy` 是**单点** Goertzel | 20ms 窗分辨率只有 50Hz，"400Hz 有没有能量"跟基频落在哪强相关，女声 400Hz 恰是谷 → tilt 掉到 0.1，真人被判成键盘 | 改成低频 300/500/700、高频 1800/2400/3000 **各三点均值**，前后端同步 |
| 回声被当成用户插话 | 外放时麦克风收到自己的播报，ASR 原样识别出客服的话，`_has_interrupt_content` 判"有实义" → **直接停播** | 前端随探针上报当前播报文本，服务端 `_is_self_echo()` 用字符覆盖度 ≥0.6 判回声并否决（`reason=echo_self`） |

**现场校准链路（新增）**：

1. 浏览器打开 `http://127.0.0.1:8000/?vadcal=1` → 点「开始」；
2. 走完四步：静音 4s → 外放播报 7s → 念一句提示的话 6s → 敲键盘 5s（共约 22 秒）；
3. 下载 JSON → 放进 `data/vad_calib/`；
4. `python scripts/fit_vad_from_calib.py` → 输出这台机器上的分位数与**建议阈值**，
   并且**先判有没有解**：如果回声 p99 高过人声 p50，脚本会直说"阈值无解"，
   给出降音量／戴耳机／靠回声否决三条路，而不是硬凑一组数字。

这一步采的是**真实链路**（扬声器→房间→麦克风→浏览器 AEC/NS/AGC），
是 4.7 那套离线仿真无法替代的部分。

## 5. 阶段 2：WebSocket 流式（要动通道，另开一轮）

> **落地状态（2026-11-05，角色 1）**：本节设计的通道已实现——
> `modules/wsproto.py`（RFC 6455 编解码，纯标准库）、`ws_channel.py`（会话协议层，
> 可注入假后端离线测试）、`app.py` 的 `/ws/call`（握手 + 读写循环）、
> 前端 `web/index.html` 的 WS 层（帧直推 + 段就绪即播 + 可回退 HTTP）。
> 流式识别适配层在 `modules/realtime_asr.py`（paraformer-realtime-v2），
> **默认关闭**（`asr.realtime=true` 才启用）：协议与解析可离线断言（verify 证据 14），
> 但**真密钥连通尚未验证**——开启前必须先跑通一次真实识别。
> 合成侧走"分段就绪即推"而非云端流式接口（不受 QPS 限制，首段延迟已达标）。
> WebRTC / 弱网传输仍不做。回归：verify **73/73**（证据 14 新增 12 条），eval 30/30。

### 5.1 为什么必须换

HTTP 是"请求-响应"：服务端没办法在用户说话说到一半时主动告诉前端"我听到前半句了"。
要做到边说边识别、边合成边播，通信模型必须从"问答"变成"双向流"。

### 5.2 目标形态

```
浏览器 ──[WS]──> 服务端 ──[WS]──> qwen3-asr-flash(realtime) / paraformer-realtime-v2
   │                                    │
   ├─ 二进制帧：PCM 20ms                 ├─ partial 文本（不回给用户，只做前端字幕）
   └─ JSON：控制指令（start/stop/barge）  └─ final 文本（触发编排）
```

关键变化：

1. **音频不再缓存整段**：采集到的帧直接推给识别，说完即出 final；
2. **服务端主动下发**：TTS 首包一到就推给前端播，不再等整句；
3. **打断变成协议事件**：`{type:"barge_in"}` 同时通知服务端停合成、通知前端停播。

### 5.3 代价

- 服务端要维护长连接与会话映射（现在每个请求无状态）；
- 前端要处理重连、半开连接、断线重放；
- 云端识别换实时接口，单价与调用方式都变（`docs/05` 有价格）。

**建议：阶段 1 上线跑通、评委试用过之后，再决定要不要投入阶段 2。**

## 7. 怎么验证"真的像打电话"

别只看代码，按下面四条实测，每条都要能过：

| # | 动作 | 期望 |
|---|---|---|
| 1 | 拿起就说，不点任何按钮 | 说完约 0.7 秒后客服开始回应 |
| 2 | 客服说到一半，插一句"等一下" | 0.3 秒内停播，日志出现 `barge_in` |
| 3 | 连续说三四轮，中间不操作 | 每轮都自动接上，不出现 409 或串轮 |
| 4 | 外放音量开大，客服自己说话 | **不能自己打断自己**（这是最容易翻车的一条） |

第 4 条如果过不了，说明打断阈值太低或 AEC 没生效，宁可把阈值调高——
"偶尔打断不了"比"自己跟自己抢话"体面得多。
