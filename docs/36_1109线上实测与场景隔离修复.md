# 11-09 线上实测与场景隔离修复

这份文档记录一次「从线上实际表现反推问题」的排查：先跑线上部署的自动对话 +
AI 监督接口，把看到的异常逐条落到代码根因，再修，再验证。

被查的部署：`https://voice-agent-skeleton.app.workbuddy.host`（`sharecode=ACYOJRLVUP`），
对应 main `8a7a77c7`。所有结论都有可复现的命令。

其中闭环只改**话术与开关**，不改代码，且上架要人工执行。

## 三、测出来的四个问题

### P0：对抗跑批把 340 条用例跑错了场景，分数是假的

修之前 `python scripts/adversarial_run.py` 输出：

```
对抗测试：374 条 × 1 轮
  第 1 轮：通过 31/374
平均通过率 8.3%
失败聚类：IDENTITY 闭环不符 x340
```

340 条全部卡在身份核验。查下去发现两条：

1. `eval/adversarial_c4_batch01~09.json` 是 **4 号按官方 68 个关单场景**生成的
   （68 场景 × 5 变体 = 340 条），属于 **POP 关单场景**；
2. 但 `adversarial_run.py` **没有 `--scene` 参数**，永远用 `config/scene.json` 的默认
   **售后场景**跑。于是开场白是「京东客服中心的小采，请问是张先生本人吗」，
   客户报的尾号跟这套售后假客户一个也对不上。

证据（同一条用例，只改场景）：

```bash
# 默认场景 → 失败，卡 IDENTITY
python3 scripts/run_eval.py --cases eval/adversarial_c4_batch01.json C4-S01-Q1
# → 通过率 0/1

# 切 POP 场景 → 通过
python3 scripts/run_eval.py --scene pop_reject --cases eval/adversarial_c4_batch01.json C4-S01-Q1
# → 通过率 1/1 = 100%
```

整批：`--scene pop_reject` 下 **40/40 = 100%**、**340/340 = 100%**。

所以 8.3% 不是「系统烂」，是**跑批工具跑错了场景**。这个数字本来会喂给
`--fail-under` 当 CI 卡口，错一次就会写出一份"系统快崩了"的错误周报。

### P1：收尾话术被挂了补救型后缀

A01 第 9 轮，客户说「好的，清楚了，我按你说的弄」，客服回：

> …感谢您的配合，再见。**我放慢一点说。**

`persona.adapt()` 的文档写明「挂断话术全冻结」，但 `_persona_freeze` 的判据只看
`end_reason` 与 `intent`：正常闭环的 `end_reason` 是空串（闭环不是异常结束），
`intent` 是 `consent`，两条都不命中，于是后缀照加。

客户已经说清楚了，还要「放慢一点说」，逻辑上就不通；而且这是整通电话最后一句话，
尾巴一定会被听见。

### P1：「我刚不是说了吗」不算修复请求

`policy.REPAIR_MARKS` 只收「再说一遍 / 没听清 / 信号不好」这类**带重说动作**的说法。
客户换一种说法——「我刚不是说了吗，就那几个数」——就识别不出来，于是落进知识库检索，
查不到就回「这个我这边确认不到」。A01 第 6~7 轮、A04 第 4 轮都是这么卡住的。

### P2：OFFER 阶段的修复分支是关的

代码里 `_repair_reply()` 早就写好了（注释还点着 A01 第 4~7 轮），但
`evolution_policy.repair = {"OFFER": false, "CONFIRM": true}`——**CONFIRM 开了，OFFER 没开**。
A01 的问题恰好全在 OFFER 阶段，所以修复代码一次也没跑。

## 四、改了什么

| 文件 | 改动 | 为什么 |
|---|---|---|
| `scripts/adversarial_run.py` | 加 `--scene` / `--all-scenes`；按文件归属场景分批；默认只取当前场景的用例并打印跳过清单 | 上面那条 P0 |
| `modules/dialogue.py` | `_persona_freeze` 增加 `next_stage == "DONE"` | P1 收尾后缀 |
| `modules/policy.py` | `REPAIR_MARKS` 增「不是说了吗 / 不是说了嘛 / 不是说了么」 | P1 抱怨重复 |
| `config/scene.json`<br>`config/scenes/pop_reject.json` | `repair.OFFER` → `true` | P2 |
| `scripts/test_scene_isolation.py`（新） | 11 条自测 | 守上面三处 |
| `scripts/verify.py` | 新增**证据 33** | 不进总闸门等于没测 |

`--all-scenes` 为什么要起子进程：场景在 `import app` 时就定死了
（`run_eval._scan_argv` 读 sys.argv），同一个进程切不回来。
汇总口径用 **总通过数 / 总用例数**，不是各批通过率的平均——340 条和 34 条不能等权。

## 五、验证

```bash
python3 scripts/verify.py                        # 217/218（原始 main 215/216）
python3 scripts/run_eval.py                      # 88/88 = 100%
python3 scripts/adversarial_run.py               # 31/34 = 91.2%（默认场景，只跑 34 条）
python3 scripts/adversarial_run.py --scene pop_reject   # 340/340 = 100%
python3 scripts/adversarial_run.py --all-scenes  # 371/374 = 99.2%
python3 scripts/test_scene_isolation.py          # 11/11
```

| 指标 | 改前 | 改后 |
|---|---|---|
| 对抗（混跑） | 31/374 = **8.3%** | 不再产生这个数字（会提示跳过 9 批） |
| 对抗（默认场景） | 混在上面 | 31/34 = 91.2% |
| 对抗（POP 场景） | 混在上面 | 340/340 = 100% |
| 对抗（全部汇总） | 8.3% | **99.2%** |
| `run_eval` | 88/88 | 88/88（未降） |
| `verify` | 215/216 | 217/218（+2 条，全过） |
| A01 `weakness.repeat` | 3 | **1** |

`verify` 的两条失败（性格单测 + 两条进化链体检）在**原始 main 上同样失败**：

「基线结果没有内容哈希」。本地完整 clone 不会有这个问题。

## 六、没修的三件，说明原因

1. **客户问「后台哪个入口」，还是会被答成「确认不到」**。
   `policy._QUESTION_CLASSES` 只有 fee/validity/material/reason/provenance 五类，
   **没有「操作路径」类**；`answer_routes` 也没配对应话术。
   POP 场景靠知识库扛住了（C4 340/340），售后场景没有这条知识。
   补法是加一类问题 + 一条话术，属内容层，建议单开一单。

2. **「你哪来的我号码，怎么信你」被答成「确认不到」**。
   分类能归到 `provenance`，但 `answer_routes` 里没有 `provenance` 路由，
   于是回落兜底。同上，缺话术。

3. **OFFER 阶段开 `repair` 是配置改动，绕过了自进化闸门**。
   我实测过：`run_eval` 88/88 不变、对抗 99.2% 不变，A01 的 `repeat` 从 3 降到 1。
   即**分数证明不了收益，只有轨迹能证明**。这正说明现有评测集覆盖不到
   「听不清 → 要求重说 → 是否复述」这条路径，建议给 C4 或 1106 补一类专门用例，
   再让闭环自己决定这个开关。

## 七、运维备忘

- 混场景跑批是**静默错误**：不报错，只是分数难看。以后加新场景批次，
  必须在 `adversarial_run.SCENE_OF_FILE` 里登记，否则会被当成默认场景跑。
- CI 想一次跑全，用 `--all-scenes`，不要直接把 `adversarial*.json` 合并。
- 线上 `GET /api/sessions` 已经 403，但 `_is_loopback()` 在反向代理后仍然恒真，
  这条防线是「靠别的检查挡住」而不是「靠地址判断」，改路由时要留意。

## 八、评审后调整（同日晚，复核）

复核方式：把 `fix/eval-scene-isolation` 检出到独立 worktree，跑对抗画像（16 通）、
三套跑批、`verify`，并对新测试做**反向变异**（把修复删掉，看测试会不会红）。

### 8.1 保留的两条

- **P0 场景分批**：复算一致。默认场景 31/34、`--scene pop_reject` 340/340、
  `--all-scenes` 371/374 = 99.2%；跳过清单会打印，汇总用总通过数不用通过率平均。
- **P1 收尾冻结**：`_reply(next_stage="DONE")` 实测输出「感谢您的配合，再见。」，
  对照组 `WRITEBACK` 仍会加「我放慢一点说。」——判据确实生效。

### 8.2 撤回的两条（有实测反例）

| 配置 | 16 通对抗画像 | 负面反馈 |
|---|---|---|
| main（8a7a77c） | **16/16** | 6 |
| PR 原样（收「不是说了吗」+ `repair.OFFER=true`） | **14/16** | 8 |
| 只撤「不是说了吗」，保留 OFFER | 16/16 | 8 |
| 两条都撤（本分支现状） | **16/16** | 6 |

1. **「不是说了吗」不能算修复请求**。它把复述塞进了确认计数那一轮，A09/A14
   最后以 `unknown` 回写收线——期望是**不闭环**，实际闭环了，属于误闭环；
   `attribution` 现有缺陷码覆盖不到，只能记成 `unexplained`。另外这句以
   「我不是」开头时会命中 `DENY_PERSON`，被判成「打错人」直接挂断。
2. **`repair.OFFER=true` 没有闭环证据**。开关本身是配置项，但：
   - 打开后负面反馈 6→8（`no_answer` 3→5）：客户问「你哪来的号码」时，
     复述整段驳回原因并不回答问题；
   - 客户说「我不是说了吗，不要了」时，修复分支排在拒绝之前，整通电话
     不回写、继续留在 OFFER——该记的「拒绝」丢了；
   - 评审用 `self_evolve.py run` 复跑：打开它收益为负，闭环不会采纳。
   所以维持 `false`；要开必须走 `self_evolve.py` 的四道验收。

### 8.3 测试假绿与已补断言

原 `test_done_turn_keeps_reply_clean` 用 `D.respond(...) + if 以再见结尾` 断言，
把 `_reply` 里的 DONE 判据删掉后 **11/11 仍然全过**——它测的是「这轮没触发」，
不是「判据生效」。已改为直接调 `D._reply(next_stage="DONE")` 并附对照组；
`test_plead_repeat_is_repair` 改为 `..._is_not_repair`，新增「拒绝优先于修复请求」
真跑断言（`consent=False`、`next_stage=DONE`）。两条都做过反向变异：删修复 → 红。

`verify` 里原来那条「OFFER 分支已打开」的断言改为「修复请求只认重说动作」，
避免把一次未经闸门的配置改动固化成验收标准。

### 8.4 顺手修的两处提示

- 跳过默认场景用例时打印「请不带 `--scene` 单独跑」，不再给出 `--scene <默认>`
  这种敲不出来的命令。
- `--all-scenes` 与 `--cases` 互斥（同时传直接报错），避免 CI 以为跑了全套。

### 8.5 仍未解决

- 「期望不闭环却闭环了」没有缺陷码：本次靠人眼从 `rows` 里发现。
  建议在 `attribution` 增一个 `agent_premature_close`（closed=True 且 expect.closed=False
  且无回写理由），否则同类问题下次还会被记成 `unexplained`。
- 「后台哪个入口」「你哪来的号码」在售后场景仍会答成「确认不到」，
  与本文第六节一致；pop 场景由知识库与 `answer_routes` 覆盖。
