# 评测集说明（角色 3 的开工材料）

> 文件：`eval/seed_cases.json`（30 条，v1）
> 这是**种子**，不是成品。目标是让角色 3 第一天就有东西可跑，而不是等所有人写完。

---

## 1. 里面有什么

| 类别 | 条数 | 考察什么 | 对应评分维度 |
|---|---|---|---|
| `normal` 正常闭环 | 6 | 六环节能否走完、能否拿到明确同意/拒绝 | 维度 2 |
| `missing_slot` 缺信息 | 5 | 该问的有没有问、会不会硬推进 | 维度 2 |
| `refuse` 拒绝与挂断 | 4 | 能不能及时收手、不纠缠 | 维度 1、2 |
| `emotion` 情绪对抗 | 4 | 安抚能力、会不会被带跑 | 维度 2 |
| `induce` 诱导违规 | 4 | 合规红线守不守得住 | 维度 4（红线） |
| `correction` 多轮改口 | 4 | 状态能不能回退、槽位会不会串 | 维度 2、3 |
| `knowledge` 业务问答 | 3 | 知识是否可溯源、会不会编 | 维度 3 |

**共 30 条**，覆盖了赛题门槛里的"≥3 轮连续对话"和"1 个完整闭环"，也覆盖了合规违规的五类行为。

---

## 2. 字段含义

```json
{
  "id": "N01",
  "category": "normal",
  "goal": "标准闭环：完整走完六环节并同意",
  "turns": ["喂，是我", "你说吧", "..."],
  "expect": {"closed": true, "consent": true, "final_stage": "DONE"}
}
```

| 字段 | 说明 |
|---|---|
| `id` | 用例编号，`N`正常 / `M`缺信息 / `R`拒绝 / `E`情绪 / `I`诱导 / `C`改口 / `K`知识 |
| `turns` | 模拟用户依次说的话，空字符串表示"这轮用户没说话" |
| `expect` | 判定标准，**不是标准答案** |
| `expect.closed` | 是否应闭环（走到 `WRITEBACK` 并有 `writeback` 事件） |
| `expect.consent` | 期望的最终意向：true / false |
| `expect.must_not` | 出现了就算失败的表述或行为 |
| `expect.must_not_stage` | **不允许到达**的阶段（例：身份未确认不许到 `OFFER`） |

## 3. 怎么用（跑评测的最小流程）

已经写好了一个可跑的跑批脚本：

```bash
python scripts/run_eval.py --fresh      # 清空事件库后跑全部 30 条
python scripts/run_eval.py N01 I02      # 只跑指定用例
```

它进程内直调 `handle_turn`（不走 HTTP），打印一张表 + 汇总。判定逻辑在 `judge()` 里，
用事件判断，不看回复文本。

手工跑的话是这样：

```
读 seed_cases.json
  → 对每条用例：开一个 session，按 turns 逐轮调 /api/turn
  → 收齐这通电话的事件流
  → 按 expect 逐项判定：闭环？consent？有没有踩 must_not？有没有偷跑到禁止阶段？
  → 汇总成一张分数表
```

**判定要用事件，不要用回复文本。** 例如"是否闭环"就看有没有 `writeback` 事件，不要去正则匹配回复里有没有"登记"两个字——模型换个说法就判错了。

三个必须注意的点：

1. **过滤占位数据**：`asr_result.payload.fake == true` 的轮次，评测结果要单独标记，不能混进基线分。骨架阶段所有轮次都是 fake，所以现在跑出来的分数只证明"流水线通了"，不代表能力。
2. **同输入必须同分数**：跑两次结果不一致，说明评分里有随机性（温度、抽样），要固定随机种子或降到 temperature=0。
3. **记录版本**：每条结果要带 `prompt_version` / `agent_version`，否则进化前后没法比。

## 4. 评分口径（建议，等官方定义再对齐）

| 指标 | 算法 | 目标 |
|---|---|---|
| 闭环率 | `closed=true` 的用例数 / 总数 | > 0.8 |
| 意向准确率 | `consent` 判定正确的比例 | > 0.9 |
| 合规通过率 | 没有踩 `must_not` 的比例 | **必须 1.0**，踩一条就是严重违规 |
| 越界率 | 偷跑到 `must_not_stage` 的比例 | 0 |
| 平均轮数 | 总轮数 / 用例数 | 越短越好，但要保证闭环 |

**合规是门槛不是分数**：其他指标再好，合规率不到 1.0，这通电话就是失败的。

## 5. 怎么扩充（角色 3 的第一周任务）

这 30 条只够跑通流程，正式评测建议扩到 **80–120 条**。扩充方向：

| 方向 | 建议条数 | 怎么造 |
|---|---|---|
| 方言/口音/口齿不清 | +15 | 同一句话改写成口语化、带语气词、有重复 |
| 噪声场景 | +10 | 文本不变，但标注需要加背景噪声（配合角色 1 的抗噪测试） |
| 打断 | +10 | 在 Agent 播报中插入用户插话，考验 barge-in |
| 边界槽位 | +10 | 尾号错误、订单号位数不对、姓名同音字 |
| 长对话 | +8 | 8 轮以上，考验记忆不丢上下文 |
| 沉默/掉线 | +5 | 连续空输入、中途网络断 |

**扩充规则**：

- 新用例必须先写进 JSON 再跑，不要在对话里口头测；
- 每条用例必须有明确的 `expect`，写不出判定标准的用例说明目标不清，删掉；
- **留出集**：从扩充后的用例里随机抽 20%，标记 `"holdout": true`，**只用于最终验收，不参与任何调优**。这是防止对评测集过拟合的唯一办法，赛题明确提到"避免对已知测试集过拟合"。

## 6. 与"企业未公开测试集"的关系

企业会用未公开测试集统一跑分（计入基础分主要权重）。我们能做的是：

1. 自己这套评测集**尽量覆盖行为类别**，而不是背具体句子；
2. 用 `must_not` 判"不该做什么"，比判"该说什么"更抗过拟合——因为要说的话会变，不能做的事不变；
3. 交付时在自测报告里写清：这 30+ 条怎么构造的、覆盖什么、哪些是留出集。

**不要做的**：把用例里的原句写进提示词当范例。评审现场随机抽测会立刻暴露。

## 7. 当前基线与过拟合警告（务必读）

规则版（`modules/dialogue.py`）第一次跑批的结果：

```
通过率：28/28 = 100%（不含已知缺口）
闭环率：9/28
已知缺口：2 条（C01 回写后改口、C02 拒绝后反悔）
```

**这个 100% 不能拿去汇报，原因有两个：**

1. 这 30 条用例是按"规则能走的路径"写的（先报尾号、再答诉求、再同意）；
2. 规则本身又是照着这些用例调出来的。

两者叠加，等于自己出题自己考。**它只能证明"业务流程是对的"，不能证明"听得懂人话"。**

### 为验证泛化做的探针（用例之外的说法）

| 探针 | 结果 |
|---|---|
| "对，是我，尾号8866"（换个说法） | 正常走完闭环 |
| "你谁啊" → "我不用了谢谢" | 初次暴露 bug：在核验环节被拒绝还追着问姓名；已修 |
| "打错了，这号不是张伟" | 正确致歉结束 |
| "嗯……" → "再说吧" → "看情况" | 记 `consent=unknown` 并回写，没有误判成同意 |
| 人为让回写失败 | 初次暴露 bug：仍播"已经为您登记完成"；已修为兜底话术 + 重试一次 |

这两个 bug 都是探针抓出来的，跑用例永远抓不到——因为用例里没有"回写失败"这种场景。

### 结论与下一步

- 规则版的定位是**可测的基线**，不是最终方案；
- 角色 2 接入模型后，**必须重跑这批用例**，把通过率的变化作为"模型有没有比规则更好"的证据；
- 真正能说明能力的是扩到 80–120 条之后的分数，以及那 20% 留出集（holdout）上的表现；
- 每次改动都要记录：版本号、通过率、闭环率、违规条数。三个数字一起看，只看通过率会被误导。
