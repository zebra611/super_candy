## 1. 一句话定位

**任务 2 决定"说什么"，不决定"怎么把声音搬过去"。**

任务 1 已经把声音变成文字、把文字变成声音、并且随时能被用户打断。
任务 2 要解决的是：拿到一句用户的话，决定**下一步走哪、查什么、怎么回**。

| 层 | 谁 | 管什么 | 不管什么 |
|---|---|---|---|
| 流程 | 状态机（现有 `dialogue.py`，**不动**） | 现在该走哪一步、能不能推进、什么时候收尾 | 这句话措辞好不好听 |
| 措辞 | **LLM（佟欣新写的 `modules/nlg.py`）** | 同一件事怎么说得像个人 | 能不能跳过身份核验、能不能不回写 |
| 事实 | **工具适配层（潘柏亦新写的 `modules/adapters/`）** | 客户是谁、买过什么、工单登记到哪 | 该不该问、该怎么措辞 |

**这个边界必须守住。** 一旦 LLM 开始决定"该不该问手机号"，就会出现
"模型觉得不用核验身份"这种要命的行为，而且不可复现、查不出来。

## 2. 为什么是"改写"而不是"自由生成"

这是整份契约最关键的一个决定，先说清楚。

**错的写法**：把用户的话丢给 LLM，让它自己决定回复什么。
→ 后果：模型会自由发挥、跳过环节、承诺没授权的东西、每次说法不一样；
合规护栏只能事后拦，拦到就整句替换，用户听到一句生硬的兜底话。

**对的写法**：状态机先决定"这一步要表达什么"，用一句**现成的骨架话术**
承载意图；LLM 只负责把这句话说得自然、结合上下文。

```python
# 现状（规则版）：话术直接从 config 取
text = cfg.get("reply")                       # "为了核对身份，请说一下手机号后四位"

# 任务2（LLM 版）：骨架不变，LLM 只改措辞
base = cfg.get("reply")                       # 同一句骨架
text = nlg.say(session, base, stage="IDENTITY")   # 可能变成："好的，为了确认是您本人，麻烦报一下手机号后四位？"
```

这样带来的好处，每一条都是硬收益：

1. **业务正确性不依赖模型**。模型抽风最多是话说得别扭，不会漏环节。
2. **合规护栏仍然有效**。禁语检查在 `app.py` 里对最终 `reply_text` 做，
   换了措辞也跑得掉。
3. **降级零成本**。LLM 超时/报错 → 直接返回 `base`，行为退回今天的样子。
4. **可回归**。把 LLM 关掉，`verify.py` 的 86 条断言必须全过——
   这是判断"有没有改坏"的唯一标准。

## 3. 接缝一：话术生成（2A 佟欣）

### 3.1 新增文件，不动旧逻辑

新建 `modules/nlg.py`，只暴露一个函数：

```python
def say(session, base_text, stage=None):
    """把骨架话术改写成自然口语。

    参数：
        session    对话状态（只读，禁止修改！里面 slots 是业务事实来源）
        base_text  骨架话术，来自 config/scene.json 的对应环节
        stage      当前环节名（GREETING/IDENTITY/NEED/OFFER/CONFIRM/WRITEBACK）

    返回：str
        改写后的话术。**任何异常都必须返回 base_text 本身**，
        不允许抛异常、不允许返回空串——外呼里没声比话说得难听严重得多。
    """
```

调用点写在 `dialogue.py` 里（**由我改，佟欣不要动**）：
所有 `cfg.get("reply")` 取到文本之后、传给 `_reply()` 之前，过一次 `nlg.say()`。

开关在 `config/scene.json`：

```json
"nlg": {
  "provider": "template",     // template = 关闭，走骨架话术；dashscope = 开
  "model": "qwen-turbo",
  "timeout_ms": 400,
  "max_chars": 45
}
```

默认必须是 `template`。理由：队友 clone 下来没有密钥，不能因此跑不起来；
自检和跑批也默认不开 LLM（否则每跑一次 30 条用例就是 30 次模型调用）。

### 3.2 时延预算：给 LLM 的额度只有 400ms

这是硬约束，不是建议。当前实测（30 轮基准，服务端口径）：

| 环节 | 现在 | 加 LLM 后预算 |
|---|---|---|
| ASR 识别 | 390ms | 390ms（不变） |
| 状态机 + 工具 | ~50ms | 50ms |
| **LLM 生成话术** | 0 | **≤400ms** |
| TTS 首段合成 | 457ms | 457ms |
| **服务端合计** | 974ms | **≤1300ms** |
| 网络 + 播放启动 | 150–250ms | 150–250ms |
| **真实首字** | ~1.2s | **≤1.55s**（门槛 2000ms） |

对应三个直接后果，写代码前先认下来：

1. **模型只能用快的**。`qwen-turbo` 这一档。`qwen-max` 首 token 就要 800ms+，
   用它等于把余量全吃掉。
2. **输出必须短**。`max_chars` 上限 45 字，超了截断并记日志。
   理由：TTS 耗时与字数近似线性（实测 3 字 344ms / 30 字 1684ms），
   LLM 多说 20 个字，TTS 就多花 0.5 秒——把省下的时延又还回去了。
3. **超时就放弃，不要等**。400ms 没出结果就用骨架话术。
   宁可话说得朴素，也不要让用户对着话筒等 1.5 秒。

### 3.3 prompt 结构（照这个写）

```
system:
你是京东客服外呼坐席，正在给一位客户打电话。
规则：
1. 只把给定的话术改写得更自然口语，不得改变它的意思、不得增加新的事实。
2. 不得承诺、不得提及任何具体金额、日期、政策——这些只能来自给定的业务数据。
3. 一次只说一件事，不超过 45 个字，不要用书面语和括号。
4. 不要重复用户刚说过的话。
5. 客户带情绪时，先简短致意再进入正题。

user:
【当前环节】{stage}
【本轮要表达的意思】{base_text}
【已知信息】姓名：{slots.customer.name or 未知}；订单：{slots.order.title or 无}
【客户刚说】{slots.last_user_text}
【客户情绪】{angry / 平静}
【最近两轮对话】{历史}
```

**注意 system 里第 2 条**：这是防止模型编造业务事实的护栏。
它不能替代合规检查，但能大幅降低触发整句替换的概率。

### 3.4 降级路径（必须实现，不是可选）

按这个顺序判断，任何一步不满足都直接返回 `base_text`：

```
1. provider != "dashscope"           → 返回 base_text
2. 没有 API Key                       → 返回 base_text（并记一次 warn）
3. 请求超时（>timeout_ms）            → 返回 base_text
4. 返回空串 / 只有标点                → 返回 base_text
5. 返回值与 base_text 字数差异 > 2 倍 → 返回 base_text（防模型跑题长篇大论）
6. 其余                               → 用返回值
```

第 5 条容易被忽略，但很实用：模型偶尔会"解释一番"，一句话变成三句话，
TTS 直接慢一倍。字数突变就是跑题的信号。

**`say()` 内部不允许抛异常。** 它在外呼主链路上，抛了就是整通电话断掉。

### 3.5 验收标准

| 项 | 标准 | 怎么测 |
|---|---|---|
| 关掉 LLM 时行为不变 | `verify.py` **86/86**、`run_eval.py` **30/30** 全过 | 直接跑 |
| 开着 LLM 时业务不变 | `run_eval.py` 通过率不低于 28/30 | 跑批对比 |
| 时延预算 | 服务端 P50 ≤1300ms | `bench_voice.py`，需 ≥20 轮 |
| 不编造事实 | 20 句抽取检查，无杜撰的金额/日期/政策 | 人工看事件链里的 `agent_reply` |
| 降级可用 | 故意配错 Key，全链路仍能出话术 | 改 `secrets.json` 跑一轮 |

**"关掉 LLM 必须全过"这条是底线**：它证明佟欣的改动没有侵入业务流程。
如果这条不过，说明改动跑到了状态机里，必须退回。

## 4. 接缝二：工具适配（2B 潘柏亦）

### 4.1 现状与目标

`modules/tools.py` 现在三个工具**全部返回写死的假数据**（文件头自己写着）。
契约（`contracts.TOOL_SCHEMAS`）已经定好了，不需要改：

| 工具 | 参数 | 返回 | 幂等 |
|---|---|---|---|
| `query_customer` | `keyword`（姓名或手机号后四位） | `{found, customer}` | 是 |
| `query_order` | `customer_id` | `{found, order}` | 是 |
| `create_ticket` | `session_id`, `content`, `idempotency_key`, `version` | `{ticket_id, created, updated, version}` | **是**（按 `idempotency_key` 幂等） |

### 4.2 怎么接真实数据

新建 `modules/adapters/`，每个工具一个适配器文件，实现同一个形状：

```python
def query_customer(keyword):
    """返回契约结构；查不到就 found=False，不要抛异常。"""
```

`tools.py` 保留为**分发层**，按配置选真实适配器还是假数据：

```json
"tools": {
  "provider": "mock",      // mock = 现在的假数据；real = 走适配器
  "timeout_ms": 300
}
```

默认必须是 `mock`。同样是为了"队友 clone 下来就能跑"。

> **注意区分两个数字**：这里 300ms 是**我们的超时预算**；
> `mock_business/README.md` 里提到的 3 秒是**Mock 服务自己模拟的耗时**。
> 适配器必须在 300ms 处主动放弃并按"查不到"返回，不能等它 3 秒——
> 整轮预算只有 1300ms，等 3 秒等于这通电话的首字直接爆掉。

### 4.3 三条硬要求

1. **失败不许抛异常，要返回契约结构**。
   查不到客户是 `{found: False}`，不是 `raise`。上层状态机会据此走"核对不上"分支。
   适配器内部异常 → 包成 `{found: False, error: "..."}`，并记日志。

2. **超时 ≤300ms，超了就按"查不到"处理**。
   工具卡住会直接压垮首字响应。现在整轮预算只有 1300ms（见第 3.2 节），
   工具吃掉 300ms 已经很多了。

3. **`create_ticket` 的幂等性不能破**。
   幂等键就是契约里的 `idempotency_key`，约定格式 `会话ID:WRITEBACK:v版本号`
   （用户改口时 version 递增，保证"同一张工单被更新"而不是新开一张）。换成真实系统后，
   这个语义要映射到真实工单的"更新"接口，**不能变成每次都新建**。
   否则用户改一次口就多一张工单，这是回写环节最典型的线上事故。

### 4.4 验收标准

| 项 | 标准 |
|---|---|
| 接口形状不变 | 关掉真实适配器（provider=mock），`verify.py` 86/86 全过 |
| 查不到不报错 | 传一个不存在的手机号后四位 → `found=False`，流程走"核对不上"分支 |
| 超时可控 | 假适配器故意 sleep 1 秒 → 300ms 内返回 `found=False` |
| 幂等 | 同一 session 同一 version 调两次 `create_ticket` → 第二次 `created=False, updated=False` |

## 7. 一个必须提前知道的坑

**LLM 会让首字时延涨一次，而这次涨幅是不可逆的。**

现在服务端 P50 是 974ms，还有 1 秒余量。加了 LLM（≤400ms）之后是 1.3 秒，
浏览器口径落在 1.4–1.55 秒，门槛 2 秒——**过线，但没有余量了**。

如果后面发现 LLM 实际要 600ms（很可能，qwen-turbo 在网络抖动时也会慢），
唯一的出路是**把识别改成流式**（边说边识别，说完即有结果），
那是任务 1 的 S2/S4，要动 WebSocket 和第三方依赖。

所以：**佟欣的 400ms 预算是硬上限，不是参考值。**
超了就换模型或砍 prompt，不要指望"后面再优化时延"——
后面那一步的代价比现在大得多。
