## 一、19:42：客服问「需不需要把清单发到后台」，客户回「需要」却答非所问

真跑复现逐字对应：

```
[4] 你：材料    → 列了原因 + 三样材料
[5] 你：知道了  → 「您是清楚怎么操作了，还是需要我把清单发到后台？」
[6] 你：需要    → 「我跟您复述一下：您这笔申请没有通过审核，原因是…」CONFIRM
[7] 你：清楚了  → 「稍后短信会同步到您后台…再见。」
```

用户判断：「你应该**直接把清单发到后台**，让他有不清楚的或者不记得的话直接看后台清单就行」。

**改法（做成真实工具动作，不是口头承诺）**：

- 新增工具契约 `send_checklist`（`contracts.TOOL_SCHEMAS`、`base.TOOL_METHODS`、
  `tools.dispatch`）；`MockAdapter.send_checklist` 把清单写进 `_checklists`，
  返回 `checklist_id / materials / channel=merchant_backend`，按
  `(application_id, session_id)` 幂等，重复调用 `already_sent=True`。
  `reset()` 同步清理，`tools.checklist_for_application()` 可查。
- `dialogue._ensure_checklist()` 按**工具真实结果**记账（失败绝不置
  `checklist_sent=True`）；`_checklist_reply()` 把 `tool_call` 交给 `app.py`
  统一写事件并 dispatch。`app.py` 里加了失败兜底：没发成功就如实说明 +
  热线 4006180092，不许播「已经发到后台」。
- 回写工单 `content` 带 `checklist_sent / checklist_id`（只在真发过时写）。
- 收线话术换成 `reply_checklist_done`：「清单也在您商家后台了，随时可以翻看」，
  并走冻结 `intent=consent_checklist`——实测不冻结会被措辞层压成
  「后台能查到」，"忘了直接翻清单"这句就没了。
- `reply_unclear_offer_2` 不再问「要不要发清单」；`_clarify` 在 OFFER 阶段
  含糊直接发清单并告知。

## 二、19:46「全是问题」：客户说了四次「清楚了/知道了/没有了」，还在复述、还在追问

同一段「原因 + 三样材料」念了四遍，问了四次「还有不明白的吗」；客户问
「什么授权」被套「您想先问哪一步」，「是不是诈骗」也被当质疑模板。

**根因**：明确表态只在 CONFIRM 被当作闭环，NEED/OFFER 里全被算含糊。

**改法**：

- `_early_answer` 统一放在 `respond()` **所有阶段分支之前**（NEED 最前面的
  `flags["no"]`、CONFIRM 的含糊梯子都拦不住这些）。
- `_is_done_ack`：客户**不耐烦/明确结束**（`清楚了清楚了`、`知道了！！！`、
  `没有了！`、`别吵`）→ 发清单 + 直接回写收线，不再多问一句。
  平静的「好的，清楚了」「行，清楚了」**不收线**，留给赛题四段式④推进
  OFFER → CONFIRM（这是踩坑，见下）。
- `_is_what_auth` / `_is_material_choice` / `_is_scam_worry` 三个窄分支正面回答：
  什么授权 → 本单 `reject_reason` + 材料 + 清单已发；材料 → 只列材料不掺原因；
  诈骗质疑 → 官方性说明 + 热线 4006180092。
- 清单已发后客户再回「知道了 / 需要」→ 短版确认，两句轮换不复读。
- `persona._NO_TAIL_MARKS` 补「清单我已经发到 / 清单已经发到 / 不会要您转账」，
  防止刚说完"清单已发"又挂上「这一步您清楚怎么补吗？」。

## 三、19:48：`yes` 说了没反应，要求中英互切

截图里客户连说 `yes / ok / i am / no / hold on hold on`，客服一直在 GREETING
用中文重复确认公司。用户要求：一旦用外语就转成英语问答；说
`i can't understand english` 或改用中文就切回中文。

**改法（新增 `modules/i18n.py`）**：两段式，不另造一套英文状态机。

1. `i18n.detect()` 判会话语言；英文短句 `to_zh()` 归一成中文等价句
   （`yes/ok/i am → 是的`、`no → 不是`、`hold on → 稍等`、
   `what materials → 材料`），喂给现有中文意图识别与阶段逻辑。
2. `dialogue._localize()` 在出口把状态机算出的中文回复按
   `intent / stage` 换成 `EN_REPLIES / EN_BY_STAGE` 的英文话术播出；
   **只换播出文本**，stage / intent / tool_call / 回写字段全不变，
   英文客户走的是同一套合规流程。
3. 切回中文：句子里出现中文，或明确说 `i can't understand english`
   / `can you speak chinese` → `lang=zh` 并回「好的，那咱们改用中文说」；
   `can you speak english` → 纯英文承接。英文模式下跳过旧的
   `_is_foreign_lang`「只能讲普通话」分支。

**如实说明**：英文话术是我们对照中文官方口径写的英文表述，官方资料包只有中文；
公司名与材料名沿用商家后台中文名称，便于客户在后台逐项核对。
`detect` 目前把拉丁字母句子一律按英语处理，日/法/西等语种未覆盖。

## 六、遗留

- 英文模式只覆盖常见 intent，长英文自由提问走通用英文承接或专员回电；
  没有接翻译模型，也不做英文语音识别（ASR 层仍按中文链路）。
- 其他语种（日/法/西等）未识别，拉丁字母一律按英语处理。
- 材料名/公司名在英文句子里仍是中文，便于后台核对，不是翻译遗漏。
- 「清楚了」的收线判据仍是词表 + 语气，语义级识别要接意图模型。
- 语音模式（插话/回声）仍未在浏览器实测；rich 话术仍整句 TTS。
