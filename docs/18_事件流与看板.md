# 事件流与指标看板（M5）

> 归属：4 号 黄睿哲。涉及文件：`events.py`、`dashboard.py`、`web/dashboard.html`、
> `scripts/archive_events.py`。
> 相关契约：`contracts.EVENT_TYPES`（17 种事件）、`contracts.EVENT_VERSION`。

---

## 1. 为什么先做这一块

赛题要的三件事——转写、质检、时延——本质上是**同一份数据的三个视角**。
如果每一块各自记一份（语音模块记时延、质检模块记合规、看板再算一遍成本），
数据一定对不上，而且对不上时没人能说清是谁错了。

所以这里的做法是：**所有事都写成事件**，其它一切都从事件流派生。

| 想要什么 | 从哪来 | 不需要什么 |
|---|---|---|
| 转写文本 | `asr_result` + `agent_reply` 按 turn_id 串起来 | 不需要另存一份聊天记录 |
| 质检报告 | `agent_reply.payload.blocked` + `must_say` 命中 | 不需要质检自己记录 |
| 时延 P50/P95 | `turn_end` + `latency_report` 两个口径并列 | 不需要埋点日志 |
| 闭环率 | `writeback` 事件是否存在 | **不能**用阶段名推断 |
| 成本 | `turn_end.payload.est_cost_cny` 累加 | 不需要单独计费表 |

> 最后一行那种"某个字段看起来能推断，其实是两回事"的坑，`contracts.py` 里
> 专门留了注释（`CLOSED_STAGES` 被删掉的来龙去脉）。看板也守着同一条纪律。

## 2. 存储层做了什么（v2）

### 2.1 表结构与索引

```sql
CREATE TABLE events (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT    NOT NULL,
    turn_id    INTEGER NOT NULL DEFAULT 0,
    ts         INTEGER NOT NULL,          -- 毫秒
    type       TEXT    NOT NULL,
    payload    TEXT    NOT NULL DEFAULT '{}',
    latency_ms REAL    NOT NULL DEFAULT 0,
    version    TEXT    NOT NULL
);
```

四个索引，每个都有明确用途，没有"以防万一"的：

| 索引 | 用在 |
|---|---|
| `idx_events_session` | 前端事件链、质检读整通 |
| `idx_events_type` | 看板的事件类型分布、闭环率、错误数 |
| `idx_events_ts` | 看板的近 N 天趋势、归档的按时间筛 |
| `idx_events_session_turn` | 取某一轮的全链路 |

### 2.2 连接复用：线程局部 + 以路径为键

```python
_local = threading.local()          # thread_id -> {db_path: Connection}
```

三条理由，缺一条这个设计就不成立：

1. **不能全局单例**——`sqlite3` 默认 `check_same_thread=True`，而服务端
   `ThreadingHTTPServer` 每个请求一个线程，跨线程共用连接会直接抛错。
2. **不能每次开关**——写入是全项目调用最多的操作，每次 `connect/close`
   都是一次文件操作，QPS 一上来就变成磁盘瓶颈。
3. **必须以库路径为键**——`scripts/verify.py`、`run_eval.py`、`bench_voice.py`
   都会把 `events.DB_PATH` 指到临时库。若只按线程缓存，同一线程先后用到两个库
   时，事件会被写进上一个库——**测试会静默污染生产库**，这是最难查的一类 bug。

同时开了 `WAL`：读（看板聚合）与写（在线通话）不互斥。
`synchronous=NORMAL`：崩溃最多丢最后一个事务，省掉每次提交的 fsync。

> `close_connections()` 是给"要删除临时目录"的场景准备的。
> Windows 上打开的文件句柄会挡住删除，这个入口不能省。

### 2.3 写入校验

`write_event()` 在落库前校验事件类型是否在 `contracts.EVENT_TYPES` 里。
拼错就抛错，而不是静默写进去——因为静默写进去的后果是：质检和看板永远看不到它，
数据缺一块但没人报错。

## 3. 看板

打开方式（服务起在 8000）：

```
http://127.0.0.1:8000/dashboard
```

**为什么是独立页面而不是改 `index.html`**：`index.html` 是 1 号（张博涵）的
区域，通话页面的改动要跟着语音链路走；看板是 4 号的交付物，两者迭代节奏不同。
放在同一个文件里，两边每次改都要解决冲突，最后谁都不敢动。

### 3.1 页面分区

| 区块 | 内容 | 口径来源 |
|---|---|---|
| 顶部 KPI | 会话数、轮次、闭环率、首字 P50/P95、成本、打断、错误 | `events.aggregate()` |
| 时延 | 首字（T4−T0）与处理耗时并列 + 说明 | `events.metrics()` |
| 事件类型分布 | 17 种事件的数量条形图 | `events.aggregate()` |
| 近 30 天 | 每日事件量/会话数 | `events.aggregate()` |
| 最近通话 | 每通的轮次、是否闭环、最后环节、打断、错误、成本 | `dashboard._session_row()` |
| 质检汇总 | 检查了几通、失败项分布、均分 | `modules/eval.py`（3 号的口径） |
| 成本与事件库 | 今日成本、闸门状态、库体积/行数/索引 | `cost_guard` + `events.db_stats()` |

### 3.2 三条不许违反的显示纪律

1. **时延两套口径永远并列**。首字响应（浏览器实测）与服务端处理耗时回答的是
   两个问题，混着报就是编数据。看板上"打字轮首字"单独一行且标了"参考"。
2. **样本不足不出 P95**。样本 < 20 时 P95 等于最大值，会误导。看板显示 `—`，
   而不是拿 0 或最大值糊弄。
3. **质检未完成就明说**。`modules/eval.py` 自己返回 `is_placeholder=True`，
   看板顶部挂一条黄色提示条。**把占位实现显示成已完成，是最容易在答辩现场被问穿的地方。**

### 3.3 新增接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/dashboard` | 看板页面 |
| GET | `/api/dashboard/summary?days=7&limit=10` | 一次返回全部区块；`days` 省略=全部历史 |
| GET | `/api/cost` | 当天成本快照与闸门开关状态 |
| GET | `/api/scenes` | 场景清单与当前场景 |
| POST | `/api/scene` | 运行时切场景，**仅本机**（`{"name":"retail_recall"}`） |

`/api/dashboard/summary` 有 15 秒进程内缓存：看板每 10 秒轮询，
不缓存等于把"读整通事件"的压力叠到在线写入上。

## 4. 归档

事件表只会变大。归档不是清理，是分层：热数据留主库，冷数据进
`data/archive/events-YYYYMM.db`（同一张表结构，`ATTACH` 就能查）。

```bash
python scripts/archive_events.py                    # 预演，只报会搬多少（默认 30 天）
python scripts/archive_events.py --days 60 --yes    # 真搬，搬前自动备份主库
python scripts/archive_events.py --stats            # 只看库体检
python scripts/archive_events.py --days 30 --yes --vacuum   # 搬完顺手回收磁盘
```

默认 dry-run 是刻意的：归档不可逆（数据还在归档库，但跨库查询多一步，
运营同学未必知道）。

**归档完主库不会自动变小**——SQLite 删除行只标记空闲页。要回收磁盘得 `VACUUM`，
它会重写整个库，所以要显式加 `--vacuum`，并且脚本会先备份。

## 5. 怎么验证这一块是真的

```bash
python scripts/verify.py                 # 91 条行为断言，含事件写入校验、时延口径
python scripts/archive_events.py --stats # 应看到 4 个索引
python config_loader.py                  # 配置校验通过
```

跑一通电话后再看：

```bash
curl http://127.0.0.1:8000/api/metrics
curl "http://127.0.0.1:8000/api/dashboard/summary?limit=5"
```

**已知的口径陷阱**（docs/14 第 3 节也记了）：跑批与基准必须写临时库。
一旦跑批产物混进 `data/events.db`，首字 P50 会被 `scripts/run_eval.py`
的 0ms 样本拉到几十毫秒——看着漂亮，实际是假的。已经踩过一次
（305 个会话里 300 个是跑批产物），排查工具是 `scripts/clean_events.py`。
