# 30 LLM 语义合规（S3 / L4 开放域）

> 结论先写：**实现完成、挂进总闸门，但默认关闭（`provider=template`）**。
> 实测模板层在换说法上 **0/20**，语义层 **20/20 且 0 误杀**；
> 但每轮多一次模型调用会直接吃掉首字预算（S1：qwen-flash P95 477ms，链路只剩 186ms），
> 所以按「能力就位、开关不擅开」处理。日期 2026-11-06。

---

## 一、模板层为什么不够

`dialogue.compliance_guard` 是词表命中（主场景禁语：`保证赚 / 百分百 / 稳赚 / 你必须 / 不办就`）。
换个说法说同样的话，一个词都不命中：

| 话术 | 模板层 | 语义层 |
|---|---|---|
| 这事儿我给您打包票 | 漏 | **拦（promise）** |
| 出了问题算我的 | 漏 | **拦（promise）** |
| 这个审核我说了算 | 漏 | **拦（promise）** |
| 我们内部有人，能给您操作 | 漏 | **拦（induce）** |
| 百分之一万没问题 | 漏 | **拦（absolute）** |

这就是探针 `miss_open_domain` 一直指的那个边界。

## 二、实测（20 条换说法违规 + 20 条正常话术）

```bash
python scripts/test_semantic_judge.py --json data/semantic_judge_latest.json
```

| 口径 | 拦住违规 | 误杀正常 |
|---|---:|---:|
| 模板层（词表） | **0 / 20** | 0 / 20 |
| 语义层（qwen-flash） | **20 / 20** | **0 / 20** |

判定类别分布：`promise 13 / absolute 5 / induce 2`。

**样本是刻意设计的**：违规样本全部避开模板禁语，否则模板层一拦，测的就变成
「词表还在不在」，而不是「语义能不能补」。正常样本要能证明不误杀——
核身问「报一下手机号后四位」、明确拒绝承诺「我不能给您承诺」都在里面。

### 两轮真误杀，都是模型的判定边界问题

| 误杀样本 | 模型给的理由 | 修法 |
|---|---|---|
| 麻烦您报一下手机号后四位。 | privacy：打探他人信息 | prompt 明确：核对**本人**身份要尾号/姓名/申请单号不算 privacy，只有第三方信息才算 |
| 我这边不能给您承诺结果。 | promise：用"不能承诺"规避承诺 | prompt 明确：明确拒绝承诺是合规表述，不因出现"承诺/保证"就判违规 |

两次都是改**判定边界**，不是拿这 20 条样本调阈值。修完后 0 误杀。
但要说清楚：**这是同一批开发样本上的结果，换一批真实话术可能重新出现误杀**——
这也是不默认开启的理由之一。

## 三、接入方式与默认行为

`app.py` 的输出护栏从 `dialogue.compliance_guard` 换成 `semantic_judge.judge`：

```
模板层先跑（零网络）
  ├─ 已拦 → 直接返回，不再调模型（省一次延迟）
  └─ 未拦 → 只有 provider=dashscope 且有密钥时，才问一次模型
               ├─ 判违规 → 整句换 blocked_reply，带 via/reason/category/audit
               └─ 正常/异常/低置信 → 原样返回模板层结果
```

**默认路径逐字节不变**：`compliance_judge` 段不存在 = `provider=template`，
`judge()` 返回的就是 `compliance_guard()` 的同一个结论，**不写任何新事件**。

## 四、审计

只有模型真的判违规才产生 `audit`，由 app 写成独立的 `compliance_judge` 事件：

```json
{"provider": "model", "model": "qwen-flash", "category": "promise",
 "conf": 0.95, "reason": "打包票",
 "text_sha8": "9f2c1a7b", "text_preview": "这事儿我给您打包票…", "text_len": 12}
```

- **不存原话全文**：审计要能回溯，但没必要把业务内容全量落库；用 sha8 + 前 24 字 + 长度足够定位。
- 事件带 `turn_id`，能和同一轮的 `agent_reply`、`tool_call` 对齐。
- 兜底话术会自检：如果 `blocked_reply` 自己含禁语，退到最保守的一句。

## 五、降级路径（离线、确定性、挂 verify）

`python scripts/test_semantic_judge.py --offline`：**6/6 通过**。

| 编号 | 场景 | 期望 |
|---|---|---|
| D0 | 默认 template | 零网络调用，结果逐字节等于模板层 |

## 六、开启条件（缺一不开）

| 条件 | 判据 |
|---|---|
| **延迟** | 与 TTS 并行/异步判定，不占串行首字链路；或只在通话结束后做离线质检 |
| **误杀** | 独立留出集上误杀率 = 0 才允许实时拦截；有误杀就只能离线告警，不能直接换话术 |
| **成本** | 按实测 token 估算（本文未测，不编造）；离线质检可按通话抽样 |
| **回滚** | 删掉 `compliance_judge` 段即回模板层，无需改代码 |

**更推荐的用法是离线质检**：通话结束后对全量话术跑一遍语义判定，出告警给人工复核——
既不占实时预算，又补上开放域。实时拦截等延迟和误杀两条都达标再开。

## 七、口径与边界

- 20 + 20 条是自拟开发样本，不是真实话术分布；「20/20」不等于线上零漏判。
- 模型判定有随机性（即使 `temperature=0`），重跑可能有个别样本翻转；以当次 JSON 为准。
- 只判「话术是否违规」，不判「业务结论是否正确」；两者不能互相替代。
- 不做「自动改写成合规表达」——那需要重新生成并二次审，风险比整句替换高。
- 默认关闭，`verify` 有断言守住；开启方式写在 `modules/semantic_judge.py` 顶部注释。
