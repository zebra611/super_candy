# 赛题话术对齐：四段式、外呼名单、实体保护

> 2026-11-07。起因是评审/演示时看到开场白还是"我是京东客服中心的小采，请问是张先生本人吗？"，
> 以及"请问是贵公司的负责人吗？"，追问一句"我凭什么信任你"——问得对，那句话本身就有毛病。

## 一、赛题原文怎么说的

`赛题数据说明.docx`（官方资料包）写得很死：

> 一通合格的外呼是四段式：
> ① 自报身份 → ② **确认对方身份（"请问您是 XX 公司吗"，不能省，打错人是重大事故）**
> → ③ 说明驳回原因 + 整改动作（整通电话的胜负手）→ ④ 礼貌结束。

`驳回外呼QA.xlsx` 的 52 条话术、21 条剧本，开头格式全部是：

```
您好，我是京东商家资质审核专员，请问您是（商家公司名/店铺名）…吗？
```

注意三点：**带公司名**、**只有自报身份 + 确认身份**、**不提前说驳回**。

## 二、我们原来错在哪

| 环节 | 原来 | 为什么不行 |
|---|---|---|
| 开场白 | "……您提交的资质申请**没有通过审核**，给您来电说明一下原因……请问是**贵公司的负责人**吗？" | 顺序反了：③ 跑在 ② 前面。商家还没确认这通电话是找谁，就先被告知被驳回了。 |
| 公司名 | 空占位符，实际播出"贵公司" | 连是谁都不知道，商家无从判断凭什么信 |
| 打错人 | 照念驳回理由 | 赛题明说"打错人是重大事故" |

**根因不是话术写错，是架构缺了一环**：系统里根本没有"这通电话打给哪家"这个概念。
`query_application` 只在核身时按用户给的关键词盲查 120 份档案，所以填不出公司名。

## 三、改了什么

### 3.1 外呼名单（`tools.next_outbound_target`）

真实外呼是从名单打的，电话打给哪家系统本来就知道。
`modules/adapters/mock.py` 新增 `next_outbound_target()`：从 `config/mock/applications.csv`
里取第一条 `close_mode=电话` 且 `call_status=待外呼` 的申请单（当前 14 条待外呼、97 条电话关单）。

- `app.start_call()` 取这份名单，存进 `session["outbound_target"]`
- 只在**开了 `application_mode` 的场景**（POP 资审）才取——售后场景不碰申请单库（C5 场景隔离）
- 取不到不阻塞通话，降级成没有公司名的泛问
- 外呼目标记进已有的 `call_started` 事件，**不新造事件类型**（`contracts.EVENT_TYPES` 是封闭契约，
  临时造名字会被 `events.write_event` 直接拒掉——这正是它该有的行为）

### 3.2 开场白与占位符

```
GREETING.reply = 您好，我是京东商家资质审核专员，请问您是{company_name}的{contact_role}吗？
GREETING.reply_confirm_company = 麻烦您确认一下，您是{company_name}的{contact_role}吗？我这边有一笔资质申请需要跟您核实。
```

- `{company_name}` / `{contact_role}` 加入 `config_loader._ALLOWED_PLACEHOLDERS`
- 由 `dialogue._fill_outbound()` 填（**不走** `_fill_application`——后者填的是申请单业务字段）
- 实测播出：`您好，我是京东商家资质审核专员，请问您是北京市川上商贸有限责任公司的法定代表人吗？`

### 3.3 确认公司这一环（流程，不只是话术）

`dialogue._stage_greeting` 加了确认门：用户确认公司之前，**只回答问题 + 重复确认公司名**，
不进核身、不说驳回原因。

- 认了：提到公司名/店名/简称，或短句肯定（"是""对""嗯""我就是"）
- 否认：短句否定（"不是""不对""打错"）→ 立即收尾，走 `reply_deny`
  （"抱歉打扰您了，麻烦您转告贵公司负责人，我们会再联系，再见。"）
- 其它：先答问题（KB），再重复确认公司名

**长短句的差别是有意的**：长句里的"不是"多半是别的意思
（"不是我不想配合，是这个章我拿不到"），那种该继续谈而不是挂断。

确认之后才按赛题往下走：③ 说明驳回原因（`IDENTITY.reply_ok`）→ ④ 确认 → 回写 → 结束。

### 3.4 nlg 实体保护（第 7 道守卫）

**这是实测踩到的真缺陷**：骨架是"您是北京市川上商贸有限责任公司的法定代表人吗？"，
阿里云改写成"您是**这家**公司的法定代表人吗？"——公司名没了。

原来六道守卫（空串 / 超时 / 字数漂移 / 编造数字 / 断句 / 异常）**一道都没拦**，
因为它既没改长度也没改数字。但商家听不出这通电话是找谁的，赛题第②环又废了。

新增 `modules/nlg.py` 的 `_entities_ok()` + `_must_keep()`：
从外呼目标档案取 `company_name / company_short_name / shop_name / application_id /
brand_name / phone_tail`，**骨架里出现过的就必须在改写后仍然原样存在**，否则丢弃改写。

原则一句话：**改写可以换语气，不能换事实。**

## 四、验证

| 项 | 结果 |
|---|---|
| `verify.py` | **175/175**（新增 4 条：官方格式 / 真实公司名 / 确认前不核身 / 实体保护） |
| 双场景评测 | 售后 88/88 + pop 340/340 |
| 端到端实跑 | `scripts/e2e_full_call.py`，真 ASR/TTS，默认场景即赛题 |

新增断言在 verify 的"证据 28"段前，显式 `set_scene("pop_reject")` 跑、跑完切回——
不靠"主进程当前恰好是哪个场景"（前面几段证据会切场景，靠默认值等于绑在执行顺序上）。

## 五、还没做的

- **说话人分离**：仍分不清"接电话的是不是本人"，只能核到"信息对得上"。
  赛题第②环现在做到的是"确认公司 + 核对申请单信息"，不是"确认本人"。
- **外呼名单是静态的**：`call_status` 不会随通话真的改成"已接通/拒绝"，
  每次 `start_call()` 取的都是同一条第一条待外呼档案。接上真实外呼系统后由对方给状态。
- **nlg 默认关闭**（`provider=template`）。开了有第 7 道守卫兜底，但每轮多一次云端往返、
  受账号配额影响，首字会慢 300~600ms——这个取舍见 `docs/20` 的技术选型表。
