## 2. 实测发现的缺陷（按严重度排序）

### 缺陷 1：含糊回答直接挂断，二次追问是死代码 ★最严重体验问题　【已修复 2026-11-03】

**证据**（探针 A）：用户说"嗯……"→ `stage CONFIRM→DONE`，`intent=declined`，回复是"那就不打扰您了，已经帮您记录下这个结果"。

**根因**：`dialogue.py` 的 `_stage_confirm` 里：

```python
session["confirm_asks"] += 1
if session["confirm_asks"] >= 1:     # 恒真
    ... unknown, 回写
return _reply(... reply_again ...)   # 永远走不到
```

`>= 1` 使得第一次含糊就命中，`reply_again`（"您可以简单回我一句同意或者不需要"）**从未被播过**。这与 `docs/02` 和 `config` 的 `_todo` 都矛盾。

**影响**：用户只是犹豫，客服直接说"不打扰了"挂断——既丢单，又会让"交互质量"扣分。

---

### 缺陷 2：P50 用的是服务端处理耗时，不是首字响应 ★会误导汇报　【已修复 2026-11-03】

**证据**（探针 C）：9 轮文字对话的 `metrics` 返回 `p50_ms=21.2`。

**根因**：`events.metrics()` 取 `turn_end.latency_ms`，而它是"收到请求到返回回复"的耗时，**不含用户说话时长，也不含声音播出来**。

**影响**：线上演示面板会显示 21ms，离 `docs/04` 定义的 `T4−T0`（目标 1400ms）差两个数量级。若拿它填"首字响应"，现场一问就露。**这是自欺型错误，不是技术缺陷。**

---

### 缺陷 3：用户沉默被当成说了一句话 ★真实外呼场景高频　【已修复 2026-11-03】

**证据**（探针 G）：`handle_turn(sid, user_text="")` 后，事件链是 `turn_start → vad_result → asr_result → agent_reply → tts_start → turn_end`，`asr_result.text = "（空输入）"`，状态机从 GREETING 推进到 IDENTITY。

**根因**：`app.py` 里 `heard = (user_text or "").strip() or "（空输入）"` —— 空输入被替换成一个非空字符串，于是 `dialogue.respond` 认为用户说了话。`dialogue._handle_empty()` **是死代码，永远不会被调用**。

**影响**：外呼里"无人应答/沉默"极其常见。现在系统会对沉默继续推进流程、自说自话，且事件库里没有任何"用户没说话"的记录，无法统计静默挂断率。

---

### 缺陷 4：`fake` 字段硬编码为 True ★会让评测永远过滤掉真数据　【已修复 2026-11-03】

**证据**（探针 I）：文字轮 `asr_result.payload = {"text": "（空输入）", "latency_ms": 0.0, "fake": true}`。

**根因**：`app.py` 写事件时字面量 `"fake": True`，不是从 `voice.asr()` 返回值取。

**影响**：角色 1 接上真 ASR 后，若不记得改这一行，评测会按 `docs/03` 的规则把它们全过滤掉——"明明接了真识别，分数还是 0"。而且文字输入根本没过 ASR，标 `fake` 语义也不对。

---

### 缺陷 5：拒绝后改口，第二次回写不生效 ★直接对应已知缺口 C02　【已修复 2026-11-03】

**证据**（探针 B）：拒绝 → 工单 `TD3D63B0D`、`consent=False`；随后说"算了，我还是同意吧" → 阶段停在 DONE、`tool_result=None`、`writeback` 事件仍只有 1 条、工单内容仍是 `consent=False`。

**根因**有两个，叠在一起：

1. `DONE` 是终态，`_stage_done` 只回结束语，**不再处理任何输入**；
2. 幂等键固定为 `session_id:WRITEBACK`，即使能再次回写，也会命中旧工单，内容不更新。

**影响**：用户改口是真实场景，业务侧会收到错误结论（"客户拒绝"），而实际客户最后同意了。

---

### 缺陷 6：禁语被替换成 `***` 后照样念出来 ★合规风险　【已修复 2026-11-03】

**证据**（探针 F）：`"我保证您百分百赚钱，不办就没名额了"` → `"我保证您***赚钱，***没名额了"`，`blocked=True`。

**根因**：`dialogue.compliance_guard()` 用 `replace(w, "***")` 打码，返回值仍被送进 TTS。

**影响**：TTS 会念出"星星星星"之类的怪音；而且打码后的句子语义仍带诱导性（"我保证您\*\*\*赚钱"），等于既没合规也没通顺。`docs/02` 早就写了"要重新生成，不是打码"，代码没跟上。

---

### 缺陷 7：事件库与接口都含个人身份信息，且无鉴权 ★合规红线　【已修复 2026-11-03】

**证据**（探针 D、E）：

- `asr_result.text` 存了用户原话 `"是我，尾号8866"`，尾号明文入库；
- `/api/turn` 返回的 `slots` 含 `customer`（姓名、手机尾号、等级）与 `order`（单号、金额）；
- `compliance_report("s_does_not_exist")` 不报错，说明接口不校验会话归属，任何 `session_id` 都能查。

**影响**：线上那个链接是**公开的**，任何人拿到链接 + 一个 session_id 就能读到姓名与尾号。现在库里是假数据无所谓，**一旦接真实名单，这就是泄露**。这条必须在接真数据前解决。

---

### 缺陷 8：`must_say` 定义了却没人用　【已修复 2026-11-03】

**证据**：`config/scene.json` 每个阶段都有 `must_say`，`modules/eval.py` 的 `must_say_hit` 恒返回 `skipped`。

**影响**：赛题把"必说话术"列为合规检查项，现在完全没检测。刘源开工第一件事就得补。

---

### 缺陷 9：内存与并发都没有边界　【已修复 2026-11-03】

**证据**（探针 H）：`_SESSIONS` 只增不减，只有 `end_call` 才 pop；无 TTL、无上限。同一 session 并发调用时，`_LOCK` 只保护 `dialogue.respond`，事件写入顺序仍可能交叉。

**影响**：浏览器关页面不挂断 → 会话永久残留；压测时内存与事件顺序都会出问题。

## 4. 必须你拍板的 6 件事（P0，决定代码怎么写）

> **已拍板（2026-11-03）**：P0-1 双口径并列、P0-2 幂等键加版本、P0-3 加 `no_answer` 事件、P0-5 加只读 token。
> P0-4（含糊要追问）与 P0-6（WS 与 HTTP 并存）按建议执行，随时可推翻。

### P0-1　首字时延用哪套口径？

- **A**：保留 `total_ms` 当"处理耗时"，另加 `first_audio_ms`（T4−T0）作为门槛指标，面板两个都显示
- **B**：直接把 `total_ms` 改成 T4−T0（会立刻从 21ms 变成 1200ms 左右，看起来"变差了"）
- **C**：暂时不改，等官方口径

**建议 A**。理由：两个数字回答两个问题——"服务器快不快"和"用户等多久"。只报后者会把服务器问题掩盖掉，只报前者是自欺。**这条决定面板、评测、答辩口径，必须先定。**

### P0-2　用户改口（DONE 之后又同意）怎么处理？

- **A**：新增 `REOPEN` 状态，允许从 DONE 回到 CONFIRM，并做二次回写（**要改 `contracts.STAGES`，禁改区**）
- **B**：不改契约，改成"回写前如果收到改口信号，把幂等键加版本号重写一次"
- **C**：接受现状，但把 C02 记为已知缺口，答辩时主动说明

**建议 B**（短期）+**A**（若时间允许）。理由：`REOPEN` 更正确，但会牵动状态机、合规、评测三处；B 能在不动契约的前提下把"改口能纠正"做出来，代价是要接受"DONE 后再改口"仍不处理。

### P0-3　用户沉默怎么算？

- **A**：新增 `no_answer` 事件 + 沉默两次自动挂断（要改 `EVENT_TYPES`）
- **B**：不加事件类型，用 `vad_result.ended=false` + `asr_result` 空文本表达
- **C**：保持现状（沉默当一句话）

**建议 A**。理由：静默挂断率是外呼的核心业务指标，必须能统计；这属于"只追加事件类型"，符合契约扩展规则。

### P0-4　含糊回答要不要二次追问？

- **A**：要，追问一次，仍含糊才记 unknown（符合 `docs/02` 与 `config._todo`）
- **B**：不要，第一次含糊就记 unknown（当前行为）

**建议 A**。理由：直接说"不打扰了"是明显的体验缺陷，而且会让"用户犹豫"被误判成"拒绝"，业务结论错。

### P0-5　公开链接的隐私怎么办？

- **A**：接口加一个只读 token（`?token=`），无 token 只能看首页
- **B**：只保留最近 2 小时事件，老数据自动清
- **C**：接真实名单前把线上链接下线，演示只用本地

**建议 A + C 组合**。理由：A 解决"别人拿到 session_id 就能查"，C 解决"真实数据不该在公网"。现在库里是假数据，可以先做 A；等企业资料包到了，按 C 下线。

### P0-6　WebSocket 接入后，HTTP 接口留不留？

- **A**：并存，`/api/turn` 保留（文本调试、评测跑批都靠它，不能删）
- **B**：WS 上线后废弃 HTTP（评测脚本要改造）

**建议 A**。理由：`run_eval.py` 是纯文本驱动的，删了 HTTP 等于把评测体系一起改，得不偿失。

1. **开场白从来没被播过**。用户第一句就报尾号时，客服直接从"核对上了"开始，自报身份整段跳过——`start_call()` 现在写入开场 `agent_reply`（`turn_id=0`），外呼由客服先开口。
2. **回写那句话的阶段记错了**。回写是从 CONFIRM 直接跳到 DONE，事件的 `stage` 记成 CONFIRM，导致"回写环节有没有说'登记'"查不到。现在用 `stage_label="WRITEBACK"` 显式标注。
3. **`_comment` 被写进工单**。`writeback_template()` 原样返回，业务单据里多出一个 `"_comment"` 字段；现在过滤掉所有 `_` 开头的键。

**回归结果**：`verify.py` 22/22 通过；`run_eval.py` 30/30 通过、闭环 11/30（原 9/30，C01/C02 由缺口转为通过）；HTTP 层 13 项检查全过（含无 token 403、错 token 403、未知会话 400、首字上报 200）。

**还没做的**（不是遗漏，是排期）：流式识别与合成、真 VAD、打断、WebSocket/WebRTC、
语义级合规、Mock 适配器、RSI 自进化。这些在 `README` 的「还没做的」一节里逐条列着。

## 9. 修复记录（2026-11-04）：接入云端合成 + 三个实测缺陷

### 9.1 接入 `qwen3-tts-flash`（音色 Serena）

此前 `tts_ms` 恒为 0，声音是浏览器 `speechSynthesis` 念的，**首字口径里根本没算合成时间**，
所以那个"818ms 首字"是虚高的。现在服务端真合成、返回 OSS 链接、前端 `<audio>` 播。

接入过程中踩到两个坑，都已修：

- **OSS 返回 `http://` 链接**，而页面是 https，浏览器按"混合内容"直接拦掉播放。
  表现是"接口 200、合成成功、就是一点声没有"。现在统一改写成 https。
- **`voice` 与 `voice_name` 混用**：前者是浏览器音色名（`zh-CN-XiaoxiaoNeural`），
  后者是云端音色 ID（`Serena`）。混着用会静默无声，排查时还会被日志误导。

### 9.2 三个真缺陷（都是实测暴露，不是推测）

| # | 缺陷 | 根因 | 修法 |
|---|---|---|---|
| 1 | 事件面板上 `latency_report` 全部显示 "turn 0" | `write_event` 时 `turn_id` 只写进了 payload，没落到事件列 | 传 `turn_id` 参数；加断言防回归 |
| 2 | 开场白永远是浏览器机械音，后续句子是真声音 | `start_call` 里 `voice.tts(opening)` 的返回值只写进 `tts_start` 事件就丢弃，没跟响应返回 | 返回 `opening_tts`；前端优先播它 |
| 3 | **重试从未生效** | 对端收下请求却不给响应就断开，抛 `http.client.RemoteDisconnected`，它既不是 `HTTPError` 也不是 `URLError`，异常直接逃到最外层回落 | 两处都补 `(http.client.HTTPException, ConnectionError)`；重试间隔 0.15s |

第 3 条最隐蔽：识别和合成各写了一份"重试两次"的循环，**两份都是摆设**，
因为真正会发生的异常类型根本没被捕获。发现过程是起服务实测，拿到第一条真实故障
`error = "Remote end closed connection without response"` 才顺藤摸瓜。

**反向验证**：把补上的那支 `except` 去掉，断言立刻 FAIL（请求次数从 2 退化成 1）。
不这么做，无法区分"测试通过"和"测试根本没测到"。

### 9.3 复查中顺手补的

- **`write_event` 加契约校验**：事件名不在 `contracts.EVENT_TYPES` 里直接抛 `ValueError`。
  以前拼错（如 `turn_ended`）能静默入库，事件链缺一环却无人报错。
- **`run_eval.py` 加离线隔离**：接 TTS 之后跑批会给 30 条用例各合成一次，
  白等 36 秒还要花钱，没有密钥的队友直接卡死。现在跑批不调云端。
- **文档 6 处过时描述**：`docs/07`（TTS 占位）、`docs/13`（22 条断言 → 42 条）、
  `docs/14`（"现在还是假的"整表重写）、`docs/15`（TTS 从"待接"改为"已完成"）。
- **删除 5 处死代码**：`config_loader.stages_order`、`voice.pcm_to_samples`、
  `voice.detect_barge_in`（空壳，半双工架构下不可能被调用）、`eval.run_batch`（无入口）、
  `verify.run_turns`。

**回归结果**：`verify.py` 42/42 通过（新增 10 条）；`run_eval.py` 30/30、闭环 11/30。

### 9.4 复查结论里必须说清楚的一件事

**首字响应没有余量了。** ASR 约 0.6s + TTS 约 1.1s ≈ 1.7s，加网络往返落在 1.8–1.95s，
门槛是 2000ms。之前看起来"轻松过门槛"是因为根本没算合成时间。

要留余量只有两条路：**流式合成**（首包就下发，SSE）或**话术切短句、第一句先合成先播**。
在解决之前，任何"首字 P50 远低于门槛"的说法都不成立。
