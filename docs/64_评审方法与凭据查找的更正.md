# 64 · 一次 PR 评审的两处方法论错误（2026-11-14）

## 缘起

11-13 审 `super_candy` 的 #49/#50/#51 时，我下了两个结论：

1. 「没有 GitHub token，关不了 PR，只能靠 git ref 审」；
2. 「三条 PR 标题都缩水，作者把大改动藏在小标题里，评审容易被骗」。

11-14 用户回了一句「全部是，而且你应该有 github token」。凭据一查就在，
而且拿到 API 后发现 **PR 标题本来就写得清清楚楚**。两个结论都错了。
这篇只记方法，不记业务——业务结论（#51 = TTS 修复 + 话术重写两块、拆分合理）
经核对仍然成立。

## 错误一：查 git 凭据先扫环境变量

**当时做的**：`env | grep -iE "github|gh_|token"`，再猜 `~/.config/gh/hosts.yml`
等几个路径，全空 → 断言「环境里没有 token」。

**实际**：`git config --get-regexp 'credential.*'` 显示 `credential.helper=manager`，
凭据存在 **Windows 凭据管理器**里。正确取法：

```bash
printf 'protocol=https\nhost=github.com\n\n' | git credential fill
# → username=zebra611 / password=<40 字符 PAT>
```

git 的凭据由 credential helper 管理，**不进进程环境变量**。能 `git push` 的机器，
就一定能通过 `git credential fill` 拿到同一把凭据。先扫环境变量是找错了地方，
而且「我 push 成功过」和「我说没有 token」当时就是自相矛盾的，没察觉。

**连带影响**：因为认定没有 token，我没走 API，改用 `refs/pull/*/head` 审 PR，
直接导致下面第二个错误。

## 错误二：把 commit subject 当 PR title，还据此推断作者动机

为了在没有 API 的情况下"看到标题"，我用 `git log -1 --format=%s refs/remotes/pr/N`
把**最新提交的 subject** 当标题代理。两处硬伤：

| 我以为的 | 实际 |
|---|---|
| `refs/pull/*/head` 列的是 open PR | 它保留**所有历史 PR**（含已关闭/已合并），当时 51 个 ref ≠ 51 个 open PR。API 显示实际 open 只有个位数 |
| head commit subject ≈ PR 标题 | 两者独立存储。PR 标题可以改写、可以覆盖多次提交，只有 `GET /repos/.../pulls/N` 能拿到 |

拿到 API 后的真标题：

| PR | 我用的代理（commit subject） | 真 PR 标题 |
|---|---|---|
| #49 | `fix(cost): snapshot() 补 note 字段…` | `fix(4号): P95 假绿、演示库、幂等库清理、C5 对端存 content` |
| #50 | `feat(ui): 补料清单常驻——把「等 N 项」展开…` | `feat(ui): 补料清单常驻在右栏——逐条列全，数据全部来自档案` |
| #51 | `fix(tts): 换声只换了一半…` | `fix(tone+tts): 语气与复述收敛；换声融进三个场景包与试听工具` |

#51 的真标题**明写了「语气与复述收敛」**，#49 明写了「演示库」。所谓"标题藏了改动"
根本不存在。我却据此反复写「别被标题骗过」「团队 PR 命名习惯值得提一句」，
还在交付里把它当成一条审查发现——这是**凭代理数据推断作者动机**，越界了。

**范围界定**（重要）：`git rev-parse pr/49 = 0909ea2`、`pr/51 = a8ad683` 与 API 的
`head.sha` 完全一致，所以我看的 diff 是最新的、没审错版本；#51 确实捆了 TTS 修复和
话术重写两件事，拆成两条分支也确实让评审粒度更清楚。**错的只是"作者藏了"这个动机判断，
以及"51 个 open PR"这个数量**。合并内容不受影响。

## 一条纪律

> 用代理数据时，结论只能覆盖代理能证明的范围。

commit subject 能证明「这条提交写了什么」，证明不了「PR 标题写了什么」；
从后者推出的"作者有没有藏东西"更是两层之外。当时该做的是明确标注
「以下是 head 提交主题，**不是** PR 标题，标题待核」，而不是拿它下判断。

同类坑：`git log` 主题 ≠ PR 标题 ≠ issue 标题 ≠ 分支名；`refs/pull/*` ≠ open 列表。

## 补救与验证

- 用 `git credential fill` 取凭据 → `GET /user` 确认身份 zebra611 → 逐条核 PR 状态；
- `PATCH /pulls/51 {"state":"closed"}` 前先留说明评论，公开更正误判；
  #49/#50 因 head 进 main 已被 GitHub 自动标记 merged，**open PR 归 0**；
- README 变更日志、docs/63「没有上线」、本文同步更正；
- 四条合并后 `verify 276/276`（271 + #49 新增 5 条），L2 v58 / 性格 p14 两条 doctor 全绿；
- 重新发布覆盖同一链接，线上 `/api/health`、`/api/scenes`、`?db=demo` 均 200。

**教训一句话**：`git push` 能成功，就说明凭据在 git 手里；审 PR 先看 API 真值，
别用 `git log` 的副产品给人扣帽子。
