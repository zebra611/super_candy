# 事件契约（K0 契约之二）

> 唯一来源：`contracts.EVENT_FIELDS`、`contracts.EVENT_TYPES`；落库实现在 `events.py`。
> 本文档定义**每个事件里装什么**，因为代码只能约束"有哪几个字段"，约束不了 payload 里该放什么。

---

## 1. 为什么值得为它单独写一份文档

事件流是全项目的地基：合规质检、时延统计、失败归因、评测复现、进化前后对比，全都从这一张表读。

它也是最容易失控的地方——十五种事件、五个角色在写、字段随手加。一旦有人把关键信息塞进一句 `note` 字符串里，后面所有分析都得靠正则去捞。

**规则：能被分析的必须是字段，不能是句子。**

---

## 2. 通用字段（每条事件都有，不许增删）

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | string | 一次通话的唯一标识，格式 `s_` + 12 位 hex |
| `turn_id` | int | 第几轮，从 1 开始；通话级事件（`call_started` / `call_ended`）填 0 |
| `ts` | int | 毫秒时间戳，**服务端时间**，统一用 `events.now_ms()` 取 |
| `type` | string | 必须取自 `EVENT_TYPES`，写错不报错但质检会漏 |
| `payload` | object | 事件内容，见第 3 节 |
| `latency_ms` | float | 该环节耗时；没有耗时概念填 0 |
| `version` | string | 写入时的协议版本，当前 `v1` |

**时间口径**：所有 `ts` 都是服务端时间，不使用客户端时间（客户端时钟不可信，且时延统计会被污染）。

---

## 3. 各事件的 payload 定义

约定：**必填**字段缺失即视为缺陷；**选填**字段允许为空或缺席。

### 3.1 `call_started` — 通话建立

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `scene` | string | 必填 | 场景名，来自 `config/scene.json` 的 `scene_name` |

`latency_ms`：0。写入者：`app.py`。消费者：统计通话量、区分场景。

### 3.2 `turn_start` — 一轮开始

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `audio_bytes` | int | 必填 | 本轮上传音频字节数，文字模式填 0 |
| `text_input` | bool | 必填 | 是否是打字输入（用于区分语音/文字两条路径） |

`latency_ms`：0。写入者：`app.py`。消费者：判断本轮是否走了语音路径。

### 3.3 `vad_result` — 端点检测

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `started` | bool | 必填 | 检测到语音开始 |
| `ended` | bool | 必填 | 检测到语音结束 |
| `speech_ms` | int | 必填 | 有效语音时长（毫秒） |

`latency_ms`：VAD 判定耗时。写入者：角色 1。消费者：**VAD 准确度打分**（评分维度 1 明确提到）。

### 3.4 `asr_result` — 识别结果

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `text` | string | 必填 | 识别出的最终文本 |
| `latency_ms` | float | 必填 | 本段识别耗时（与事件级 `latency_ms` 保持一致） |
| `confidence` | float | 选填 | 置信度 0–1，没有就省略 |
| `fake` | bool | 必填 | 是否是占位结果。**由识别实现自己声明，不在 app.py 里硬编码** |
| `source` | string | 必填 | `asr`（真语音识别）/ `text`（打字调试）。文字输入不是识别结果，故 `fake=false` |

`latency_ms`：识别耗时。写入者：角色 1。消费者：时延拆解、转写重建、评测。

> **`fake` 字段的意义**：防止把假数据算进真实分数。角色 3 的评测流水线要用它过滤，否则第一版基线分毫无意义。
>
> **注意**：`fake` 必须由 `voice.asr()` 的返回值决定。早期版本在 `app.py` 里写死 `true`，接上真 ASR 后若不改这一行，评测会把真数据全部过滤掉，表现是"明明接了真识别，分数还是 0"。
>
> **文字输入不写 `vad_result`**。打字没有端点检测这回事，混进去会污染 VAD 准确度统计。

### 3.5 `agent_reply` — 编排产出回复

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `text` | string | 必填 | 最终要播报的文本（已过合规护栏） |
| `stage` | string | 必填 | 回复归属的阶段（取自 `STAGES`） |
| `next_stage` | string | 必填 | 回复之后推进到的阶段 |
| `blocked` | bool | 必填 | 是否被合规护栏拦截/改写 |
| `hits` | string[] | 必填 | 命中的禁语列表，无命中填空数组 |
| `replaced` | bool | 必填 | 是否发生了**整句替换**（命中禁语时为 true，此时 `text` 是合规话术而非打码原文） |
| `intent` | string | 必填 | 识别出的意图（`yes`/`no`/`ambiguous`/`opening`/`error` 等），便于统计"哪类意图最难处理" |
| `source` | string | 必填 | 这一轮输入的来源：`asr` / `text` / `silence` / `budget`；`opening` 表示开场白（`turn_id=0`） |

`latency_ms`：编排耗时（意图 + 生成）。写入者：角色 2。消费者：阶段覆盖率统计、合规报告、转写重建。

> **开场白也是一条 `agent_reply`**（`turn_id=0`，`intent="opening"`）：外呼由客服先开口，自报身份是六环节第一环。不记下来的话，"必说话术有没有说到"这项检查会漏掉开场。

### 3.6 `tool_call` — 发起工具调用

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | 必填 | 工具名，必须是 `TOOL_SCHEMAS` 里的键 |
| `args` | object | 必填 | 调用参数，结构按 `TOOL_SCHEMAS[name].params` |

`latency_ms`：0（耗时记在 `tool_result`）。写入者：角色 2/4。消费者：工具调用正确率、调用链复盘。

### 3.7 `tool_result` — 工具返回

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `found` | bool | 视工具 | 查询类工具是否有结果 |
| `customer` / `order` | object | 视工具 | 查询结果 |
| `ticket_id` | string | 视工具 | 工单号（`create_ticket` 才有） |
| `created` | bool | 视工具 | 是否**新建了工单**；false 表示命中幂等或更新了已有工单 |
| `updated` | bool | 视工具 | 是否**更新了已有工单**（用户改口时 true）；`created=false` + `updated=false` 才是纯幂等命中 |
| `version` | int | 视工具 | 第几次回写，从 1 开始；改口递增 |
| `error` | string | 视工具 | 错误码，如 `UNKNOWN_TOOL`、`TOOL_FAILED` |

`latency_ms`：工具耗时。写入者：角色 4。消费者：工具正确率、异常归因。

> **`created` / `updated` 要分开**：只报 `created=false` 会把"用户改口更正了结论"和"重复调用被幂等挡住"混成一件事，而这两件事的业务含义完全相反。

### 3.8 `writeback` — 结构化回写成功

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `ticket_id` | string | 必填 | 工单号 |
| `created` | bool | 必填 | true 新建 / false 未新建（幂等命中或更新） |
| `updated` | bool | 必填 | 是否是改口后的更正（同一张工单，内容被更新） |
| `version` | int | 必填 | 第几次回写；同一通电话多次回写时按此排序 |
| `retried` | bool | 必填 | 是否经历过一次失败重试（幂等键不变，所以重试不会重复建单） |

`latency_ms`：0。写入者：`app.py`。消费者：**任务闭环率的唯一依据**——没有这条事件就等于没闭环。

> **回写可以有多条**：用户改口会出现第二条 `writeback`（`version=2`，`updated=true`，`ticket_id` 不变）。统计闭环率要按 `session_id` 去重，不能数事件条数。

### 3.9 `tts_start` — 开始播报

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `mode` | string | 必填 | `browser`（前端自带 TTS）/ `server`（服务端合成） |
| `text` | string | 必填 | 播报文本 |
| `voice` | string | 选填 | 音色标识，来自 `config.tts.voice` |
| `rate` | float | 选填 | 语速，来自 `config.tts.rate` |
| `latency_ms` | float | 必填 | 首包耗时；`browser` 模式填 0 |

`latency_ms`：TTS 首包耗时。写入者：角色 1。消费者：时延拆解。

### 3.10 `barge_in` — 用户打断（v2 待实现）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `at_ms` | int | 必填 | 在本次播报开始后的第几毫秒被打断 |
| `cancelled_text` | string | 选填 | 被打断时已播出的文本片段 |

`latency_ms`：从用户开口到停止播报的响应耗时。写入者：角色 1。消费者：**打断响应指标**。

### 3.11 `turn_end` — 一轮结束

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `stage` | string | 必填 | 本轮结束时所处阶段 |
| `closed` | bool | 必填 | 此时是否已闭环 |
| `source` | string | 必填 | 本轮输入来源：`asr` / `text` / `silence` / `budget` |
| `processing_ms` | float | 必填 | **口径 A 处理耗时**：请求到达 → 回复文本就绪 |
| `server_first_audio_ms` | float | 必填 | **服务端下界**：请求到达 → 首包就绪；不含网络回程与浏览器起播 |
| `asr_ms` / `llm_ms` / `tts_ms` | float | 必填 | 分段耗时，用于定位瓶颈 |
| `est_cost_cny` | float | 必填 | 本轮估算成本（元），按 `config.budget` 单价折算，仅用于告警 |

`latency_ms`：与 `processing_ms` 相同（保留该列是为了让所有事件都有统一字段）。写入者：`app.py`。消费者：时延指标、成本看板。

> **`turn_end` 里的两个数都不是门槛口径**。真正的首字响应 `T4−T0` 由浏览器上报，落在 `latency_report`。三者关系见 `docs/04` 第 5 节。

### 3.12 `call_ended` — 通话结束

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `closed` | bool | 必填 | 整通电话是否闭环 |
| `est_cost_cny` | float | 选填 | 这通电话的估算总成本 |

`latency_ms`：0。写入者：`app.py`。消费者：通话量、闭环率、成本。

### 3.13 `no_answer` — 用户这一轮没说话（v1 新增）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `reason` | string | 必填 | 目前只有 `empty_input`（既无音频也无文字）；将来可扩 `asr_empty`（有声音但没识别出字） |
| `stage` | string | 必填 | 沉默发生时处于哪个阶段 |

`latency_ms`：0。写入者：`app.py`。消费者：**静默挂断率**（外呼的核心业务指标之一）。

> **为什么单独记一条**：用户不说话在外呼里极常见，它既不是"识别失败"也不是"用户拒绝"。混进 `asr_result` 会让人分不清"没听到"和"没听懂"。
>
> **这一轮不写 `asr_result`**：没有任何识别结果，硬造一个 `"（空输入）"` 会让状态机误以为用户说了话。早期版本就是这么错的，导致沉默时系统继续自说自话。

### 3.14 `latency_report` — 浏览器实测的首字响应（v1 新增）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `turn_id` | int | 必填 | 对应哪一轮（前端回传，不是事件级的 `turn_id`，两者应一致） |
| `first_audio_ms` | float | 必填 | **T4 − T0**：用户说完/点发送 → 听到第一帧声音 |
| `estimate` | bool | 必填 | 是否估算值（浏览器没触发 `onstart` 时的兜底计时） |

`latency_ms`：0（数值在 payload 里，避免与"该事件自身耗时"混淆）。写入者：`web/index.html` 通过 `POST /api/turn/metric` 上报。消费者：**首字响应门槛指标**。

> **为什么必须由前端上报**：只有浏览器知道自己什么时候真的出声。服务端能测的只是"请求到达 → 首包就绪"，那是一个下界。
>
> **不做时钟换算**：前端传的是 `performance.now()` 相减得到的时间差，不是绝对时间戳，所以客户端时钟不准也不会算出负数。

### 3.15 `error` — 某个环节出错（v1 新增）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `code` | string | 必填 | 错误码：`DIALOGUE_FAILED` / `TOOL_FAILED` / `BUDGET_MAX_TURNS` / `BUDGET_MAX_CALL_SECONDS` |
| `stage` | string | 选填 | 出错时处于哪个阶段 |
| `detail` | string | 选填 | 异常信息（截断到 200 字符），只用于排障 |
| `tool` | string | 选填 | 出错的是哪个工具 |

`latency_ms`：0。写入者：`app.py`。消费者：**异常率统计**、失败归因（角色 3）。

> **原则：单轮出错不打断通话**。记一条 `error`，给一句兜底话术，让流程停在原环节继续。
> 外呼里中途崩掉、用户听到静音，比说错一句话严重得多。

## 5. 扩展规则（四个人都要遵守）

1. **加字段**：直接在 payload 里加，选填即可，不需要改版本号。但要在这里补一行说明。
2. **改名 / 改语义**：必须升 `EVENT_VERSION`，并在本文档写迁移说明，通知全员。
3. **新增事件类型**：往 `EVENT_TYPES` 里追加，同时在本文档补一节 payload 定义。
4. **不许把可分析的信息塞进自由文本**。要记"为什么失败"，用 `error_code` 字段，不要写在 `note` 里。
5. **`fake` 标记必须如实填**。任何占位/模拟产生的数据都要标 `fake: true`，否则评测基线会被污染。

## 6. 消费者对照表

| 谁 | 读哪些事件 | 用来干什么 |
|---|---|---|
| 角色 1 | `vad_result`、`barge_in`、`tts_start`、`latency_report` | 调时延与打断 |
| 角色 2 | `asr_result`、`tool_result`、`agent_reply` | 复盘对话走向、改意图规则 |
| 角色 3 | 全部（尤其 `error`、`writeback`） | 质检、评测、归因 |
| 角色 4 | `turn_end`、`writeback`、`call_ended` | 看板、指标、成本 |

**没有人可以直接改别人写入的事件**，要加信息就加新字段。
