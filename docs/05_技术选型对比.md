# 技术选型对比（供四人统一口径）

> 目的：三个人各自选型会打架，接口对不上、成本算不清、答辩说不圆。
> 原则：**每一层都留一个适配层，选型可替换**。不要把供应商的 SDK 直接写进业务代码。

---

## 1. 选型评分维度与权重

| 维度 | 权重 | 为什么这么定 |
|---|---|---|
| 首包延迟 | 0.4 | 2 秒门槛是硬指标，权重最高 |
| 成本 | 0.2 | 「费用自理」，且评分维度 5 明确要"成本控制" |
| 准确率/自然度 | 0.2 | 直接决定维度 1 与维度 2 的分数 |
| 接入难度 | 0.1 | 四人队伍的工时是最稀缺资源 |
| 合规与可控性 | 0.1 | 涉及个人信息与大模型备案要求 |

---

## 2. ASR（语音识别）

| 方案 | 首包延迟 | 成本 | 准确率 | 接入难度 | 备注 |
|---|---|---|---|---|---|
| **云 ASR 流式**（阿里/腾讯/讯飞） | 好（200–400ms 出中间结果） | 按小时计费，小额可控 | 好，带热词 | 低，SDK 成熟 | 需要账号与实名，数据出本地 |
| **FunASR 自建**（阿里开源） | 中（需自己搭流式服务，调优后可用） | 只有机器成本 | 中上，中文强 | 中高，要部署 + 调参 | 可离线，数据不出机器，答辩加分 |
| **Whisper 本地** | 差（模型大，非流式为主） | 机器成本 | 好 | 中 | 适合离线转写，不适合实时对话 |

**建议**：先用云 ASR 跑通并拿到基线时延，同时把 FunASR 作为备选写进适配层。理由：比赛只有几周，自建流式 ASR 的调优成本被低估得厉害。

**切换成本**：`modules/voice.py` 的 `asr()` 是唯一入口，换供应商只改这一个函数内部。

---

## 3. TTS（语音合成）

| 方案 | 首包延迟 | 自然度 | 成本 | 接入难度 | 备注 |
|---|---|---|---|---|---|
| **云 TTS 流式** | 好（首包 200–400ms） | 好 | 按字符计费 | 低 | 最省事 |
| **CosyVoice 自建** | 中（需 GPU 或较强 CPU，调优后可用） | 好，可定制音色 | 机器成本 | 中高 | 音色可定制，适合做"数字员工"人设 |
| **GPT-SoVITS 自建** | 中差（few-shot 音色克隆，首包偏慢） | 很好 | 机器成本 | 高 | 音色像人，但实时性要下功夫 |
| **浏览器 speechSynthesis** | 极好（本地合成） | 一般，机械 | 零成本 | 极低 | **骨架当前方案**，只适合演示占位 |

**建议**：演示阶段可以继续用 `speechSynthesis` 兜底（保证"有声音"），但**正式提交前必须换成流式云 TTS 或 CosyVoice**，否则"语音自然度与可懂度"这一项会明显吃亏。

**切换成本**：`voice.tts()` 已返回 `mode` 字段（`browser` / `server`），前端据此决定播报方式。换成服务端合成时，前端改一处播放逻辑即可。

---

## 4. 大模型

| 方案 | 首 token 延迟 | 成本 | 工具调用能力 | 备注 |
|---|---|---|---|---|
| **云 API**（通义/DeepSeek/智谱等） | 好（300–600ms） | 按 token 计费，可控 | 好，Function Calling 成熟 | 首选 |
| **本地小模型**（7B 级） | 差（除非有 GPU） | 机器成本 | 中 | 适合做兜底/离线评测 |
| **不调模型，纯规则** | 极好 | 零 | — | 不可行，话术会非常机械 |

**建议**：云 API 为主。注意两点：

1. **首 token 延迟比总时长重要得多**，选型时要测"首 token"而不是"整段返回"；
2. 提示词越长，首 token 越慢。把长指令压到系统提示，把当轮上下文控制在一屏内。

**切换成本**：`dialogue.respond()` 内部调用，换供应商改一处。

---

## 5. 传输：WebRTC 还是 WebSocket（**最大技术风险**）

| 方案 | 是否符合赛题 | 实现难度 | 风险 |
|---|---|---|---|
| **HTTP 整段上传**（当前骨架） | 不符合 | 极低 | 无法做打断，无法做双讲，现场演示会被扣分 |
| **WebSocket 传 PCM 流** | 部分符合（网页端实时，但不是 WebRTC） | 中 | 评审若严格检查"WebRTC"会质疑 |
| **WebRTC（PeerConnection）到自建网关** | 完全符合 | 高 | 需要信令服务器 + 网关，工期紧 |

赛题原文要求「在 **WebRTC 网页端**真实跑通全流程」，且列举了「回声消除、双讲抗噪及 **WebRTC 弱网传输**」。

**建议路径**（按周的推进，不要一步到位）：

1. 第 1 周：HTTP 整段上传先跑通全流程（已完成）；
2. 第 2–3 周：换 WebSocket 传流式 PCM，做 VAD 与打断（能演示打断，已经能拿分）；
3. 第 4 周起：接 WebRTC（`getUserMedia` + `RTCPeerConnection`），把回声消除交给浏览器原生能力。

**不要在第 1 周就上 WebRTC**，会卡死整条链路，四个人全在等一个人。

---

## 6. 存储

| 方案 | 结论 |
|---|---|
| SQLite（当前） | 够用。单机、零运维、评测可反复查同一批数据 |
| PostgreSQL / MySQL | 不需要。赛题不考数据库能力，且云沙箱不支持外挂数据库 |
| 文件 + JSON | 只适合临时实验，查询能力不够 |

**注意**：部署到公网沙箱时文件系统是临时的，事件库会在重新发布后清空。长期跑分要用本地环境。

---

## 7. 推荐组合（写进技术方案书的那一版）

| 层 | 开发期 | 提交前 |
|---|---|---|
| 终端 | 浏览器 + getUserMedia | + WebRTC 传输 |
| 传输 | HTTP 整段 → WebSocket 流式 | WebRTC |
| ASR | 云 API 流式 | 云 API，附 FunASR 备选说明 |
| TTS | 浏览器 speechSynthesis | 云 API 流式 或 CosyVoice |
| 大模型 | 云 API | 云 API |
| 工具 | Mock 接口 | 企业 Mock 接口 + 适配器 |
| 存储 | SQLite | SQLite |

**答辩时的加分说法**：把"为什么这样选"讲成权衡，而不是"我们只会这个"。例如：「ASR 我们选了云服务，因为它把首包延迟压到了 300ms 以内，省下的两周用来做评测闭环；代价是数据出本地，我们用脱敏数据和调用限流来控制风险。」

---

## 8. 需要拍板的三件事

1. **ASR 用云还是自建**（影响角色 1 的第一周排期）
2. **TTS 什么时候从浏览器换成服务端**（影响角色 1 与角色 4 的联调节点）
3. **WebRTC 谁来做**（角色 1 单人可能扛不住，需要角色 4 支援信令）

这三条定了，选型就不会在第三周反复。
