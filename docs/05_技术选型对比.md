# 技术选型对比（供四人统一口径）

> 目的：三个人各自选型会打架，接口对不上、成本算不清、答辩说不圆。
> 原则：**每一层都留一个适配层，选型可替换**。不要把供应商的 SDK 直接写进业务代码。

---

## 1. 选型评分维度与权重

| 维度 | 权重 | 为什么这么定 |
|---|---|---|
| 首包延迟 | 0.4 | 2 秒门槛是硬指标，权重最高 |
| 成本 | 0.2 | 「费用自理」，且评分维度 5 明确要"成本控制" |
| 准确率/自然度 | 0.2 | 直接决定维度 1 与维度 2 的分数 |
| 接入难度 | 0.1 | 四人队伍的工时是最稀缺资源 |
| 合规与可控性 | 0.1 | 涉及个人信息与大模型备案要求 |

---

## 2. ASR（语音识别）

| 方案 | 首包延迟 | 成本 | 准确率 | 接入难度 | 备注 |
|---|---|---|---|---|---|
| **云 ASR 流式**（阿里/腾讯/讯飞） | 好（200–400ms 出中间结果） | 按小时计费，小额可控 | 好，带热词 | 低，SDK 成熟 | 需要账号与实名，数据出本地 |
| **FunASR 自建**（阿里开源） | 中（需自己搭流式服务，调优后可用） | 只有机器成本 | 中上，中文强 | 中高，要部署 + 调参 | 可离线，数据不出机器，答辩加分 |
| **Whisper 本地** | 差（模型大，非流式为主） | 机器成本 | 好 | 中 | 适合离线转写，不适合实时对话 |

**建议**：先用云 ASR 跑通并拿到基线时延，同时把 FunASR 作为备选写进适配层。理由：比赛只有几周，自建流式 ASR 的调优成本被低估得厉害。

**切换成本**：`modules/voice.py` 的 `asr()` 是唯一入口，换供应商只改这一个函数内部。

---

## 3. TTS（语音合成）

| 方案 | 首包延迟 | 自然度 | 成本 | 接入难度 | 备注 |
|---|---|---|---|---|---|
| **云 TTS 流式** | 好（首包 200–400ms） | 好 | 按字符计费 | 低 | 最省事 |
| **CosyVoice 自建** | 中（需 GPU 或较强 CPU，调优后可用） | 好，可定制音色 | 机器成本 | 中高 | 音色可定制，适合做"数字员工"人设 |
| **GPT-SoVITS 自建** | 中差（few-shot 音色克隆，首包偏慢） | 很好 | 机器成本 | 高 | 音色像人，但实时性要下功夫 |
| **浏览器 speechSynthesis** | 极好（本地合成） | 一般，机械 | 零成本 | 极低 | **骨架当前方案**，只适合演示占位 |

**建议**：演示阶段可以继续用 `speechSynthesis` 兜底（保证"有声音"），但**正式提交前必须换成流式云 TTS 或 CosyVoice**，否则"语音自然度与可懂度"这一项会明显吃亏。

**切换成本**：`voice.tts()` 已返回 `mode` 字段（`browser` / `server`），前端据此决定播报方式。换成服务端合成时，前端改一处播放逻辑即可。

---

## 4. 大模型

| 方案 | 首 token 延迟 | 成本 | 工具调用能力 | 备注 |
|---|---|---|---|---|
| **云 API**（通义/DeepSeek/智谱等） | 好（300–600ms） | 按 token 计费，可控 | 好，Function Calling 成熟 | 首选 |
| **本地小模型**（7B 级） | 差（除非有 GPU） | 机器成本 | 中 | 适合做兜底/离线评测 |
| **不调模型，纯规则** | 极好 | 零 | — | 不可行，话术会非常机械 |

**建议**：云 API 为主。注意两点：

1. **首 token 延迟比总时长重要得多**，选型时要测"首 token"而不是"整段返回"；
2. 提示词越长，首 token 越慢。把长指令压到系统提示，把当轮上下文控制在一屏内。

**切换成本**：`dialogue.respond()` 内部调用，换供应商改一处。

---

## 5. 传输：WebRTC 还是 WebSocket（**最大技术风险**）

| 方案 | 是否符合赛题 | 实现难度 | 风险 |
|---|---|---|---|
| **HTTP 整段上传**（当前骨架） | 不符合 | 极低 | 无法做打断，无法做双讲，现场演示会被扣分 |
| **WebSocket 传 PCM 流** | 部分符合（网页端实时，但不是 WebRTC） | 中 | 评审若严格检查"WebRTC"会质疑 |
| **WebRTC（PeerConnection）到自建网关** | 完全符合 | 高 | 需要信令服务器 + 网关，工期紧 |

赛题原文要求「在 **WebRTC 网页端**真实跑通全流程」，且列举了「回声消除、双讲抗噪及 **WebRTC 弱网传输**」。

**建议路径**（按周的推进，不要一步到位）：

1. 第 1 周：HTTP 整段上传先跑通全流程（已完成）；
2. 第 2–3 周：换 WebSocket 传流式 PCM，做 VAD 与打断（能演示打断，已经能拿分）；
3. 第 4 周起：接 WebRTC（`getUserMedia` + `RTCPeerConnection`），把回声消除交给浏览器原生能力。

**不要在第 1 周就上 WebRTC**，会卡死整条链路，四个人全在等一个人。

---

## 6. 存储

| 方案 | 结论 |
|---|---|
| SQLite（当前） | 够用。单机、零运维、评测可反复查同一批数据 |
| PostgreSQL / MySQL | 不需要。赛题不考数据库能力，且云沙箱不支持外挂数据库 |
| 文件 + JSON | 只适合临时实验，查询能力不够 |

**注意**：部署到公网沙箱时文件系统是临时的，事件库会在重新发布后清空。长期跑分要用本地环境。

## 7. 推荐组合（写进技术方案书的那一版）

| 层 | 开发期 | 提交前 |
|---|---|---|
| 终端 | 浏览器 + getUserMedia | + WebRTC 传输 |
| 传输 | HTTP 整段 → WebSocket 流式 | WebRTC |
| ASR | 云 API 流式 | 云 API，附 FunASR 备选说明 |
| TTS | 浏览器 speechSynthesis | 云 API 流式 或 CosyVoice |
| 大模型 | 云 API | 云 API |
| 工具 | Mock 接口 | 企业 Mock 接口 + 适配器 |
| 存储 | SQLite | SQLite |

**答辩时的加分说法**：把"为什么这样选"讲成权衡，而不是"我们只会这个"。例如：「ASR 我们选了云服务，因为它把首包延迟压到了 300ms 以内，省下的两周用来做评测闭环；代价是数据出本地，我们用脱敏数据和调用限流来控制风险。」

---

## 8. 需要拍板的三件事

1. **ASR 用云还是自建**（影响角色 1 的第一周排期）
2. **TTS 什么时候从浏览器换成服务端**（影响角色 1 与角色 4 的联调节点）
3. **WebRTC 谁来做**（角色 1 单人可能扛不住，需要角色 4 支援信令）

这三条定了，选型就不会在第三周反复。

## 9. 开源可复用组件清单（2026-11 核实）

> 如果你只想知道"能不能不自己写"，看这一节就够了。

### 9.1 先说清一件事：能"直接采用"的是管道，不是产品

LiveKit Agents 和 Pipecat 都是**编排框架**，不是开箱即用的语音助手。它们提供 VAD、轮次判定、打断协调、传输层，但**模型仍要你自己接 key 或自己部署**。所以"装上就有语音客服"是不成立的。

它们真正的价值在于：**赛题要求的"WebRTC + 打断 + 回声消除 + 双讲抗噪"，恰好是这两个项目已经解决好的部分**。自己写等于重造 jitter buffer、轮次判定、barge-in 协调这三样，而这三样恰恰是最难调的部分。

### 9.2 三个层次的清单

| 层 | 项目 | 许可 | 跑在哪 | 公开延迟 | 我们能用在哪 |
|---|---|---|---|---|---|
| **VAD** | silero-vad | MIT | CPU 实时，模型约 2MB | 帧级，几十 ms | 替换现在恒为真的占位 VAD |
| **轮次判定** | Pipecat Smart Turn v3.2 | BSD | CPU，8MB 量化 ONNX | 部分 CPU 上约 10ms | 解决"用户停顿被误判成说完" |
| **流式 ASR** | FunASR `paraformer-zh-streaming` | 见仓库 | CPU 可跑，不必 GPU | 约 600ms 出增量文本 | 首选：中文强、带热词、可离线 |
| **流式 ASR（备选）** | sherpa-onnx | Apache-2.0 | C++/ONNX，CPU 高效 | 与上面同量级 | 包体小、无 Python 依赖，适合部署 |
| **编排框架（重）** | LiveKit Agents 1.8.x | Apache-2.0 | 需 SFU + Redis + worker | 打断 <100ms（房间级 flush） | 沙箱单端口跑不起来，**不建议现在上** |
| **编排框架（轻）** | Pipecat 1.12.x | BSD-2 | 纯 Python 管线，可跑单机 | 打断 <100ms（帧级 cancel） | 中期可选项，可只用它的 transport + turn 检测 |
| **TTS** | CosyVoice 2 | 见仓库 | 有 GPU 才流畅 | 流式首包 200ms 级 | 有 GPU 时的备选，音色可定制 |
| **TTS（云）** | 阿里/腾讯/讯飞流式 | 商业 | — | 首包 200–400ms | **首选**：本地 CPU 合成太慢 |
| **端到端语音** | Moshi | CC-BY 4.0 | 需 GPU，约 6GB(int4) | 约 200ms，全双工 | 英文为主，中文不可用 |
| **端到端语音** | Qwen3-Omni | Apache-2.0 | 需较大显存 | 首包约 211ms（官方口径） | 半双工 + 演示级打断，见 9.4 |

> 版本号与数字来自 2026-10/11 的公开文章与仓库说明，**会变**。落地前按自己机器实测，不要直接抄进方案书。

### 9.3 对我们这个项目的四条建议

1. **VAD 与轮次判定立刻换成开源件**：Silero VAD + Smart Turn。自己写能量门限的问题不是写不出来，而是**自适应噪声底没有想象中好调**，换个房间就要重调，而 Smart Turn 解决的"用户思考时停顿"问题，手写规则基本无解。
2. **ASR 两条都留着，先做"手上已经有账号"的那条**。本地 FunASR 的三个好处是真的：中文强且带热词、数据不出机器（答辩加分）、流式模型在 CPU 上就能跑；代价是要装 torch、下模型、调 chunk 参数，顺利半天、不顺一天。云 ASR 的好处是**当天就能通**、首包更短（200–400ms vs 本地约 600ms 一档），代价是要实名账号和按量计费。因为 `asr()` 是唯一入口，**两条可以在一个函数里切换**，不要提前二选一。
3. **TTS 继续走云**。CosyVoice 2 在 CPU 上合成慢到不能用，而有 GPU 的队伍是少数。云 TTS 首包 200–400ms，正好在预算内。
4. **不要整包上 LiveKit**。它需要 SFU + Redis + worker 进程，我们的线上沙箱只有一个端口，跑不起来；本地演示要额外起三四个服务，现场出问题的概率不值这个收益。Pipecat 更轻，可以作为 K3 之后的"传输层替换"选项。

### 9.4 为什么不用端到端语音大模型

看着很诱人：延迟 200–500ms，全双工，能插话。但它和这个赛题是错配的。

| 赛题要什么 | 端到端模型给什么 |
|---|---|
| 六个环节一个不能漏，可审计 | 端到端生成，**没有显式的环节概念** |
| 工具调用 + 结构化回写 + 幂等 | 工具调用能力弱于同级 LLM，且难保证参数正确 |
| 全量事件链，供质检与归因 | 中间状态不可见，**无法落事件** |
| 失败可归因（没听清/没听懂/没查对） | 出错时说不清错在哪一层 |
| RSI 自进化：改提示词/话术/知识 | 改什么、改了有没有用，都难以定位 |

**结论**：端到端适合"聊天型"语音助手，不适合"要对结果负责"的外呼任务。答辩时如果被问"为什么不上端到端"，这就是标准答案——**不是不会，是任务要求可审计的中间状态**。

### 9.5 一句话总结

**ASR 不需要大模型，但整个系统仍然需要 LLM**：ASR 用专用声学模型（FunASR/Whisper 这类）又快又准；"大模型"是用在对话编排那一层的（佟欣的活）。把这两件事分开，选型就不会乱。

## 10. 成本估算（2026-11 查价）

> 结论先给：**不贵。** 全云方案一通 2 分钟电话约 **4–7 分钱**，整个比赛周期（开发 + 评测 + 演示）**按克制用量约 18 元，放开跑压测也就一百元以内**；把免费额度用上，可能趋近 0。真正贵的不是 API，是"想自建 TTS 带来的 GPU"和"你调参的时间"。

### 10.1 单价（阿里云百炼口径，按量付费标准价）

| 项 | 单价 | 换算 |
|---|---|---|
| **Paraformer 实时识别**（paraformer-realtime-v2，本项目用这个） | 0.00024 元/秒 | ≈ 0.86 元/小时 |
| fun-asr-realtime（新一代，噪声下更稳） | 0.00033 元/秒 | ≈ 1.19 元/小时 |
| Paraformer 录音文件识别（paraformer-v2） | 0.00008 元/秒 | ≈ 0.29 元/小时；**需要公网可访问的音频 URL，本项目暂时用不上** |
| CosyVoice v3.5-flash 合成 | 0.8 元/万字符 | 1 个汉字记 2 字符 |
| CosyVoice v3.5-plus 合成 | 1.5 元/万字符 | 同上 |
| qwen3.7-flash | 输入 0.24 / 输出 0.96 元每百万 token | 极便宜 |
| qwen3.8-flash | 输入 0.8 / 输出 2.7 元每百万 token | 便宜 |
| qwen3.8-max | 输入 12 / 输出 36 元每百万 token | 不要用在实时对话 |

> **一处必须纠正的错**：本文早前把 "0.288 元/小时" 当成了实时识别的价格，那其实是**录音文件识别**的价。实时识别按秒计费 0.00024 元/秒，折合 0.86 元/小时，是它的三倍。总成本量级不变，但报价单里不能写错单价。
>
> 腾讯云实时识别约 1.8 元/小时起，豆包流式 1.8–2.4 元/小时，讯飞约 2.0 元/小时。百炼仍是三家里最便宜的，**没必要为省几毛钱换供应商**。

### 10.2 一通 2 分钟电话的拆解

假设：用户说 90 秒，客服回 5 句共约 150 字，每轮输入 1500 token、输出 200 token，共 6 轮。

| 项 | 用量 | 费用 |
|---|---|---|
| ASR（Paraformer 实时） | 120 秒 × 0.00024 | 0.0288 元 |
| TTS（CosyVoice flash） | 150 字 = 300 字符 | 0.024 元 |
| LLM（qwen3.7-flash） | 9000 输入 + 1200 输出 token | 0.0033 元 |
| **合计** | | **约 0.056 元（5 分半）** |

换成更贵的组合（fun-asr-realtime + Plus 音色 + qwen3.8-flash），约 **0.09 元/通**。

**这个数字可以直接写进方案书**——赛题要求"对成本进行量化分析"，"成本/通 ≈ 0.06 元、其中识别占一半"是有说服力的具体数字，比"我们控制了成本"强得多。

### 10.3 比赛周期总成本

| 场景 | 用量 | 费用 |
|---|---|---|
| 开发调试（边改边测，200 通短通话） | 200 × 0.056 | ≈ 11 元 |
| 评测跑批（30 条用例 × 跑 100 遍，纯文本不耗 ASR） | 只用 LLM | ≈ 5 元 |
| 真人录音采集（补 100 条语音用例） | 100 × 0.056 | ≈ 6 元 |
| 答辩演示（20 次） | 20 × 0.056 | ≈ 1 元 |
| **合计** | | **≈ 23 元** |

压测另算：连续跑 10 小时语音（模拟 300 通），ASR 约 8.6 元、TTS 约 7 元，仍是两位数。

### 10.4 真正贵的三个东西（都不在 API 账单里）

1. **自建 TTS 要 GPU**。CosyVoice 在 CPU 上慢到不能用，租云 GPU 按 2–8 元/小时计，开发期每天 8 小时 × 10 天 = **160–640 元**，比全云 API 贵一个数量级。**这是"开源免费"最大的错觉**：软件免费，机器不免费。
2. **自建 ASR 的时间**。FunASR 装依赖、下模型、调 chunk 参数，顺利半天、不顺一天。按你的时间成本算，远比几十块 API 费贵。
3. **压测不设限**。忘了限流跑一整晚，或者死循环重复调用，几百块也能烧掉。必须设单通时长上限与并发上限。

### 10.5 五条把成本压到接近 0 的做法

1. **吃免费额度**：百炼新用户各模型有 100 万 token 额度（90 天有效）；Paraformer 有 10 小时免费；CosyVoice 每个模型 1 万字符免费。省着点用，比赛期可能一分不花。
2. **分环境**：本地做逻辑调试时用假 ASR/TTS（`fake: true`），只在验证音质与时延时调真接口。逻辑调试占总调试量的八成，但一分钱不花。
3. **TTS 结果缓存**：同一句话（开场白、结束语、兜底话术）合成一次后存音频文件复用。开场白那几句会被播上千遍。
4. **限流兜底**：`config/` 里配单通最长 3 分钟、并发上限 2；超限直接走兜底话术，不调云。
5. **用 flash 档模型**：实时对话不需要旗舰模型，qwen3.7-flash 的输入价是 max 档的 1/50。

### 10.6 一句话给答辩

> "成本/通约 0.04 元，云 API 只占整体投入的 5% 以下，主要成本是调试与评测的人力。我们没有自建 TTS，因为租 GPU 的费用是云 API 的十倍，且赛题并不考核推理性能。"

**这个回答同时答了三个评分点**：成本量化、技术权衡、工程判断。

### 10.7 一条必须避免的错误省钱方式

**不要为了省几十块钱，推迟接真语音。**

曾经有过这样的建议："前两周用本地 ASR + 浏览器 TTS，第三周再切云"。这是错的，因为下面这些东西**假管道根本测不出来**：

| 只有真语音能验的 | 假管道会给你什么 |
|---|---|
| 首字时延 T0–T4 | 假 TTS 延迟恒为 0，算出来的 P50 是假的 |
| 打断能否真停住 | 浏览器 `speechSynthesis` 的取消行为与流式音频完全不同，用它会得出错误结论 |
| 回声自激 | 需要真实"麦克风 + 扬声器"回路才复现，假 TTS 不发声就没有回声 |
| VAD 门限与噪声 | 需要真实房间噪声与设备差异 |
| 音色与可懂度 | 维度 1 的评分就是这么来的 |

按这个方式省下的钱是几十元，代价是**两周后才发现打断做不出来**——这个损失没法用钱衡量。

**正确的省钱方式是"调短"，不是"调晚"**：

| 做法 | 单次费用 | 每天 40 次 | 两周 |
|---|---|---|---|
| 每次跑完整 3 分钟通话 | 约 0.04 元 | 约 1.5 元 | 约 21 元 |
| 每次只测 30 秒一轮 | **约 0.012 元** | **约 0.5 元** | **约 7 元** |

同一天调同样的次数，只因为"每次只测一轮而不是一整通"，成本差三倍多。**所以第一周就该接云**，但每次只测一轮、只验证一个点。

配套三个闸门：① 单次录音上限 30 秒（调试期）；② 每天预算上限 2 元，超了打印告警；③ 逻辑回归永远走文本，不走语音。

> 价格数据查于 2026-11，会变。提交前按自己实际用量拉一次账单，用真实数字替换估算。
